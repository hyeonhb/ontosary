# 첫 변경 계획의 가림 판정

계획 본문 네 건을 과업 안에서 임의로 X/Y에 배정했다. 제출 순서, 역할, 요청 여부와 질문, 조사 경위 별첨, 사용량은 가림 판정에 사용하지 않았다. 같은 진행자가 사전 기준과 고정 소스를 대조했으며, 별도의 독립 채점자 간 일치도는 측정하지 않았다. 아래 판정은 계획에 필요한 설명과 검사가 있는지를 뜻한다.

### 공개 결제·배송 수단

| 사전 기준 | X 판정과 근거 | Y 판정과 근거 |
| --- | --- | --- |
| M1 두 active 목록의 공개 타입 | 충족. 1·2항에서 두 Public 타입과 두 서비스를 연결한다. | 충족. 1항에 두 필드와 공개 타입이 명시돼 있다. |
| M2 설정 기반 타입과 공개 범위 | 충족. Shop에서 생성한 엔티티별 필드 타입을 재사용하고 내부·비공개 필드를 제외한다. | 충족. 같은 타입을 재사용하고 두 제외 조건을 스키마·응답에 적용한다. |
| M3 두 목록의 스칼라·관계 값 | 충족. 2항에서 양쪽 공개 타입에 원본 ID를 붙이는 기존 resolver를 재사용하고 저장값·관계 조회를 연결한다. | 충족. 2·3항에서 양 서비스가 반환한 엔티티의 값과 ID를 공개 resolver로 넘기는 경로를 제시한다. |
| M4 기존 목록 보존 | 충족. 현재 채널, 결제 활성, 배송 삭제, 요청 언어를 모두 보존한다. | 충족. 3항에 채널별 활성 결제·미삭제 배송·번역을 명시한다. |
| M5 회귀 | 충족. 두 목록의 실제 공개 값·관계, 비공개 필드, 제외할 수단을 E2E로 비교한다. | 충족. 두 목록의 스칼라·관계 반환, 숨긴 필드 선택 거부, 타 채널·비활성·삭제 수단 제외를 검사한다. |

부모 소스에는 Shop용 필드 타입 생성과 필터가 있고, 기존 quote도 엔티티용 타입을 사용한다. 기존 resolver는 저장된 customFields와 원본 ID를 전달하고, 관계가 미리 로드되지 않았을 때 ID로 조회하는 경로가 있다. 두 계획 모두 이를 공개 타입에 연결하는 다른 설계를 설명했으므로 서비스의 eager load를 명시하지 않았다는 이유로 감점하지 않았다. 공개 필드가 하나도 없을 때 X는 필드 생략, Y는 null을 제안한다. 이 세부 계약은 사전 기준에 지정되지 않았다. 실제 GraphQL 부팅·응답 호환성은 실행 전 미확인이다. ### 판매 채널별 상품 주소

| 사전 기준 | X 판정과 근거 | Y 판정과 근거 |
| --- | --- | --- |
| S1 후보 선택 시점과 채널 | 충족. getRawOne 이전에 현재 채널을 조인하는 이유를 잘못 선택된 ID와 후속 빈 결과로 설명한다. | 충족. findOne이 후보를 다시 고르지 않는다는 점과 ID 선택 전 조인을 연결한다. |
| S2 삭제·언어 | 충족. 삭제 제외와 요청·기본·기타 언어 순서를 명시한다. | 충족. 동일한 세 단계의 정렬과 삭제 제외를 유지한다. |
| S3 기존 로딩·미발견 | 충족. ID와 relations를 findOne에 전달하고 타 채널에만 있는 경우 null을 검사한다. | 충족. 기존 findOne 호출·번역과 타 채널 또는 없는 slug의 null을 명시한다. |
| S4 두 채널 회귀 | 충족. 두 상품에 같은 영어 slug를 부여하고 각각 자기 상품 ID가 나오는지 검사한다. | 충족. 두 채널 토큰과 별도 상품·동일 slug를 설정하고 양방향 ID를 확인한다. |
| S5 추가 회귀 | 충족. 한 상품에만 독일어 번역을 두고 각 응답 언어와 타 채널만 있는 경우를 검사한다. | 충족. 타 채널 전용 slug의 null, 기본 언어 폴백, 삭제 상품의 slug 재사용을 검사한다. |

부모의 첫 쿼리는 번역별 후보에서 ID 하나를 뽑고 두 번째 조회는 이미 정해진 ID와 채널을 사용한다. X는 언어 우선순위를 이용해 기존 오선택이 드러나도록 예를 구체화했다. Y의 대칭 조회와 음성 대조도 사전 기준을 충족한다.
