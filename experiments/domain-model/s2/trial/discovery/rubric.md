# 첫 수정 전 제출의 판정표 · 평가자 전용

독립 리뷰어는 조건·예산·최종 소스·동작 점수를 가린 채 봉인한 `impact` 하나를 읽는다. 원래 리비전에서 제출이 가리키는 줄·심볼·코드 인용을 열어 설명을 대조한다. 파일명이 맞더라도 관계가 틀리거나, 레이블이나 점수만 있고 코드 위치가 없으면 그 항목은 0이다. 네 항목을 각각 0/1로 기록하고 원문 구절과 판정 근거를 남긴다. 4/4일 때 발견 성공이다. 미제출은 별도로 표시한다. 평가자 간 해석이 갈리면 같은 원문으로 재검토하며 수정 결과로 발견 점수를 보충하지 않는다.

| 항목 | 1점에 필요한 관계와 코드 근거 |
| --- | --- |
| 노출 | 대상이 Aggregate가 아니며 Cancelled가 nextStates에 있어야 한다. 잔액 변경이 이 게이트를 넓혀서는 안 된다. |
| 문구 | 기존 템플릿이 Settled 존재에 따라 환불·취소와 취소 전용 문구를 고른다. 모두 소진 시 취소 전용, 잔액이 있으면 기존 문구다. |
| 클릭 | 실제 메뉴 핸들러에서 취소·환불 대화상자로 연결되는 위치를 찾는다. 잔액이 없으면 취소, 양수여도 PaymentAuthorized 또는 active이면 기존 직접 취소를 유지한다. |
| 잔액 | 각 Settled 결제의 amount에서 Failed를 제외한 환불 total 합을 뺀다. 어느 한 결제에라도 양수가 남는지 판단한다. Pending이나 실패 이력을 잘못 처리하거나 첫 결제만 검사하면 0이다. |

**인정할 수 있는 근거**에는 정확한 심볼과 해당 데이터 흐름, 템플릿 바인딩과 그 번역 키, 직접 읽은 파일의 행 범위, 원본까지 추적 가능한 부록 좌표가 있다. 필수 파일 목록이나 동일한 변수명은 없다. 서버의 환불 한도와 UI 후보 결제의 범위는 각각 확인한다. 예컨대 서버의 `getPaymentRefundTotal`만 인용하면 Failed 제외는 확인할 수 있지만 UI에서 Settled만 고르는 규칙까지 입증하지는 못한다.

## 수기 교정 사례

아래 D는 `OrderDetailComponent`, T는 같은 컴포넌트의 템플릿, H는 `getRefundablePayments`, S는 `PaymentService`다. 숫자는 고정 소스의 행이다. 첫 줄은 세 모의 참가자가 실제로 낸 답을 판정했고, 그 아래는 평가자 대조 답안이다. 대조 답안에서 ‘유지’한 항목은 첫 답안의 해당 문장을 그대로 사용한다.
