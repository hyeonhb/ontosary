# R20 보완 — 진단 기록 실패와 정리 실행 분리

2026-11-18. [결과 중심 지시](2026-11-18-s2-r20-outcome-instructions.md)에 따른 국소 보완이다. **진단 예산이 소진돼도 정상 대체 stop/delete가 실제 완료해 가짜 VM 상태를 제거한다.** 실행 오류·진단 오류·부재 확인을 분리했으며 Python32와 pnpm check304가 통과했다. 새 VM·실제 limactl/CLI·trace·정책·자격 증명·provider/model 실행은 없다.

## 구현과 이유

수정 전 `Smoke.cmd(safety=True)`는 남은 디스크 진단 용량으로 subprocess capture 한도를 계산했다. 용량이0이면 stop/delete의 첫 진행 출력만으로 process group을 SIGKILL해 실제 정리를 중단했다.

수정 후 safety 명령은 stream당 최대1MiB 메모리에 먼저 받아 실행한다. 초과 출력은 계속 배출하되 보관하지 않으며, 명령 종료 뒤 남은 디스크 용량만큼 저장한다. 진단 조회·stdout/stderr·명령 메타데이터 기록 실패는 후속 정리를 막지 않는다. 일반 실험 명령은 기존처럼 출력 초과 시 중단한다. 저장량은 기존4MiB 중64KiB 메타데이터 여유를 제외한 범위이고 UTF-8 재인코딩도 byte 단위로 제한한다. 명령 마감은 기존 stop/delete 각30초·list8초·process 조회5초이며 pipe EOF 뒤 살아 있는 프로세스도 마감에 종료한다. 종료 신호는 한 번 보내고 유한 reap을 유지한다.

정리 결과에는 명령별 exit/timeout/truncation, 진단 저장 상태, 최종 VM/root 부재를 따로 남긴다. stop 오류 뒤 delete와 온전한 부재 조회가 성공하면 `complete`와 앞선 오류가 함께 남는다. 조회 실패·timeout·절단·JSON/PID행 파싱 불능은 `unconfirmed`이며 root를 보존한다. 진단 파일을 새로 만들어 잠그는 대신 이미 존재하는 ownership 파일에 배타 잠금을 걸고 소유권을 재확인한다. receipt와 disposed marker 기록 실패도 정리 후 진단 오류로 반환한다. 소유권 자체를 읽거나 검증하지 못할 때 정리를 우회하지 않는다.

## 반례와 회귀

[before.json](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/before.json)은 원래 `2008351` 코드, [after.json](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/after.json)은 수정 코드로 같은 fixture를 실행한 원시 결과다. fixture는 실제 Python subprocess가 진행 출력을 낸 뒤150ms 후 완료 표식을 만들고, delete가 소유 root 밖의 VM 상태 파일을 삭제한다. 실제 `dispose → cleanup → cmd → capture`를 통과하며 단순 호출 확인으로 성공 판정하지 않는다. fake 프로세스의 보통 상한은3초, 멈춤 주입은0.25초로 제한한다.

| 조건 | stop 완료 | delete 완료 | 가짜 VM 상태 | 판정 |
| --- | --- | --- | --- | --- |
| 수정 전, 정상 예산 | 예 | 예 | 제거 | complete |
| 수정 전, 진단 stream4,128,768bytes | 아니오 | 아니오 | 잔존 | unconfirmed |
| 수정 후, 같은 예산 소진 | 예 | 예 | 제거 | complete |
| 수정 후, 진단 조회/기록 실패 | 예 | 예 | 제거 | complete + diagnosticErrors |
| 수정 후, 양 stream 출력 초과 | 예 | 예 | 제거 | complete + truncation |
| stop 실패/timeout | 아니오 | 예 | 제거 | complete + stop 오류 |
| delete 실패/timeout | 예 | 아니오 | 잔존 | unconfirmed |
| list/process 조회 실패·절단·timeout·파싱 불능 | 예 | 예 | 제거됐으나 입증 불가 | unconfirmed |

[최종 Python 로그](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/tests-final.log)의32개는 기존17개와 추가15개다. 위 조건 외에도 모든 report 쓰기 실패, 쓰기 불가 진단 디렉터리의 lock, 잘못된 이전 receipt, marker 실패, 소유권 불일치, pipe EOF 뒤 timeout, 일반 명령의 출력 초과 중단을 포함한다. 소진·대량 출력 fixture는 stream 저장4,128,768bytes 이하와 메타데이터 포함4MiB 이하도 검사한다. [pnpm check](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/pnpm-check.log)는304테스트·타입 검사·예제 빌드를 통과했다. 분석기/제품 의미는 변경하지 않아 pnpm experiment는 실행하지 않았다.

초기 검사 실패도 보존했다. [초기 로그](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/tests-first.json)는 fake Python 시작까지 포함한0.5초가 정상 경로에 부족한 경우와 죽는 process group에 SIGKILL을 반복해 EPERM이 발생한 경우다. fixture 정상 상한을3초로 정하고 product capture의 신호를 한 번으로 제한한 뒤 통과했다. [초기 반례](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/before-initial.json)의 정상 stop 미완료는 이 시간 설정의 영향이며 최종 before/after는 동일한 수정 fixture로 다시 비교했다.

## 코드와 과거 관측 보존

검증 구현은 **`e7759f9f31eb45f95a76a0f82077ec837e9197ca`**다. after.json에 runtime·회귀·historical helper의 SHA-256을 기록했고 before.json에는 당시 복원 코드와 같은 fixture hash를 기록했다. PR #70의 원래 head는 `2008351b926aa8c7f7c762f297c0be8b43c2e2a9`, 최신 main 기준은 `78ff102166b9fc3122e38b47b49cef5526d99623`이며 merge `48b213f`로 반영했다. 뒤따르는 문서/증거 커밋은 구현을 바꾸지 않는다.

`verify_historical.py`는 Git2008351에서 원래8개 smoke 소스·verifier·필요한 공유 helper를 임시 디렉터리에 복원한다. 원래 freeze와 hash를 대조한 후 **당시 verifier와 runtime**으로 원래 저장 증거를 검증한다. 결과는 blocked-before-payload, VM1/sandbox1, payload 미시작, cleanup complete, index98파일/121,674bytes로 유지됐다. [보존 대조](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/preservation.json)는 index 자체를 포함한 과거99개 tracked 파일의 bytes가 전부 같음을 확인했다. [현재 코드 거부](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/current-code-rejection.json)는 원래 verifier가 변경 runtime을 옛 freeze로 인정하지 않음을 확인한다. hash 예외나 증거 덮어쓰기는 없다.

재현은 저장소 root에서 다음 두 로컬 명령으로 가능하다. 두 번째 명령에는 Git2008351 이력이 필요하다.

```sh
/opt/homebrew/bin/python3.13 -m unittest discover -s experiments/domain-model/s2/trial/vm-cli-smoke -p 'test_*.py' -v
/opt/homebrew/bin/python3.13 experiments/domain-model/s2/trial/vm-cli-smoke/verify_historical.py --reproduce-r20
```

## 범위와 인계

작업 착수는 [원시 시각](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/first-command.json)의07:04:54 UTC다. 읽기·수정·검사·보고의 종료 시각과 소요 시간은 [완료 기록](../../experiments/domain-model/s2/verification/2026-11-18-r20-cleanup/completion.json)에 남긴다. 총45분 범위 안의 작업이며 실제 실행으로 전환하지 않았다.

이번 결과는 R20의 로컬 정리 경로 보완이다. 디스크가 완전히 쓰기 불가하면 영구 receipt 저장은 보장하지 못하며 호출자에게 `receiptWritten=false`와 오류를 반환한다. OS/파일시스템 자체의 무응답이나 실제 VM 명령의 성공을 이 fake 검증으로 보장하지 않는다. 기존 마감·메모리·저장 한도를 확대하지 않았고 새 supervisor/제출 계약도 만들지 않았다.

PR #70을 갱신하고 **독립 보완 리뷰 전 병합하지 않는다.** PR #67의 `ed0250b` 초안은 그대로 유지한다. EROFS 정확한 쓰기 대상·R11 unresolved·R12 기존 범위·production/live 거부·fixtureOnly=true·validSubmission=false·trialAuthorized/readyForTrial=false·results=null·H-O/H-F 미검증은 그대로다. 후속 실제 시험과 C안 전체 통합·본 비교의 범위/예산은 리뷰 뒤 결정한다.
