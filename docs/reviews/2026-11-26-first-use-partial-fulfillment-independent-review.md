## 전달본과 공개 CLI

고정 Vendure Git 사본에서 `prepare.sh`로 두 역할의 디렉터리를 새로 만들었다. 각각 원본 파일 4,735개의 Git blob 식별자가 모두 일치했다. 작성자 사본의 Vendure 트리에 추가된 파일은 앱 범위 설정 하나였다. agent 사본에는 원본 Vendure 트리와 후속 요청, 제공한 모의 인계 기록만 있었고 모의 기록의 바이트가 보존됐다. 두 시작 안내를 읽고 참가자 자료에서 검토자용 주문 예와 근거 파일 목록이 빠져 있는지 확인했다.

이미 의존성이 설치된 작성자 사본에서 공개 CLI를 다시 실행했다. 앱 설정의 `scan`은 구현 파일 552개, 함수 4,097개, 타입 1,640개, 진단 0개, 누락 설명 715개를 반환했다. 주문 상세와 출고 창의 관련 메서드가 실제 파일과 줄을 가리켰다. `concepts`는 객체 4,097개·속성 7,033개에서 한도 128·64를 보고하고 종료 코드 1로 끝났다. 설치 비용은 개발 세션의 준비 기록에 의존한다. ## 검토 사례의 변별력

고정 소스의 템플릿 바인딩과 초기화 코드를 읽고, 주문 진입·결제 차액·품목 수량·제출 판정 메서드를 추출해 보고서의 주문으로 실행했다. 재고 추적을 켜고 처리 양식을 유효하다고 두었다. 다음은 프런트엔드 메서드 단위 결과다.

| 남은 품목의 재고 | 주문에서 출고 창 진입 허용 | 두 품목의 수량 상한 | 초기 선택으로 제출 허용 |
| ---: | --- | --- | --- |
| 0 | 예 | 0, 0 | 아니오 |
| 1 | 예 | 1, 0 | 예 |

재고가 1일 때 사용자가 선택 수량만 0으로 바꾸자 상한은 1이고 제출은 비활성화됐다. 따라서 ‘출고할 수 있는 품목이 없음’ 안내를 단순히 제출 버튼의 비활성 상태로 판정하는 제안을 구별할 수 있다. 브라우저 조작과 서버 출고 처리는 이 관측 범위 밖이다. 저장소 검사 304개와 기존 예제 비교 4/4도 통과했다.

## 다음 판단

현재 설정으로 코드 탐색, 기록 작성, 후속 변경 제안에 대한 첫 사용 관찰을 진행할 수 있다. FCA는 후보 생성 전에 멈추므로 후보의 품질과 모델 작성 기여는 미측정으로 둔다. 상한을 높이거나 정답 위치로 범위를 미리 좁히는 작업을 선행할 이유는 없다. 다음 결정은 처음 접하는 TypeScript 개발자를 작성자로 배정할지, 별도 합의로 두 agent 간 대리 인계를 관찰할지다. 대리 인계에서 사람의 첫 사용성과 소요 시간은 계속 미측정이다.
