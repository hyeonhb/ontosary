# S2 독립 리뷰 · Vendure #4348 참가 패치 채점

**PR #107의 병합과 A/B/C 참가 실행을 보류한다.** `4638eed`에서 보고된 네 제출은 재현됐다. 같은 채점기에 추가 제출 두 건을 적용하니 저장 시점에 잘못된 금액이 전달돼도 만점이 나왔고, 취소 요청 뒤 상품 수량이 그대로인 제출은 업무 실패 집계에서 빠졌다. 두 문제 모두 메모리 저장소와 현재 여섯 사례로 확인할 수 있다. [개발 지시](2026-11-26-s2-shipping-submission-grading-instructions.md) · [검토한 PR](https://github.com/hyeonhb/ontosary/pull/107)

## 재현된 결과

보고서의 환경에 맞춰 Python 3.12.10과 Node 22.19.0으로 새 디렉터리에서 `reproduce.py --verify`를 실행했다. 네 제출과 추가 대조 다섯 건의 통합 JSON이 보관본과 바이트 단위로 일치했다. 원본과 부분 수정은 서로 다른 두 사례에서 실패해 각각 4/6이었다. 업스트림 수정과 외부 헬퍼를 사용한 수정은 각각 6/6이었고, 호출부를 유지한 채 헬퍼 본문만 바꾸자 4/6이 됐다. 패치 적용 거부, 관측 밖 서비스, 미실행 분기, 대역 필드 부재도 보고대로 구분됐다. 기존 선정 재생 결과도 일치했다. PR head에서 `pnpm check`의 테스트 304개와 빌드, `pnpm experiment`의 비교 4개가 통과했다. 참가 호출은 0회다. [개발 보고서](https://github.com/hyeonhb/ontosary/blob/4638eed/docs/reviews/2026-11-26-s2-shipping-submission-grading.md)

## 실제 채점이 달라진 두 제출

**R26 · 재계산을 저장 뒤로 옮겨도 6/6.** 업스트림의 차감식은 유지하고 주문을 저장한 다음 합계를 재계산하도록 했다. 메모리 저장소는 `save`에 전달된 객체의 참조를 보관하고, 관측기는 취소 메서드가 끝난 뒤 같은 객체에서 금액을 읽는다. 별도 진단에서 주문 저장 호출 순간의 네 숫자를 복사해 보니 여섯 사례 모두 취소 전 값인 `1000 / 1200 / 1200 / 1400`이었다. 전체 취소 네 건의 세후 주문 합계는 저장 시점에 1,400, 메서드 종료 때 0이었다. 일부 취소 두 건도 각각 1,400과 1,300이었다. 실제 DB에 관한 추정 없이 저장소에 전달된 값의 오류를 관측할 수 있다. [저장 대역](https://github.com/hyeonhb/ontosary/blob/4638eed/experiments/domain-model/s2/trial/angular-shipping/observe.mjs#L70-L72) · [금액 채점](https://github.com/hyeonhb/ontosary/blob/4638eed/experiments/domain-model/s2/trial/angular-shipping/observe.mjs#L98-L105)

**R27 · 실제 수량 오류 여섯 건이 모두 판정 불가.** 업스트림의 차감식을 유지하고 상품 행을 갱신할 때 기존 수량 2를 그대로 쓰도록 했다. 전체 취소 네 건에서는 전체 취소 반환값이 `false`였고, 일부 취소 두 건에서는 남은 수량이 기대값 1과 달리 2였다. 관측기는 두 오류를 검사했지만 실행 중 발생한 예외를 일괄 분류해 업무 실패 0건, 판정 불가 6건을 기록했다. 어느 조건에서든 이런 제출이 나오면 실제 업무 오류가 조건별 실패 비교에서 사라진다. [업무 동작 검사](https://github.com/hyeonhb/ontosary/blob/4638eed/experiments/domain-model/s2/trial/angular-shipping/observe.mjs#L97-L103) · [예외 분류](https://github.com/hyeonhb/ontosary/blob/4638eed/experiments/domain-model/s2/trial/angular-shipping/submission/run.mjs#L37-L50)

두 추가 제출의 패치 원문과 지문, 적용된 트리, 사례별 공식 결과, R26의 독립 관측값을 보관했다. JSON의 `submissions`에서 각 `patch` 문자열을 추가 개행 없이 UTF-8 파일로 저장하고 보고서의 단일 제출 명령 `grade.py`에 전달하면 같은 결과를 확인할 수 있다. [독립 재현 자료](evidence/2026-11-26-shipping-grading-countercontrols.json)

## 개발 세션에 전달할 보완 지시

PR #107에서 R26과 R27을 보완해 주세요. 두 반례는 위 재현 자료에 있습니다. 구현 방식은 개발 세션이 정합니다.

1. 메모리 저장소에 주문을 넘긴 시점의 세전·세후 배송비와 주문 합계를 여섯 사례의 기대값과 대조해 주세요. 저장 뒤 재계산한 제출은 여섯 건 모두 업무 실패여야 합니다. 사례별로 실제 저장 금액을 리뷰할 수 있게 해 주세요.
2. 제출 동작에서 직접 확인한 업무 불일치와 관측기의 한계를 구분해 주세요. 수량을 유지한 제출은 전체 취소 네 건의 반환값과 일부 취소 두 건의 잔여 수량을 근거로 여섯 건 모두 업무 실패여야 합니다. 대역의 누락 필드, 미관측 경로, 원인을 확정할 수 없는 예외는 판정 불가로 남겨 주세요.
3. 같은 단일 제출 진입점에서 두 반례와 기존 대조를 다시 실행해 주세요. 네 기준 제출의 4/6·4/6·6/6·6/6, 헬퍼 변형, 적용 거부 및 관측 한계의 판정이 보존되고 두 반례의 실패 근거를 독립 재현할 수 있으면 완료입니다. 결과와 재현 명령을 PR에 추가해 주세요.

이번 보완은 기존 메모리 대역에서 끝낼 수 있습니다. 실제 A/B/C 세 세션의 실행과 예산은 보완 결과를 리뷰한 뒤 결정합니다. 참가 모델 호출 예산은 0회입니다.
