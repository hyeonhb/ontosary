# S2 개발 지시 · Vendure 환불 잔액 변경의 영향 범위 탐색 비교 준비

지난 실험에서는 관련 소스를 처음부터 제공했다. Sol의 적용 실패 3건도 별도 진단에서는 해당 업무 검사를 모두 통과했다. 이번 질문은 **에이전트가 업무 요청만 받고 시작할 때, 변경 전 도메인 모델이 일반 코드 검색보다 영향 범위와 보존할 동작을 더 정확하게, 또는 더 적은 비용으로 찾게 해 주는가**이다. 기존 환경에서 어디까지 측정할 수 있는지 참가 모델 호출 없이 확인하고, 실제 실행 여부를 결정할 결과 PR을 인계해 주세요. ## 참가자에게 공개할 업무 요청

> 관리자 주문 상세에서 고객에게 돌려줄 금액이 전혀 남지 않은 주문은 환불로 안내하지 말고 취소 절차로 연결해 주세요. 환불할 금액이 남은 주문에서는 기존 취소·환불 동작을 유지하고, 원래 취소할 수 없던 주문에 새로 취소를 허용하지 마세요.

대상은 Vendure `534e6003534f74761e82de1b8c6061cba89945d1`의 기존 Admin UI다. 이 요청은 실험용 제품 정책이다. 참가자에게는 위 요청, 공통 탐색 범위와 도구 사용법, 제출 방법만 제공한다. 아래 평가 단서, 정답 파일 목록, 과거 실험 응답과 채점 자료는 평가자 쪽에 둔다.

| C · 문서 조회 | A의 모든 기능에 B와 대응하는 기존 서술 문서·근거 부록 검색과 읽기를 더한다. |

세 조건 모두 검색에서 시작한다. 파일과 자료를 통째로 프롬프트에 넣거나 정답을 아는 사람이 관련 파일을 골라 주면 탐색 비용을 측정할 수 없다. 같은 소스 접근 범위, 실행·제출 기회, 예산을 적용한다. B/C에서 이번 과업과 관련된 사실·예외·근거·검토 상태가 대응하는지 실제 내용을 대조한다. 기존 모델이 잔액 계산까지 연결하지 못하면 그 공백을 기록한다. 과업에 맞춘 지식 보충은 이 비교의 결과를 바꾼다. ## 이번에 확인할 것

1. **영향 범위 발견을 먼저 측정한다.** 세 조건에서 검색·읽기가 동작하고 배정된 자료만 보이는지 모의 세션으로 확인한다. 참가자는 첫 수정 직전에 영향을 받는 곳, 보존할 동작, 판단을 뒷받침하는 코드 위치를 한 번 짧게 제출한다. 탐색만 가능한 환경이면 탐색 종료 때 같은 기록을 받는다. 평가 기준은 메뉴 노출과 문구, 클릭 시 실제 절차, 여러 결제의 잔액·환불 이력 사이의 관계다. 파일명을 나열한 답과 소스 근거로 정확한 관계를 설명한 답을 구분하고, 동등한 근거도 인정한다. 예시 답안으로 중요한 관계를 빠뜨렸을 때 판정이 갈리는지 확인한다.
2. **최종 수정은 기존 환경에서 공정하게 수집할 수 있을 때 평가한다.** 조건별 독립 작업 사본에서 실제 변경 소스를 같은 방식으로 회수할 수 있는지 확인한다. 가능하면 타입 검사와 함께 **사용자에게 보이는 메뉴 문구와 클릭 후 열리는 절차**를 모두 관측한다. 전액 환불, 한 결제에만 잔액이 남은 주문, 실패한 환불, 기존 직접 취소 경로와 숨겨진 메뉴를 포함한다. 고정 소스에서 성립하는 사례인지 확인하고, 원본·정상 수정·문구만 바꾼 부분 수정으로 판정 차이를 보여 준다. 정답 패치 모양에 의존하지 않는다. 탐색만 준비된 경우에는 그 근거와 최종 수정에서 남은 제약을 보고한다. 탐색 성적으로 변경 성공을 추정하지 않는다.
3. **결과를 보기 전에 비교 단위와 비용을 정한다.** 후속 실행 후보는 `gpt-6.2-sol`·`medium`, 조건별 독립 세션 3회, 최대 9세션이다. 각 조건에서 탐색 기준을 충족한 건수와, 관측 가능한 경우 최종 수정 성공 건수를 각각 예정된 3회 기준으로 보고하도록 설계한다. 같은 세션 안의 여러 호출과 실패 시도까지 합산해 입력·출력 토큰과 시간을 집계한다. 검색·읽기·조회 횟수와 반환량은 비용 차이를 설명하는 데 쓴다. 세션별 시간·토큰 상한, 집행 또는 사후 판정 방식, 순서·중단·결측 처리, 9세션의 총비용 추정 근거를 제안한다. 자료 작성·유지에 든 사람 비용은 실행 비용과 구분하고 미측정이면 그대로 표시한다.
