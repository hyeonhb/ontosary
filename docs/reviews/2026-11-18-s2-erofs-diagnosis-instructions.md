# S2 EROFS 쓰기 경로 진단 지시

2026-11-18. [R20 독립 리뷰](2026-11-18-s2-r20-cleanup-independent-review.md) 다음 작업이다. 목적과 필요한 결과를 정하고, 조사 방법과 순서는 개발 세션에 맡긴다.

## 목적과 현재 근거

S2의 목적은 변경 전 도메인 모델이 agent 수정 작업에 도움이 되는지 확인하는 것이다. 지금은 첫 실행을 막은 원인을 좁혀 환경 작업을 필요한 범위로 한정해야 한다.

고정 CLI `0.167.0-alpha.3.2`의 직접 VM smoke에서 `error building bubblewrap command: Read-only file system (os error 30)`가 발생했고 payload는 시작하지 않았다. R20의 정리 결함은 보완됐지만 EROFS의 정확한 경로와 실패 연산은 아직 모른다.

**당시 CLI가 어떤 준비 작업에서 어느 경로에 쓰려고 했는지 좁히고, 다음 조치 하나를 판단할 수 있는 근거를 제시해 주세요.** 이번 목표는 원인 진단이며, 오류를 없애기 위한 권한 변경이나 실행기 확장이 아니다.

## 조사 범위와 자율성

당시 저장 증거, 고정 바이너리의 출처·패키지 메타데이터, 대응 소스와 설정을 읽기 전용으로 조사한다. 필요한 공개 자료의 조회·분석용 보관과 작은 로컬 분석 스크립트는 사용할 수 있다. 자료 선택, 탐색 도구, 조사 순서와 후보를 좁히는 방법은 개발 세션이 결정한다. 필요 이상의 전체 소스 수집이나 범용 진단 도구 구현은 피한다.

시작할 근거는 [당시 보고서](2026-11-17-s2-vm-cli-smoke.md), [저장 증거](../../experiments/domain-model/s2/verification/2026-11-17-vm-cli-smoke), [smoke 코드](../../experiments/domain-model/s2/trial/vm-cli-smoke)다. 현재 코드와 당시 freeze의 차이를 구분한다. 버전 문자열만으로 소스 대응을 확정하지 말고 가능한 commit·패키지·바이너리 식별 근거를 확인한다. 정확한 소스를 확보하지 못하면 그 사실을 명시하고, 최신 소스는 후보를 찾는 참고로만 사용한다.

새 VM·실제 limactl 제어·CLI binary 실행·동적 trace·소스 빌드/패키지 설치·정책 변경·자격 증명 전달·모델 호출·본 비교는 이번에 수행하지 않는다. 과거 원문·freeze·증거를 보존하고 제품·평가·실행 경계는 변경하지 않는다.

## 필요한 결과와 완료 기준

- **실행 조건:** 실제 argv, CLI 프로세스의 환경과 작업 디렉터리, 관련 파일 접근 정책을 당시 근거로 연결한다. CLI 초기화 시점과 sandbox 안의 payload 실행 시점을 구분한다. 환경 변수 이름이 같다는 이유로 두 시점의 값과 적용 범위를 같다고 가정하지 않는다.
- **코드와 경로:** 오류가 만들어지거나 전달되는 코드 경로를 찾고, 도달 가능한 쓰기 연산과 경로 계산을 당시 입력에 대입한다. 후보마다 경로 또는 경로 패턴, 연산, 실행 단계, 지지 근거와 남은 불확실성을 설명한다. 소스 대응이 불명확한 후보는 확인된 사실과 분리한다.
- **인과 판단:** 읽기 전용 정책과 해당 연산의 충돌 가능성을 설명하되, 정책 설정만으로 실제 실패 지점을 확정하지 않는다. 원문 관측, 정적 추론, 추가 확인이 필요한 가설을 구분한다. 다른 경로를 배제할 수 없다면 정확한 단일 경로를 찾았다고 보고하지 않는다.
- **다음 결정:** 근거가 가장 강한 후보와 이를 확인하거나 기각할 최소 후속 조치를 제안한다. 동적 관측이 필요하다면 얻으려는 정보, 필요한 실행·권한·대략적 비용과 결과별 판단을 설명한다. 그 시험을 이번에 구현하거나 실행하지는 않는다.

정확한 경로가 정적으로 확정되지 않아도, 후보를 줄인 근거와 확정할 수 없는 이유 및 다음에 필요한 관측을 제시하면 이번 진단을 인계할 수 있다. 이 경우 상태는 미확정이며 EROFS 해결로 기록하지 않는다. 대응 자료가 없어 더 좁힐 수 없는 경우에도 확인한 출처와 부족한 근거를 남긴다.

## 시간과 이슈 공유

첫 진단 보고는 **30~60분 정도를 참고 예상**으로 잡되, 확정된 시간 상한으로 해석하지 않는다. 개발 세션은 착수 시 자료 접근성과 난이도를 보고 예상 시간을 조정해 알린다. 대응 소스 확보가 어렵거나 조사 범위가 예상보다 커지면 지금까지의 근거와 선택지를 먼저 공유하고, 핵심 질문에 기여하지 않는 탐색을 계속 늘리지 않는다. 별도의 단계별 완료 gate나 횟수 제한은 두지 않는다.

합의 범위 안의 조사 방법 변경과 국소 분석은 자율적으로 진행한다. 실제 재실행이나 권한·아키텍처·비용의 의미 있는 확대가 필요하면 이번 결과를 인계하고 논의한다.

## 결과 인계

보고서에 결론, 근거의 식별자·출처, 후보와 불확실성, 다음 권고, 소요 시간을 남긴다. 보고 형식은 자유이며 자료가 많아도 판단에 필요한 내용을 먼저 제시한다. 실행하지 않은 시험을 검증 결과로 포함하지 않는다.

저장소 지침에 따라 문서와 필요한 분석 자료를 반영하고 PROGRESS를 실제 결과로 갱신한다. 추가한 분석 코드가 있다면 그 코드의 핵심 가정과 오류 경로에 맞게 검증하고, 저장소 필수 검사인 `pnpm check`를 수행한다. 관련 없는 실험을 반복하거나 이전 PR #70을 다시 열 필요는 없다. 이번 진단 결과를 리뷰한 뒤 후속 실제 시험·설정 변경·C안 채택 여부를 결정한다.
