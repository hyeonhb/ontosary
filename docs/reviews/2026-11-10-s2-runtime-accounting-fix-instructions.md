# 개발 세션 지시 — S2 R11 종료·수집 경계와 R12 usage 보완

## 1. 목표와 이번 작업의 끝

**기존 Codex CLI·macOS 범위에서 R11의 종료/제출 수집 경계와 R12의 usage 완료 판정을 보완하고, 새 검증 근거를 독립 리뷰에 인계한다.** 사용자는 보완 결과를 리뷰한 뒤 본 비교를 진행하기로 했다. 이번에는 실제 모델 호출·연결 시험·비교 agent 생성·9회 중 일부 예비 실행을 하지 않는다. `s2:trial:run`의 실행 거부, `trialAuthorized:false`, `readyForTrial:false`, `results:null`을 유지한다.

ADR-028의 과업·A/B/C·평가 범위와 ADR-029의 비용 결정을 유지한다. 30분 외부 시간 제한을 준비하며, 100,000토큰은 관측 참고선이다. 토큰 hard cap을 복원하거나 초과를 실패/중단 조건으로 만들지 않는다. API 실행기·컨테이너/VM·클라우드·새 호스트 계정/관리자 권한을 자동 도입하지 않는다.

이번 보완은 H-O(변경 전 도메인 모델의 agent 수정 효용)를 측정하기 위한 준비다. H-F(FCA의 모델 구축 기여), S3(변경 후 지식 갱신), 제품 코어·분석 알고리즘·온톨로지 형식 확장은 포함하지 않는다. R11/R12 해결과 실제 비교 준비 전체 승인을 구분한다.

## 4. R11 — 종료 확인 후에만 제출을 수집한다

### 4.1 원래 반례와 먼저 할 조사

현재 `runTool`은 새 process group을 만들고 `process.kill(-pid, SIGKILL)`로 종료한다. 실제 probe에서 별도 세션/그룹을 만든 자손이 350ms timeout 뒤에도 파일을 썼다. 부모의 `close`나 그룹 kill 성공은 모든 writer의 종료 증거가 아니다. 복사 전후 hash 일치는 관찰된 변경 검사이며 살아 있는 writer가 없다는 증명이 아니다.

현재 설치된 CLI의 버전/바이너리 hash·help·권한 설정과 macOS에서 실제 사용할 수 있는 수명주기 기능을 확인한다. **구현 전에 짧은 선택 기록**에 다음을 적는다: 선택한 종료 경계, 그 경계에 자손이 포함되는 원리, 탈출 경로, 필요한 권한, 종료 지연과 수집 순서, 유지 비용. 공개 OS/CLI 기능에 의존하면 그 기능의 근거와 현 환경에서의 최소 재현을 연결한다. 특정 native 기능이 가능하다고 추측해 구현을 시작하지 않는다.

기존 CLI/macOS에서 경계를 제공하는 방법을 우선 검증한다. 프로세스 트리 감시를 쓰면 재부모화·새 그룹·감시 사이 생성/종료·PID 재사용을 어떻게 다루는지 설명한다. 단발성 `ps`, 주기적인 후손 kill, 이름/명령행 검색만으로 탈출 방지를 보장했다고 판정하지 않는다. `chmod`, 경로 이동/삭제, 복사본 hash만으로 이미 열린 파일 핸들이나 잔존 프로세스 문제가 해결됐다고 주장하지 않는다.

최소 재현에서 경계가 성립하지 않으면 같은 약한 방법을 계속 덧붙이지 않는다. 실패 증거와 최소 대안별 구현/운영 비용·남는 위험을 인계한다. 새 플랫폼/권한이나 허용 도구·실행 정책의 큰 변경이 필요하면 사용자와 먼저 결정한다. 이 경우 R12와 독립적인 회귀/문서 작업은 끝내되 R11은 unresolved로 유지한다. 이는 정상적인 부분 인계이며 R11 해결 또는 전체 준비 완료는 아니다.

### 4.2 실행 수명주기 계약

권장 흐름은 `running → stopping → 종료 경계 확인 → collecting → sealed`이며 어느 단계든 실패하면 `blocked/collection-failed`로 남긴다. 실제 이름은 코드에 맞춰 정하되 다음 의미를 보존한다.

1. 정상 부모 종료, 비정상 종료, timeout, spawn 실패, supervisor의 처리 가능한 중단에 대해 종료 경로를 정의한다. 정상 종료 때에도 백그라운드 자손이 남을 수 있으므로 같은 확인을 수행한다. supervisor 자체 비정상 소실 시 OS 경계가 무엇을 보장하는지도 명시한다. 보장하지 못하면 다음 실행 전 잔존 검사 실패를 차단한다.
2. 종료 요청 이후 새 작업을 받지 않고 해당 실행의 자손/쓰기 능력을 정리한다. unrelated 호스트 프로세스를 이름이나 넓은 PID 범위로 종료하지 않는다. 확인과 정리 자체에도 짧고 명시적인 제한을 둔다. pipe가 열려 있거나 kill/권한/확인이 실패해도 무한 대기하지 않는다.
3. task 종료 사유, 실제 exit/signal, 제한 시각, 종료 요청/확인 시각, 정리 소요 시간, 수집 허용 여부를 구분해 기록한다. 30분은 과업 수행 예산이며 정리 시간을 추가 작업 시간으로 허용하지 않는다. 실제 종료 지연을 0으로 꾸미거나 수집 결과를 정확한 deadline 순간의 상태라고 소급 표현하지 않는다. deadline 뒤 쓰기가 가능한 상태는 해결로 보지 않는다. 보장 가능한 시간 경계가 원래 계약과 다르면 차이를 보고하고 재판단 전 차단한다.
4. 자손 종료/쓰기 차단을 확인할 수 없으면 유효 제출을 만들지 않고 후속 실행도 시작하지 않는다. 진단용 파일을 보존할 수는 있지만 정상 snapshot/평가 입력과 상태·경로를 구분한다. timeout 자체와 종료 경계 실패도 다른 상태다.
5. 실행 ID·전용 경로·종료 증거를 수집 입력과 연결한다. 서로 다른 실행의 종료 성공 플래그를 넘기거나 호출자가 `true` 하나를 주는 것만으로 검사를 우회할 수 없게 한다. 실제 보장은 supervisor/권한 경계에서 제공하며 TypeScript 타입만으로 OS 보장을 주장하지 않는다.

### 4.3 수집·평가 경계

종료가 확인된 실행에서 전체 production source와 auxiliary를 수집한다. 추가/수정/삭제, 전체 tree와 baseline delta를 보존한다. baseline으로 복원하거나 읽기 어려운 파일·범위 밖 변경을 조용히 제외하지 않는다. symlink/특수 파일·동시 변경·manifest 불일치는 명시적 실패다. 실패 중간 산출물은 sealed 제출로 노출하지 않는다.

수집 후 평가자는 source뿐 아니라 auxiliary·manifest도 변경할 수 없는 권한으로 읽는다. 기존 평가 전후 hash·complete-root 대조를 유지한다. 권한 검증은 실제 같은 UID·permission profile에서 수행한다. 읽기 전용 파일 mode만 검증하지 않는다. 다음 실행 경로는 새로 만들고 이전 실행의 잔존 프로세스가 접근/변경할 수 없음을 확인한다.

### 4.4 모델 없는 실제 macOS 검증

원래 detached 쓰기 반례를 수정 전/후 같은 조건으로 실행한다. 새 probe는 독립 원본을 보존하고 별도로 추가한다. 임시 전용 경로, 짧은 제한, 자체 종료하는 fixture와 바깥 정리 절차로 검증한다. 테스트 실패가 실제 잔존 프로세스를 남기지 않게 한다.

| 사례 | 관찰/판정 |
| --- | --- |
| 정상 종료·일반 timeout | 정상 파일은 수집 가능, 종료 사유/시간/수집 상태 정확, 자손 잔존 없음 |
| 부모 정상 종료 후 계속 쓰는 자식 | 부모 exit만으로 sealed 처리하지 않으며 후속 쓰기 차단 |
| detached/새 세션·그룹, 재분리하는 손자 | 원래 반례와 한 단계 재부모화/분리에도 같은 경계 적용 |
| 종료와 겹친 자손 생성·지연 쓰기·기존 열린 핸들 쓰기 | 종료/복사 사이 경쟁을 성공으로 숨기지 않음 |
| 자손의 열린 stdout/stderr·종료/확인 오류 | 제한 안에 종료 또는 blocked 반환, 로그 절단 상태 보존 |
| 수집 변경/실패·source/auxiliary/manifest 조작 | 정상 제출로 평가 불가, 진단 근거 보존 |
| 새 실행 workspace와 외부 canary | 이전 실행의 접근/쓰기 거부, 기존 자료·control·cache·홈·네트워크 거부 유지 |

핵심 종료 사례는 새 임시 경로에서 최소 두 번 실행해 한 번의 타이밍 우연과 구분한다. 준비 완료 판정은 probe 통과만이 아니라 선택한 경계의 원리/한계 설명도 필요하다. 일반 커널 보안을 증명하는 연구나 대규모 침투 시험으로 확대하지 않는다.

## 5. R12 — 이벤트 수가 아닌 turn 상태로 usage를 집계한다

### 5.1 입력·상태·집계

실제 CLI에서 확인 가능한 JSONL 계약을 근거로 지원 이벤트/usage 필드를 명시한다. 이번에는 라이브 모델을 호출해 로그를 만들지 않고 로컬 스키마/기존 검증 자료와 합성 fixture를 사용한다. 합성 fixture를 실제 공급자 관측이라고 표현하지 않는다.

JSON 파싱 뒤 object/null/array/type과 사용 필드를 검사한다. 알려지지 않은 정상 object 이벤트는 원문/행 번호를 보존하면서 비계측 이벤트로 다룰 수 있지만, 깨진 구조와 알려진 turn/usage 이벤트의 필수 필드 오류는 issue로 남긴다. 복구 가능한 줄 오류 때문에 전체 집계가 예외로 사라지지 않게 한다.

turn별 시작/활성/완료/실패를 추적한다. 실제 계약에 turn ID가 있으면 이를 사용하고, 없으면 순차 활성 turn을 관리한다. 임의 event ID를 turn ID로 해석하지 않는다. 시작 없는 완료, 중첩 시작, 이미 끝난 turn의 추가 완료, 끝나지 않은 turn, 실패/error, usage 누락을 구분한다. 지원하지 않는 순서/동시성은 추측해 정상화하지 않는다.

동일 identity와 동일 내용의 이벤트 재전달은 한 번만 집계하고, 같은 identity의 다른 내용은 충돌로 표시한다. 서로 다른 ID의 완료가 같은 활성 turn을 두 번 완료시키면 중복/모순이다. ID 없는 경우 같은 숫자라는 이유만으로 서로 다른 정상 turn을 합치지 않으며, 재전달인지 확인할 수 없는 완료를 새 소비량으로 더하지 않는다. ID의 존재·유일성 범위와 dedup 규칙을 문서화한다.

수치 필드는 유한한 비음수 safe integer인지 확인하며 누적 합계의 overflow도 검사한다. 입력에는 cached input, 출력에는 reasoning output이 이미 포함된다는 현 계약을 유지한다. 세부 필드는 다시 더하지 않고, 미관측 세부값은 null이다. 계약 위반인 cache>input/reasoning>output도 정상으로 합산하지 않는다.

### 5.2 결과의 의미

- 검증된 정상 turn 합계와 전체 기록의 완료 여부를 분리한다. 모든 관찰된 turn이 올바르게 끝나고 로그/실행 종료 상태에도 결손이 없을 때만 이 계약의 `complete=true` 및 확정 total을 낸다. 이는 completed-turn 기록의 완전성이지 공급자 청구 전체나 내부 요청 관측의 보장이 아니다.
- timeout·출력 절단·읽기/파싱 오류·끝나지 않은 turn·모순이 있으면 전체 total은 null이다. runtime의 종료/절단 정보를 집계와 연결하고, 앞선 정상 완료 이벤트가 있다는 이유로 종료 중 계측을 complete로 표시하지 않는다. 정상 EOF와 단순 수집 중단을 구분한다.
- 검증된 관찰 subtotal과 제외/모호한 이벤트를 원시 행까지 추적한다. 모순된 turn의 값은 격리하거나 집계에서 철회한다. 중복 의심 수치를 모두 더한 값을 ‘관찰 하한’이라고 부르지 않는다. 하한이 성립하는 범위를 설명할 수 없으면 subtotal로만 표시하고 하한은 unknown으로 둔다.
- usage가 없으면 소비량 unknown이며 0이 아니다. 참고선 초과도 확정 총량의 초과인지, 검증된 관찰분에서 이미 확인된 초과인지를 구분한다. 불완전한 subtotal이 참고선 아래라고 전체 미초과로 단정하지 않는다. 초과해도 hard cap/중단 규칙을 도입하지 않는다.
- raw JSONL·행 번호·진단·실행 종료 근거를 보존하고 계측 스키마/의미 변경을 명시한다. 비밀이나 호스트 개인정보가 섞인 로컬 자료를 그대로 커밋하지 않는다.

### 5.3 필수 회귀

독립 리뷰의 다섯 입력을 그대로 의미상 재현한다. `started→completed(10+2)`는12, `started→completed→started`는 incomplete, 시작 없는 completed는 incomplete, 서로 다른 완료 ID 두 개 뒤 미완료 turn은 total=null이며24로 확정하지 않음, JSON null은 구조 오류 기록 후 집계 결과 반환이다.

추가로 정상 다중 turn/ID 없는 정상 순서·숫자가 같은 두 정상 turn, 동일 이벤트 재전달·상충 재전달, 중첩 시작·실패·usage 누락, 잘린 JSON·non-object·잘못된 수치·누적 overflow, 정상 turn 뒤 timeout/로그 절단을 검사한다. 기존 input99,999+output5=100,004/cache90,000/reasoning2 사례는 중복 합산 없이 관찰 초과4를 유지한다. 별도 provider/API 호출 없이 순수 fixture로 검증한다.

## 6. 구현 순서와 검증 범위

1. 기준 버전·환경/CLI 지문·git 상태를 기록하고 원래 R11/R12 반례를 재현한다. 실패 결과도 보존한다.
2. R11의 최소 native 경계를 검증해 선택/한계를 기록한다. R12는 그 조사와 독립적인 작은 수정으로 진행할 수 있다. 외부 인프라 투자가 필요한 지점에서는 자동 확대하지 않는다.
3. R12의 입력 검사·상태 전이·집계 계약과 회귀를 구현한다. R11은 실행/종료/수집 상태를 분리하고 선택한 경계에 맞춰 연결한다. 테스트를 만족시키기 위해 실제 probe의 탈출 동작을 제거하지 않는다.
4. 모델 없는 macOS probe를 실행하고 종료·제출 수집·계측의 연결을 검증한다. 제한된 참조 snapshot을 수집/평가해 delta/complete-root와 sourceId/submissionId·52사례/요청/trace의 일치를 확인한다. 종료 증거가 없거나 실패한 수집은 이 경로에 들어갈 수 없어야 한다.
5. `pnpm check`와 `pnpm experiment`를 실행한다. 변경한 runtime을 쓰는 v4의29제출 교정을 새 경로에서 한 번 실행해 기존 판정/60파일과 비교한다. 의도적인 메타데이터 변경과 기존 의미를 분리해 설명한다. 같은 검사 반복은 새 실패/변경이 있을 때만 넓힌다.
6. 공통 configuration/권한·workspace 공급을 바꿨으면 실제 A/B/C 접근·공개/private 타입7제출 대조를 다시 실행한다. 변경하지 않은 무거운 환경 검증은 기존 근거의 입력/구현 hash 동일성을 확인해 재사용할 수 있다. stale runtime 증거를 새 구현의 검증으로 재사용하지 않는다.
7. 새 실행 manifest·계측 계약·종료 증거를 hash로 결합하고 상태/미해결 목록을 갱신한다. `s2:trial:run`은 여전히 실제 dispatch 없이 거부하는지 확인한다. 보고서와 PR을 인계한 뒤 독립 리뷰를 기다린다.

CLI 명령·입력·출력 경로와 exit code를 재현 README에 남긴다. 전체 로그를 사람 보고서에 복사하기보다 원시 증거와 짧은 판정 표를 연결한다. 시간/PID/임시 경로처럼 변동하는 필드를 명시적으로 분리하되, 종료 성공·늦은 쓰기·usage issue·내용 hash는 비교에서 제외하지 않는다. macOS 필수 검증을 skip하고 전체 완료로 처리하지 않는다.

## 7. 동결 자료와 남아 있는 승인

새 결과는 `experiments/domain-model/s2/verification/<실제 날짜>-runtime-accounting-fix/`에 추가한다. 새 execution artifact도 별도 경로로 만들고 당시 구현/환경/계측 스키마·증거를 연결한다. 기존 구현 hash만 바꾸고 이전 차단 증거를 통과 근거로 연결해서는 안 된다.

모델·TASK·B/C가 그대로면 baselineId/modelId/bundleId 및 agent84파일 bytes를 유지한다. 실행 명세의 구현/환경 hash와 executionId는 새로 산출한다. 공개 RUN 안내 등 agent 입력 변경이 꼭 필요하면 A/B/C에 같은 계약을 반영하고 새 bundleId·전체 배포/대응 검사를 수행한다. 과거 bundle을 덮어쓰거나 기존 ID를 새 bytes에 재사용하지 않는다. evaluatorId는 실제 평가 의미/구현 변경에 맞춰 계산하며 기존 값 보존을 위해 계산을 우회하지 않는다.

R11/R12의 기술 상태, C 사람 의미 동등성 검토, 도메인 의미 승인, 실제 CLI 도구 inventory/인증·전역 지시·플러그인 유입 배제, 모델 버전 관측 한계/자원 정책, 실제 실행 권한을 별개 항목으로 관리한다. shell 대역 통과를 실제 모델 세션 전체 검증으로 표현하지 않는다. 이번 수정에서 다루지 않은 항목을 자동 완료로 바꾸지 않는다. C 사람 검토와 모델 의미 승인은 서로 대체하지 않는다.

## 8. 완료 조건과 부분 인계 조건

보완 구현 완료로 인계하려면 다음을 모두 충족한다. 독립 해결 판정은 후속 reviewer가 한다.

- R11: 선택한 경계의 근거·한계와 실제 normal/timeout/분리 자손 probe가 일치하고, 잔존 writer·수집 경쟁·다음 실행 영향이 차단된다. 실패/확인 불가 상태는 정상 제출/평가로 진입하지 않는다.
- R12: 원래 다섯 반례와 인접 부정 사례가 계약대로 처리되고, lifecycle·중복·종료/절단 상태를 합친 결과에 false complete/이중 합산/unknown→0 변환이 없다.
- 기존 과업·모델·자료 의미와 R8/R9/R10·v4 종료 정책을 유지한다. 새 검증, 재사용 근거, 미검증 범위를 분리하며 pnpm check·필요한 교정/실제 macOS 검증이 통과한다.
- 새 동결/인계 자료가 정확한 구현/환경/증거를 가리키며 실제 모델/본 비교0회, `trialAuthorized/readyForTrial=false`, `results:null`, 사람 검토 pending을 유지한다.

R11이 현재 범위에서 해결되지 않으면 **R12 완료 + R11 차단 인계**가 가능하다. 다만 제목/상태를 전체 완료로 쓰지 않는다. 재현된 한계, 시도한 최소 방법, 다음 선택지별 변경 범위·비용·계약 손실을 보고하고 새 구조/정책은 사용자와 결정한다. 비용 절감을 이유로 종료 보장을 조용히 낮추거나 본 비교를 먼저 실행하지 않는다.
