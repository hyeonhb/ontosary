# 개발 세션 지시 — 공개 업무 앱 적합성과 한 탐색 과업 고정

## 작업 목표

사용자가 선택한 “업무 개념·관련 코드 탐색 우선”과 “공개 TypeScript 업무 앱 후보부터 조사”에 따라, 실제 앱 한 개념의 소스 근거와 재현 가능한 분석 범위를 준비한다. 이번 완료물은 **대상/과업 준비 또는 근거 있는 표본 부적합 판정**이다. 제품 기능이나 사람 효용 결과를 한꺼번에 만들지 않는다.

## 현재 상태와 근거

AGENTS/CONTRIBUTING/PROGRESS, [V3 독립 리뷰](2026-11-08-type-context-independent-review.md), [후보 조사](2026-11-08-public-app-candidates.md), [실험 절차 초안](../experiments/concept-exploration-protocol.md)을 읽는다. 기준 구현은 PR #9/main `2dba3e2e52a3e085fcfe35fdee87a1fd16aa1365`다. 이후 리뷰 문서가 추가될 수 있다. R4/R5는 보고된 범위에서 해결됐고 136개 테스트·기존 비교 4/4·V1/V2/V3 재현을 확인했다. 제품 효용 Gate는 여전히 미검증이다.

Saleor Dashboard `2e1776949e8cae747da480ec3712692554f3284c`는 주문 취소의 UI/조건/API 요청 근거가 있어 첫 적합성 점검 후보지만 strict=false와 codegen·의존성 경계 때문에 현 분석 성공은 미검증이다. Medusa의 조사 revision은 별도 라이선스 대상 hook이 주문 화면 의존에 있어 우선 보류한다. 어느 앱도 분석 표본으로 확정된 것은 아니다.

## 구현·조사 범위

1. 원격/브랜치/사용자 변경을 확인한다. 공개 원본을 고정 revision으로 확보하고 라이선스·필요 파일·hash·실행 도구 버전과 준비 비용을 기록한다. 원본 앱을 서비스로 배포할 필요는 없다.
2. 도구 후보 출력보다 먼저 원문과 공식 자료에서 과업 질문·예비 근거 목록을 작성한다. Saleor 후보는 “일반 주문 취소 메뉴 → fulfillment 조건 → 확인/차단 UI → API 요청”이다. draft 삭제·fulfillment 취소·서버의 최종 취소 정책은 구분한다. 필수/허용/비관련/불확실 근거와 선정 이유를 남기고 agent 작성임을 표시한다.
3. 원래 설정을 먼저 점검하고 거부/오류를 보존한다. 별도 분석 설정이 필요하면 변경 이유와 영향을 명시한다. strictNullChecks 전제나 core 오류 처리를 완화하지 않고, 원문 로직을 변형하거나 임의 any/stub으로 진단을 없애지 않는다. 실제 import closure, generated 파일 출처와 라이선스, 외부 project 범위를 기록한다.
4. 가능하면 한 개념의 범위를 사전에 고정한 뒤 scan·단순 type/property 그룹·FCA를 실행하고 진단/omissions/상한/잘림을 그대로 보고한다. scope를 바꾸면 변경 전후 결과를 보존한다. 모든 TS 소스를 성공적으로 분석한 것처럼 files 수를 coverage 비율로 쓰지 않는다. 전체 분석이 불가능해도 표본 실패는 정당한 결과다.
5. Saleor가 현 전제/비용에 맞지 않으면 공개 TS 업무 앱 한 후보를 추가 조사한다. 무제한 후보 탐색이나 설정 패치를 하지 않고 비교표와 진행/보류 권고를 남긴다. 사용자 문제 변경·core 전제 완화·주요 기술 투자가 필요해지는 경우 구체적인 근거/선택지/권고로 사용자 판단을 요청한다.
6. 선택 가능한 표본을 확보하면 검색/LSP / 같은 facts의 단순 그룹 / FCA에 동일하게 제공할 범위·질문·표시 자료·시간 기록 양식을 준비한다. 참가자/첫 노출/학습 효과/정답 검토는 미확정 항목으로 명시하고 모집 가능성을 확인하기 전 수치를 결과로 채우지 않는다.

## 제외 범위

코어 문법·논리/FCA 알고리즘·상한 변경, 평가기 리팩터링, 새 UI/LLM/SMT/플러그인, 실제 업무 의미 승인, 사람 실험 결과 생성, 참가자 연락/모집, 서비스/npm 배포는 제외한다. 같은 이름의 symbol이나 구조적 타입 공유를 업무 의미 동일성으로 확정하지 않는다.

## 완료 조건

- 선정/보류 후보별 revision·라이선스·설정/의존 경계·비용과 원래 실패 근거가 있다.
- 한 과업의 질문과 소스 기반 예비 정답/불확실 항목이 있다. UI 조건과 서버 정책을 구분한다. scan/FCA 결과를 보고 정답을 역으로 채우지 않는다.
- 성공 시 동일 입력 새 경로 두 실행의 비시간 산출물을 대조한다. 실패 시 재현 명령/환경/원시 실패를 남긴다. 후보를 선정하지 못해도 그 이유가 재검토 가능하다.
- 사람 참여 없이 탐색 시간 개선·의미 승인·Gate 2~4 통과를 주장하지 않는다. 분석 준비 시간과 사람 과업 시간도 분리한다.
- core/기존 corpus·과거 리뷰 증거를 보존하고 `pnpm check`, `pnpm experiment`로 기존 검증을 유지한다. 결과와 불확실성에 근거한 다음 판단 한 가지를 인계한다.

## 검증 방법

독립 원문 근거 작성 → 범위/질문 고정 → 원래 설정 점검 → 명시적 준비 → scan/그룹 결과 및 실패 보존 → 재현 대조 순서다. 이름 검색만으로 정답을 모두 찾을 수 있다면 그 사실도 기준선 관찰로 남긴다. 후보가 추가 근거 도달을 돕는지와 불필요한 검토량을 분리할 수 있게 자료를 구성한다.

## 문서화 및 인계

날짜별 보고에 실제 수행/미수행·원시 결과·설정 비용·사람 판단 필요 항목을 남긴다. PROGRESS와 실험 README를 실제 결과로 갱신하고 가설은 RESEARCH, 중요한 결정은 DECISIONS에 기록한다. 기존 절차 초안은 새 준비 자료와 연결하되 과거 미실행 기록을 덮어쓰지 않는다. 검증·staged diff 검토 후 지속 승인된 PR/merge/main 동기화를 완료한다.
