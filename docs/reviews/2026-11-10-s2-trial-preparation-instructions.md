## 1. 승인된 목표와 이번 완료 지점

사용자는 다음 조합을 승인했다. 취소 사유 변경의 무요청 종료 정책, 같은 지식을 설명하는 일반 문서 C, 기존의 제한된 메서드 실행 평가, 동일 설정의 새 세션으로 A/B/C 각3회다. **이번 작업은 과업·실행 계약, C 자료·의미 대응 검토 자료, 격리·계측 환경, 새 배포의 동결까지다. 본 비교는 준비 결과의 독립 리뷰 후 별도로 진행한다.**

실제 Vendure 과업을 agent에게 풀게 하거나 9회 중 일부를 예비 실행하지 않는다. 새 비교 chat/agent를 생성하거나 외부 모델에 과업·소스·B/C 자료를 보내지 않는다. 준비 검증에는 자체 fixture·스크립트 대역·이미 공개된 참조/결함 제출 교정만 사용한다. 운영 절차를 구현해 두는 것과 이를 실행할 권한을 구분한다.

H-O는 변경 전 도메인 지식이 agent 수정에 주는 효과다. B–A는 추가 지식 제공 효과, B–C는 동등 지식의 표현 차이, C–A는 일반 문서 제공 효과를 관찰한다. 한 과업의 소규모 비교로 일반적 우월성을 주장하지 않는다. FCA의 모델 구축 기여 H-F, 지식 갱신 S3, 승인된 업무 모델 구축은 이번 범위 밖이다.

## 3. 공통 과업과 공개 실행 계약

`lib/bundle.ts`의 초안 한 문장을 교체할 단일 과업 원본을 두고 A/B/C에 동일 bytes로 배포한다. 사용자에게 승인된 **실험용 클라이언트 로컬 요구**임을 명시한다. 실제 Vendure 제품 정책이나 서버 전체의 강제를 주장하지 않는다.

| 상황 | 공통 과업에 공개할 요구 |
|---|---|
| 정상 취소 사유 | 문자열의 앞뒤 공백을 제거해 취소 payload에 사용 |
| 빈 문자열·공백만·null·undefined | 취소 요청 없음 |
| 환불과 일부 취소가 함께 발생 | 취소 입력이 invalid면 그 흐름의 취소와 후속 환불 모두 중단 |
| 취소 없는 환불 | 기존 동작·사유를 그대로 보존 |
| 혼합 경로의 환불 사유 | 취소 payload만 정규화하고 환불 사유는 원래 값 유지 |
| invalid 입력의 dialog 종료 | 결과 `undefined`로 한 번 resolve하고 요청 없이 종료 |
| invalid 입력의 service 직접 호출 | 값 방출 없이 완료. 동기 예외/stream error 없음 |
| 사용자의 닫기 | 기존 무요청 동작 보존 |
| 취소 실패 응답 | 기존 후속 환불 중단 유지 |
| 그 밖의 요청 값 | 대상 주문/line/결제·수량·금액·배송·순서·횟수 보존 |

어떤 함수에 guard를 넣거나 EMPTY를 import하라는 해법은 공개하지 않는다. 업무 요구와 서비스 직접 호출에도 적용되는 계약은 공개하되 파일명/수정 경로 목록·참조 diff·결함 변형·숨긴 입력값은 제공하지 않는다. 새 평가 정책만 과업에 추가하며 B/C의 변경 전 모델에 새 요구의 정답을 주입하지 않는다.

공통 실행 안내에 허용 범위를 공개한다. admin-ui의 지원되는 TypeScript 메서드와 실제 Program에 포함되는 상대 helper 변경, 기존 타입/호출자 보존을 허용한다. generated/server schema·설정/lock·HTML·constructor/field 초기화·상속/데코레이터 변경, 삭제·미포함 파일, Promise/async·미검토 연산자 등 기존 미지원 경계를 설명한다. 이 문법/환경 안내는 A/B/C 공통이며 비공개 채점 조건으로 숨기지 않는다.

공개 검증은 고정 scope 타입 검사와 사전 정상 동작이 확인된 공통 명령이다. 기존 upstream 전체 테스트가 통과한다고 가정하지 않는다. 공개 타입 검사는 제출의 실제 파일·추가 helper를 검사하고 원래 설정/의존성을 유지해야 한다. 평가기 원문·기대값·참조 수정·정답 경로를 mount하지 않고 실행할 수 있게 한다. 원래 inventory에 없는 준비용 config/build 산출물은 공통 읽기 전용 환경 영역에서 공급하며 production 제출에 섞지 않는다. baseline·helper·helper 오류/누락/삭제에서 공개 검사와 비공개 타입 gate의 관련 판정을 대조한다.

agent 자체 테스트·메모는 별도 scratch/auxiliary 영역에 허용한다. 최종 제출은 완전한 production source snapshot과 별도 보조 산출물이다. 임의로 생산 소스 변경/추가/삭제를 제거하거나 baseline으로 복구하지 않는다. 기존 evaluator가 임의 테스트/문서 파일을 범위 밖으로 판정하므로, 수집 경계를 사전에 공개하고 소스 밖 보조 파일만 분리한다. 숨긴52사례의 결과·피드백은 최종 제출 전에 제공하지 않는다.

## 4. C 문서와 의미 동등성 검토

현재 C는 B의 값 트리를 필드 목록으로 옮긴 표현이다. 이를 같은 지식을 전달하는 설명 문서로 바꾼다. B는 기존 구조화 view를 유지한다. C는 개념/흐름별 문장, 필요한 표·목록, 코드 근거 부록과 찾아가기 색인을 사용한다. 예를 들어 dialog 닫기와 주문 취소의 차이를 문장으로 설명하되 동일한 근거·미확인 사항·검토 상태를 함께 제공한다.

기존 B 전체 JSON/필드 덤프를 C에 그대로 붙여 일반 문서를 명목상으로 만들지 않는다. 근거 원문과 hash·ID·좌표 등 재현 메타데이터는 부록에 보존할 수 있다. 관계의 from/to·방향·종류를 문장으로 명시하며 삭제하지 않는다. 가독성을 이유로 조건·예외·불확실성·사람 승인 상태를 생략하지 않는다. B에 없는 인과 설명·수정 위치·새 정책 해석을 C에 추가하지 않는다. 양쪽의 원문 근거와 부분 coverage/변경 전 snapshot 한계를 동일하게 보존한다.

다음 검토 자료를 평가자 전용으로 만든다.

1. 기존68 view의 단위 목록에서 출발한 명제/관계/근거/상태/메타데이터 inventory. 필요한 단위 분할은 안정적인 ID로 기록한다.
2. 각 단위의 B 경로/필드·C 문서/절/위치·source 근거·변환 종류·자동 검사 결과·개발자 검토 결과. C에서 B로도 대응시켜 C 전용의 추가 주장과 누락을 찾는다.
3. 핵심 정책 관련 단위의 대조표: 직접 취소/환불중취소/환불만/닫기/service 경계/UI 한계. 파일 수가 적다는 이유로 근거를 합쳐 추적성을 잃지 않는다.
4. 사람이 읽고 승인/수정/보류할 수 있는 간결한 검토 묶음과 미해결 항목. 개발자 검토와 사람 검토의 주체·대상 hash를 별도 기록한다.

단위의 존재/참조/근거 hash 일치와 누락·추가·중복을 자동 검사한다. 조건 부정, 관계 방향 뒤집기, 승인 상태 변경, 근거 누락, C에만 해법 추가를 부정 fixture로 넣는다. 자동 검사가 자연어 의미를 증명한다고 표현하지 않는다. 실제로 자동 탐지할 수 없는 사례는 사람이 검토할 항목으로 표시한다. 단순히 같은 원본에서 생성됐다는 `semanticHash`로 새 문서 의미 동등성을 통과시키지 않는다.

**사용자는 C 재구성과 검토 절차를 승인했으며 아직 생성되지 않은 문서의 의미 동등성을 승인한 것이 아니다.** 이번 개발 세션은 전체 대응의 자체 검토와 사람 검토용 인계를 완료한다. 실제 사람이 확인한 기록이 없으면 `humanParityReview: pending`이다. 독립 agent 리뷰도 사람 승인으로 표시하지 않는다. 자료 동등성 승인은 모델의 업무 의미 승인이 아니므로 `semanticReview: pending`·승인 지식0을 유지한다.

같은 파일 도구·명시적인 시작 색인·동일 수준의 자료 발견 안내를 제공한다. 모델이 정답이거나 B가 우월하다는 문구는 넣지 않는다. 파일 수/길이/탐색 구조의 차이는 기록하며 억지 token padding이나 정보 삭제로 크기를 맞추지 않는다. 전체 bytes, 사용 가능한 tokenizer 기준의 전체 tokens, 실행 시 실제 읽힌 자료/전송 tokens의 측정 방법을 구분한다. 미지원 tokenizer 수치는 추정 또는 미측정으로 남긴다.

## 5. 실행 조건과 계측 명세

평가자용 run-plan과 모든 agent에게 동일한 공개 실행 안내를 분리한다. 다음 조건을 명세에 기록하고 준비 검증으로 뒷받침한다.

| 항목 | 동결할 조건 |
|---|---|
| 모델/추론 | 현재 개발 세션에 실제 사용된 한 종류와 같은 설정. 실행 메타데이터에서 정확한 ID/버전·추론 설정을 확인하고 실행기/도구 버전과 함께 고정 |
| 반복 | A/B/C 각3회,9회. 이번에는 실행하지 않음 |
| 순서 | 3개 블록마다 A/B/C 각1회, 세 순서 위치에 고르게 배치. 기록한 배정 seed로 생성하고 평가자만 조건 매핑 보유 |
| 세션 | 실행마다 새 대화·소스·scratch·홈. 이전 대화/답변/메모리·사용자 전역 지시·플러그인 등의 조건 외 유입을 차단하거나 공통 통제 |
| 시간 | 과업/자료가 사용 가능해지고 첫 모델 요청을 시작하는 시점부터1,800초. agent 도구 실행 포함, 사전 환경 준비와 제출 후 평가 시간은 별도 |
| 토큰 | 누적 입력+출력100,000. cache 입력 포함; 출력에 포함된 reasoning tokens를 이중 합산하지 않음. 실제 공급자의 계측 정의를 기록 |
| 도구 | 같은 읽기·검색·편집·셸·공개 검증. 병렬 agent/서브에이전트·외부 검색·추가 모델 호출 금지 |
| 실행 배치 | 자원 경합을 줄이기 위해 한 번에 한 실행. 시스템 자원 한도·warm-up·cache 초기 상태를 공통화하고 기록 |
| 사람 개입 | 과업 도중 힌트·답변 보정 없음. 질문은 기록하되 새로운 해법 안내를 주지 않는 공통 정책 |
| 제출 | 종료 또는 한도 도달 시 단일 최종 source snapshot과 설명/검증 기록 수집. 재시도 해법 선택 없음 |

모델명은 자기소개·추정·UI 별칭만으로 채우지 않는다. 정확한 설정을 찾지 못하거나 실행기에서 해당 설정을 사용할 수 없으면 unresolved로 기록하고 필요한 선택만 사용자에게 요청한다. 임의의 최신 모델·다른 추론 강도로 대체하지 않는다. 모델 seed가 지원되지 않으면 `not-supported`로 쓰며 배정 seed와 구분한다. 사용 가능한 API/CLI의 옵션은 실제 설치 버전/공식 자료로 확인한다.

토큰 hard cap은 실제 강제 가능할 때만 주장한다. 요청 전 잔여 입력+최대 출력 예산 확인, 누적 usage 중복 이벤트 제거, 한도 도달 시 신규 요청 차단·종료·snapshot 수집을 설계한다. streaming/in-flight 요청의 초과 가능성·사용량 누락·공급자 내부 요청 처리도 명시한다. 강제 불가능하면 관측 상한/초과량과 시간 hard cap을 구분해 보고하고 **이번에 합의한 token 조건을 조용히 완화하지 않는다**. 지원 가능한 대안을 준비해 리뷰 시 결정할 항목으로 남긴다.

계측은 monotonic wall time, 종료 원인, 모델/도구 호출·토큰·cache/추론 내역, 읽은 자료 경로/bytes(수집 가능한 범위), 검증 실행, 최종 diff/소스 hash, 누락/재시도·실패 원인을 포함한다. 파일 읽기량과 모델 입력 token은 같은 지표가 아니다. shell을 통한 접근까지 완전히 추적하지 못하면 coverage를 명시한다. 모델/문서 작성·환경 준비·개발자 검토 비용은 별도로 측정하고 과거 비용을 소급 추정해 실제 측정처럼 쓰지 않는다. 사람 재작업 시간은 실제 수행하지 않으면 null이다.

## 6. 격리와 제출 경계

기존 `workspace.ts`는 허용 파일의 복사기이며 OS 격리가 아니다. 실험 내부의 작은 실행/수집 계층을 추가하고, 설치돼 있는 컨테이너 또는 동등한 강제 접근 제한을 우선 사용한다. 범용 agent 플랫폼이나 코어 공개 API로 확장하지 않는다.

- agent 영역에는 해당 조건 자료, 고정 원문, 공통 도구/준비 config/의존성만 제공한다. 의존성·도구·자료는 읽기 전용, 생산 소스와 scratch는 정해진 쓰기 영역이다.
- Ontosary checkout·평가기·참조/결함 패치·리뷰·다른 조건 자료/제출물·호스트 홈·cache 전체·컨테이너 제어 socket·관리자 자격 증명은 노출하지 않는다. 원본 upstream 문서/라이선스는 공통 입력이다. 링크를 통한 외부 탐색은 허용하지 않는다.
- 셸/도구 환경의 임의 외부 네트워크를 막고, 모델 통신은 agent 셸이 자격 증명이나 임의 relay로 이용할 수 없는 제한된 실행기 경로로 분리한다. 단순히 모델 API 도메인 전체를 셸에 열어두고 격리 검증 완료라고 하지 않는다.
- 조건별 자료는 같은 경로에 놓고 조건 코드/가설/다른 조건 목록은 agent에게 전달하지 않는다. 문서 형태 자체를 숨길 수 있다는 뜻은 아니다. 결과는 블라인드 실행 ID로 저장하고 조건 매핑은 평가자만 소유한다.
- 제출 때 실행기와 자식 프로세스를 정지시키고 final source를 immutable snapshot으로 수집한다. 실행 중 바뀌는 파일을 검증/평가하지 않는다. manifest·모든 수정/추가/삭제·보조 파일 분리를 보존한다.
- 제출 코드의 평가도 평가자 호스트의 전체 권한으로 실행하지 않는다. 별도 제한된 작업 환경·고정 의존성·자원/시간 상한을 사용한다. evaluator 파일의 무결성을 유지하며, 비공개 결과가 다음 agent 실행으로 돌아가지 않게 한다. 현재 VM을 보안 경계로 취급하지 않는다.

실제 agent 도구와 같은 사용자·권한·mount·network 경로에서 읽기/쓰기/접근 거부 probe를 실행한다. 허용 소스 읽기/편집·타입 검사, evaluator/다른 조건/호스트 경로 거부, symlink/상위 경로 우회, 읽기 전용 자료 변경, 외부 network, 남은 프로세스/다음 실행 잔존 상태를 확인한다. 존재하지 않는 경로에서 ENOENT가 난 것만으로 격리를 통과시키지 않는다. 격리 바깥에 존재하는 비민감 canary를 두어 거부를 검증한다. 실제 비밀을 probe에 쓰거나 로그에 남기지 않는다.

격리 runtime이 없거나 필요한 기능이 막혀 있으면 자체 fixture·문서 작업은 진행하되 환경 준비 완료를 주장하지 않는다. 새 유료 인프라·광범위한 호스트 권한 변경·다른 실행 모델이 필요할 때는 구체적인 대안/비용/남은 검증을 인계한다. 일반적인 모듈 분리·파일명·테스트 구성은 개발자가 결정한다.

## 7. 평가 계약과 결과 처리

현재52사례와 R8/R9/R10을 유지한다. 새로 확정된 **값 없이 완료·예외/stream error 없음·undefined resolve** 계약이 실제 assertion으로 확인되는지 감사한다. 요청0만 검사하면 `of(undefined)`/미완료 stream 등 다른 동작도 통과할 수 있으므로, 필요한 최소 관찰·회귀를 추가한다. 지원된 동기 완료를 직접 관찰하며 sleep을 늘려 비동기 지원을 흉내 내지 않는다. 기존52사례 안에 assertion을 추가할지 별도 사례를 둘지는 자유지만 분모/기존 판정 변화와 이유를 보고한다.

참조 diff와 일치하도록 채점하지 않는다. 별도 helper 해법은 계속 통과해야 한다. 실제 제출 타입/호출자·snapshot·component/locals·전체 payload/순서 비교는 약화하지 않는다. 평가기 변경 시 version/ID·모듈 지문과 원문 대응을 갱신한다. 새 정책과 관련 없는 evaluator 확장은 하지 않는다.

실행별 결과는 성공, 타입/동작 실패, 미지원, 시간/토큰 한도·미제출, 환경 장애를 분리한다. 모든 예정 실행의 상태를 남기며 미지원/중단을 성공률 분모에서 제거하지 않는다. 성공은 타입·지원 동작·동일 소스 검증의 통과다. 52사례를52개의 독립 실험 표본으로 세지 않는다. 보존/새 요구·누락 경로·불필요 변경/가정 위반과 비용을 함께 제시한다.

과업 성능에 따른 재실행은 금지한다. 명확한 환경 장애에만 같은 조건으로 최대1회 대체 실행을 허용하는 계획을 명시하고, 원래 시도와 장애 근거를 모두 보존한다. 반복 장애나 공통 평가기 결함은 배치를 중단해 검토하며 조건별로 선택 재실행하지 않는다. 실제 재실행 역시 이번에는 수행하지 않는다.

제출 diff의 블라인드 검토 양식과 데이터 수집 스키마를 준비한다. 설명에 근거가 있는지·불필요한 변경·범위 위반을 검사하되, 특정 참조 구현 사용 여부는 점수로 쓰지 않는다. 사람 검토가 수행되지 않으면 agent 검토와 구분한다. 긍정/부정/동률/미지원 결과의 해석과 추가 반복 여부는 최초9회 결과를 확인한 뒤 별도 결정한다.

## 8. 구현 순서와 검증

1. **계약 명세:** 단일 TASK/공개 안내/평가자 run-plan·판정 기준을 작성한다. 정확한 모델/실행기·토큰 계측·격리 runtime의 가능 여부를 먼저 조사해 장애를 일찍 드러낸다. 이 조사는 실제 과업 실행을 포함하지 않는다.
2. **C 및 대응표:** 변경 전 B/모델을 고정하고 C를 작성한다. 전체 단위의 양방향 대응·근거/상태·개발자 의미 검토를 마친다. 사람 검토 묶음을 별도 생성한다.
3. **배포/공개 검사:** 공통 TASK/안내·C·manifest/allowlist·parity/readiness를 갱신한다. 공개 타입 검사와 source/auxiliary 수집 경계를 구현한다.
4. **격리/계측:** 실행 adapter·수집기·거부 probe와 계측 fixture를 구현한다. 모델 대신 정해진 도구 호출/usage 이벤트를 내는 대역으로 전체 경로를 통과시킨다.
5. **교정/재현:** 기존24제출과 정책 assertion·격리/계측의 부정 사례를 실행한다. 새 준비를 두 번 생성해 시간 등 명시된 비결정 필드만 제외하고 대조한다. 실제 A/B/C workspace를 만들고 조건별 내용·권한·해시를 검사한다.
6. **동결/인계:** 버전별 artifacts와 정확한 실행 명령·미해결 항목을 저장한다. 본 비교 실행 권한을 열지 않고 리뷰를 요청한다.

| 과업/공개 조건 | A/B/C TASK·안내 동일 hash, 공개 정책과 private assertion 대응, 해법/숨김 평가 누출 없음 |

임의 모델 응답·실제 계정 비용을 발생시키지 않는 대역 검증으로 실행기 제어/계측 경로를 확인한다. 공급자 실통신·실제 모델 usage까지 검증한 것은 아니므로 해당 범위는 분리해 기록한다. 실제 모델 연결 확인이 필수로 남으면 리뷰 후 무관한 작은 입력을 사용하는 연결 점검 절차를 제안하고, 이번에 과업을 보내 우회하지 않는다.

## 9. 동결 산출물과 완료 조건

새 날짜/버전 경로에 TASK·공개 안내·C·bundle/allowlist·정보 대응표·run-plan·readiness·환경 명세/이미지 digest·검증 로그·교정 원시 결과·재현 hash를 보존한다. 가능하면 `results/<완료일>-trial-preparation/`, `verification/<완료일>-trial-preparation/`을 사용한다. 과거 결과/독립 probe는 덮어쓰지 않는다.

정적 내용 manifest와 별도 execution-manifest를 연결해 모델/설정·도구·환경·평가기·예산·순서·검증 명령·source/bundle 지문을 모두 식별한다. execution-manifest를 자기 hash에 포함하는 순환 정의를 만들지 않는다. 자격 증명·토큰·개인 홈 내용은 artifact에서 제외한다. 기반 source/모델/근거가 같으면 baselineId/modelId는 유지하고, 공통 과업/C/배포 변화는 새 bundleId로 표현한다. 환경 변경으로 기반 입력 자체가 달라지면 기존 ID를 강제로 유지하지 말고 원인과 영향 검증을 인계한다.

모든 기술 준비가 끝난 경우에도 상태는 **배포 내용 동결·독립 리뷰/사람 대응 검토 대기**다. `trialAuthorized:false`, `readyForTrial:false`, `results:null`을 유지한다. 실제 실행 진입점은 이 상태에서 과업 실행을 거부하며, fixture 검증 경로와 분리한다. 검증으로 확인된 기술 항목만 verified로 올리고, 사람 동등성·최종 실행 승인은 pending으로 남긴다. 이후 승인은 해당 불변 artifact hash에 연결한 별도 기록으로 남길 수 있다. 실제 필수 설정/환경이 unresolved이면 전체 준비 완료나 실행 계약 동결로 표현하지 않고 완료 부분·차단 항목을 분리한다.

완료 조건은 다음과 같다.

1. 승인된 정책이 동일한 공통 TASK/공개 실행 안내와 평가 assertion에 반영돼 있다.
2. C는 읽기 좋은 동등 지식 문서이며 전체 대응·개발자 검토·사람 검토용 자료가 있다. 사람 승인을 대신 만들지 않았다.
3. 정확한 실행 조건과 한도 계측/종료·제출 경계가 구현되고 실제 격리 probe 및 대역 검증 근거가 있다. 미검증 실통신 범위를 분리했다.
4. 기존 평가 회귀·확정 정책·공개 검사·complete-root·재현/배포·전체 검사가 통과했다. 평가기/ID/파일 개수 변화가 설명된다.
5. 동결된 새 artifacts와 재현 가능한 명령, 실패/복구/블라인드 평가 절차가 있다. 실제9회 비교·추가 agent 실행·H-O/H-F 결과·S3는 수행하지 않았다.
