## 작업 목표

Ontosary가 인공 예제 밖의 코드에서 어느 정도의 사실을 추출하고 어디서 실패하는지 재현 가능한 자료를 만든다. R1/R2/R3는 main `c6e0fc7babb28ac37fde6fdd68f416af7add8e78`에 대한 독립 검토에서 해결로 판정됐다. Gate 1은 당시 제한된 지원·검증 범위에서 통과했지만 업무 의미 유용성·기존 도구 대비 효용·실무 비용은 아직 미검증이다.

이번 하나의 작업은 **작은 실제 corpus 2개, 코드 사실 라벨 20~30개, 현재 분석기의 coverage 및 실패 관찰 보고**다. 제품 기능 확장이 아니다.

## 현재 상태와 근거

AGENTS, CONTRIBUTING, PROGRESS, ARCHITECTURE, ROADMAP, `docs/reviews/2026-11-07-post-merge-review.md`부터 읽는다. 원격·브랜치·사용자 변경과 최신 main을 확인한다. 위 SHA 이후 변경이 있으면 현재 분석기 버전을 별도로 기록한다.

독립 리뷰 시 `pnpm check` 82개, 실험 4건, 기존 독립 probe와 추가 receiver/this/import/file 경계 검증이 통과했다. enum receiver는 직접 enum 선언 식별자만 허용하고 explicit this는 거부한다. FCA는 기본 128객체/64속성/256개념, 논리 비교는 4,096조합 상한이 있다. `files`는 실제 분석한 구현 파일 수이며 프로젝트 전체 coverage 비율이 아니다.

## 구현·실험 범위

1. 공개/허가된 실제 TS 프로젝트 2개를 선정한다. 작은 업무 규칙이나 상태 판정이 존재하고, 코드 사실을 사람이 대조할 수 있는 범위를 선택한다. 사용자 사적 코드나 실행 권한이 없는 데이터는 수집하지 않는다. repository URL, 정확한 revision, 라이선스·재배포 조건, 수집 경로와 범위 선택 이유, 가져온 파일의 해시를 manifest로 남긴다. 전체 저장소 복제가 불필요하면 재현용 다운로드 절차와 최소 추출 범위만 저장한다.
2. 원래 tsconfig/타입 관계를 가능한 한 보존한다. 별도 분석용 tsconfig가 필요하면 수정 내용·준비 시간·빠진 파일/참조와 이유를 기록한다. 분석하기 쉬운 함수를 새로 작성하거나 인공 예제처럼 바꾸지 않는다. 원본 전체가 한도를 넘으면 실패 결과를 기록하고, 의미 있는 작은 범위를 별도 실행한다. 축소 결과를 전체 프로젝트 coverage로 일반화하지 않는다.
3. 결과 후보를 정답으로 사용하기 전에 총 20~30개 코드 사실 라벨을 만든다(두 corpus에 모두 분포). 예: 선언 identity, 실제 속성 사용, 특정 반환 조건, 알려진 비관련 동명/동형 타입. 라벨마다 source location, 주장, 근거, 범위, 작성자/방법을 기록한다. 업무 의미 후보는 별도 층으로 두고 `unreviewed`로 표시한다. agent의 판단을 사람의 승인으로 표시하지 않는다.
4. 고정 분석기에서 scan을 실행하고 라벨별 맞음/누락/오연결/미지원/판정 불가를 기록한다. “전체 함수 중 predicate 지원 비율”과 “사전에 정한 비교 대상 중 지원 비율”을 구분한다. 컴파일 오류, 추출 누락, 비교 미지원, FCA 상한 초과, 잘림을 별도로 보고한다. 각 지표의 분모를 명시한다.
5. 한도 내에서 concepts 결과를 보존한다. 타입·속성별 단순 공유 그룹을 같은 facts에서 만들어 FCA와 나란히 검토할 자료를 준비할 수 있다. 후보 개수 증가를 품질 향상으로 계산하지 않는다. 업무 관계/의미 평가는 사람이 검토하지 않았다면 미검증으로 남긴다.
6. 가능한 비교 과업에는 동일 입력·도메인 전제를 명시하고 비교할 함수를 선택한다. 그 전제를 정당화하지 못하면 비교하지 않거나 Unknown으로 기록한다. 반례는 실행 결과의 차이이며 정책 위반의 증거라고 쓰지 않는다. 임의 원본 프로젝트 코드를 실행하는 기능을 추가하지 않는다.
7. 준비 비용, 분석 wall time, 후보 수, 검토자가 확인해야 할 근거·실패 목록을 정리한다. 실제 사람의 검토 시간을 측정하지 않았다면 이를 별도 미측정 값으로 남긴다. 후속 사용자 과업 실험은 “관련 규칙 위치 찾기 / 후보 검토 / 조건 차이 설명”으로 준비한다.

## 제외 범위

코어 지원 문법 확장, FCA 상한을 임의로 높여 성공시키기, 새 랭킹/온톨로지/LLM/SMT/프레임워크 플러그인/승인 UI, 성능 최적화, npm 배포는 제외한다. 새 false proof가 나오면 별도 최소 재현을 보존하고 Gate 1 재검토 대상으로 보고한다. 측정 작업 안에서 조용히 수정해 전후 결과를 섞지 않는다.

## 완료 조건

- 정확한 revision·라이선스·분석 범위·해시를 가진 corpus manifest 2개와 재현 절차가 있다.
- 20~30개 라벨이 도구의 FCA 출력과 독립적으로 작성됐고 코드 사실/업무 의미 후보/사람 승인 상태가 분리돼 있다.
- 각 라벨에 판정과 원본 근거가 연결되고, metric 분모와 미지원/실패/한도 초과가 누락 없이 기록된다.
- 프로젝트가 분석에 실패해도 실패 자료를 보존한다. 성공하는 코드만 골랐다는 선택 편향을 숨기지 않는다.
- 동일 분석기·revision의 재실행에서 핵심 결과가 재현된다. 경로와 의존성 레이아웃 때문에 ID가 달라지면 그 원인을 기록한다.
- 다음 개선 후보는 관찰 근거가 가장 강한 **하나**만 제안하거나, 유용성 근거가 부족하면 추가 기능보다 사용자 검토를 권장한다.
- `pnpm check`와 관련 실험이 통과하고 과거 날짜별 원시 증거를 덮어쓰지 않는다. 새 연구의 실패 결과는 검사 통과와 별개로 사실대로 보고한다.

## 검증·문서화·인계

작은 고정 manifest와 재현 runner를 사용해 원시 결과와 해석 보고를 분리한다. 코드 사실의 source evidence를 재확인하고, agent 작성 라벨은 사람이 검토할 자료를 함께 남긴다. 사람이 검토할 수 없는 경우 해당 승인·시간 측정을 완료로 표시하지 않는다.

PROGRESS에는 실제 수행한 내용과 다음 리뷰 자료를 기록한다. RESEARCH에는 관찰·추정·미검증을 분리한다. 범위·우선순위가 바뀌면 ROADMAP, 중요한 설계 선택은 DECISIONS에 이유를 남긴다. 2026-11-04/06/07의 과거 리뷰 원시 증거는 보존하고 새 실험은 실행 날짜로 저장한다.

AGENTS/CONTRIBUTING의 지속 승인에 따라 검증·staged diff 확인·커밋·작업 브랜치 push·PR 검토·필수 검사 확인·merge·main 동기화를 수행한다. 원격 보호 규칙을 우회하지 않고 self-review를 다른 사람의 승인으로 쓰지 않는다. 이 승인은 패키지 배포나 저장소 권한 변경을 포함하지 않는다.
