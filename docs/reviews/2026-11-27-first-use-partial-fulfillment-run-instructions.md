# 개발 세션 지시문 · Vendure 부분 출고 두 agent 간 대리 인계 실행

진행자로서 작성 agent 한 세션과 후속 agent 한 세션의 대리 인계를 한 차례 진행해 주세요. 부분 출고를 조사한 작성자가 근거를 남기고, 그 기록을 처음 받는 agent가 새 변경 요청에 활용할 수 있는지 봅니다. 이 문서는 진행자용입니다. 참가자는 자기 역할의 `START.md`에서 시작합니다.

## 참가자와 실행 범위

사용자가 선택한 구성은 **새 작성 agent 한 세션 → 새 후속 agent 한 세션**입니다. 사람 섭외 없이 실행하세요. 준비·검토를 진행한 대화는 어느 참가 세션에도 상속하지 말고 각 역할에 지정된 전달 디렉터리만 작업 대상으로 주세요. 작성 agent는 코드나 과업의 답에 관한 사전 설명 없이 시작합니다. 두 세션 모두 기존 승인된 접속 경로를 쓰고 참가 자료 밖의 공개 답안이나 이전 리뷰를 조회하지 않도록 안내하세요. 한 역할의 실패를 다른 세션으로 대체하거나 새 비용·권한을 추가할 필요가 생기면 그 지점까지 보고하세요.

이 실행에서 관찰할 수 있는 것은 두 agent가 코드 근거를 기록하고 재사용하는 과정입니다. 작성·탐색 시간은 agent의 실측 시간으로 기록합니다. 사람의 첫 사용성·소요 시간과 업무 담당자의 정책 승인은 미측정입니다.

## 실제 인계

1. [준비 보고서의 전달 명령](2026-11-26-first-use-partial-fulfillment-preparation.md#누구에게-무엇을-전달하는가)으로 작성자 자료를 만드세요. 검증된 Vendure v3.5.0 리비전 `534e6003534f74761e82de1b8c6061cba89945d1`과 [작성자 안내](../../experiments/first-use/partial-fulfillment/author.md)를 그대로 씁니다. 준비자가 설치·빌드를 대신했다면 그 작업과 시간을 따로 적으세요.
2. 작성자는 추가 출고를 시작할 조건과 품목별 출고 가능 수량의 관계를 조사해 `HANDOFF.md` 한 건을 제출합니다. IDE·검색과 공개 CLI 중 어떤 도구를 쓸지는 작성자가 정합니다. 진행자는 설정·조사·기록 시간, 핵심 근거를 처음 찾은 수단, 받은 도움과 시점을 별도로 받습니다. 기본 범위에서 FCA 상한에 걸려도 그대로 관찰을 이어가세요. 과업 전에 관련 파일을 골라 주거나 상한을 조정하면 첫 발견의 의미가 달라집니다.
3. 작성자의 첫 제출을 원문 그대로 보존하고 그 파일로 `prepare.sh agent`를 실행하세요. 새 agent 세션에는 같은 리비전의 깨끗한 소스, 제출된 기록, [후속 변경 요청](../../experiments/first-use/partial-fulfillment/agent.md)만 전달합니다. 앞선 대화, 진행자의 보충 설명, 공개 저장소에 있는 검토 답안은 입력에서 제외합니다. 기록에 오류나 누락이 있어도 고쳐 주지 마세요. 기록이 제출되지 않으면 이유를 남기고 후속 단계는 미실행으로 마감합니다.
4. 후속 agent의 첫 변경 제안을 보존하세요. 어떤 위치에서 안내를 추가할지, 보존할 동작과 회귀 사례가 무엇인지, 어떤 판단은 기록에서 가져왔고 어떤 근거는 직접 찾아 보충·교정했는지 받습니다. 제출물은 소스에 근거한 변경 제안까지입니다. 한 차례의 인계로 끝내고 결과를 리뷰해 주세요.

## 관찰 결과와 완료 조건

검토자는 두 제출을 받은 뒤 [원문과 주문 대조 사례](2026-11-26-first-use-partial-fulfillment-preparation.md#검토자용-기준-소스와-주문-예)로 아래 질문을 각각 판정합니다. 다른 코드 경로나 수치 예로도 같은 동작을 설명하면 인정해 주세요.

| 판단할 질문 | 보고서에 남길 근거 |
|---|---|
| 작성자가 재확인 가능한 기록을 남겼는가? | 주문 단위 진입과 행별 수량을 구별한 설명, 실제 파일·심볼, 검산한 주문 예. 확인한 코드 동작과 추정한 업무 의도를 구별하고 도움을 받은 지점을 적습니다. |
| 그 기록이 새 변경 제안에 쓰였는가? | 기록의 주장 하나를 후속 제안의 특정 판단과 연결합니다. 타당한 제안을 전부 재조사해 만든 경우, 제안의 정확성과 기록의 재사용을 따로 판정합니다. |
| Ontosary가 어디에 기여했는가? | 핵심 근거를 일반 검색에서 먼저 찾았는지, `scan`으로 발견하거나 확인했는지, 근거를 찾는 데 방해된 출력이나 오류가 있었는지 적습니다. FCA 후보를 받지 못했다면 후보의 유용성은 미측정입니다. |

결과 PR에는 실제 전달한 버전, 두 세션의 역할과 분리 방법, 두 최초 제출물, 도움이 필요했던 지점과 실제 소요 비용, 판단별 소스 근거를 연결해 주세요. 사용한 agent의 모델·설정과 확인 가능한 시간·사용량을 남기고 결측치는 추정하지 않습니다. 미제출·중단도 관찰 결과입니다. 막힌 단계와 그때까지의 증거를 남기면 됩니다. 개인 식별 정보는 공개 자료에서 제외하세요.

이 한 사례로 판단할 수 있는 범위는 기록의 정확성, 인계에서 관찰한 재사용, 도구의 구체적인 기여까지입니다. 결과를 좋게 만들기 위한 재시도, 제품 기능 변경, 배송비 취소 A/B/C 재개는 별개 작업입니다.
