# EROFS 정적 진단 독립 리뷰

2026-11-18. [개발 보고서](2026-11-18-s2-erofs-diagnosis.md)와 구현/근거 커밋 `f180c311868a37803692ddd257ae4482aca96162`를 검토했다. PR #76은 개발 세션에서 이미 `6042f23`으로 병합됐고 두 tree가 같음을 확인했다. **읽기 전용 진단 과업은 완료로 인정한다. 보완을 요구할 결함은 발견하지 못했다.** 정확한 실패 syscall은 여전히 미관측이므로 EROFS 해결이나 C안 실행 성공으로 판정하지 않는다.

## 기술 판단

선두 후보인 `canonical(/tmp)/codex-daemon-22002` 생성은 근거가 충분하다. [고정 소스](https://github.com/openai/codex/blob/c40729ea5cf8e947481b130c59807273eda2f8e9/codex-rs/uds/src/daemon_directory.rs)에서 경로는 `/tmp`와 effective UID로 계산하고 디렉터리를0700으로 생성한다. TMPDIR/HOME/CODEX_HOME를 사용하지 않으며, 호출하는 filesystem 인자 구성에는 daemon_auto_start 조건이 없다. `TMPDIR=/scratch`만 지정해도 이 준비가 scratch로 옮겨지는 것은 아니다.

[호출 지점](https://github.com/openai/codex/blob/c40729ea5cf8e947481b130c59807273eda2f8e9/codex-rs/linux-sandbox/src/bwrap.rs#L409)과 오류 전파·proc preflight·환경 재구성도 보고서와 맞는다. helper 준비는 내부 sandbox 파일 뷰를 완성하기 전에 이미 적용된 외부 서비스 경계에서 수행된다. 당시 명령에는 ProtectSystem=strict가 있고 `/tmp` 쓰기 예외나 PrivateTmp는 없다. [systemd 공식 문서](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#ProtectSystem=)의 설정 의미와도 충돌 가설이 일치한다. 다만 현재 문서로 당시 mount 상태를 증명할 수 없고, 디렉터리가 이미 올바르게 존재했는지도 모른다. 따라서 선두 후보와 확정 원인을 구분한 현재 결론을 유지한다.

다른 초기화 경로·synthetic mount bookkeeping·payload 쓰기를 단계별로 비교한 것은 적절하다. launcher 탐색을 고려해 bwrap이 전혀 실행되지 않았다고 단정하지 않은 점도 정확하다. 모든 쓰기를 완전 열거한 증명이나 재현 빌드 수준의 동일성 증명은 이번 진단의 완료 조건이 아니며 추가로 요구하지 않는다.

## 독립 검증과 한계

- GitHub의 해당 commit에서12개 소스를 다시 읽어 byte 수·SHA-256·Git blob ID를 모두 확인했다. 보존된20개 발췌의 행 범위·원문·hash도 일치했다.
- 공개 npm archive165,822,267bytes를 분석용으로 다시 읽어 현재 registry의 SHA-512 integrity와 보존된 release asset SHA-256에 일치함을 확인했다. 압축 내4개 파일의 크기/hash를 재계산했고 native hash는 당시 worker 기록과 같았다. 다운로드한 임시 archive는 검증 후 제거했으며 설치·실행하지 않았다.
- 저장 attestation의 payload를 직접 decode해 보존본과 같음을 확인했다. subject digest는 위 archive와 일치하고 선언된 source commit은tag object와 같은c40729e다. Sigstore 서명 체인의 별도 검증·재현 빌드는 하지 않았다. 공개 배포자의 선언을 동일 bytes로 연결한 근거로만 평가한다.
- analysis.json의 native 관측·service argv를 당시 원시 JSON과 대조했다. 과거99개 tracked 파일은2008351과 bytes가 같았다. PR 변경은 문서/정적 근거뿐이고 runtime 코드는 바뀌지 않았다.
- `pnpm check`:304개 테스트·타입 검사·예제 build 통과. 코드 변경이 없어 관련 없는 VM/Python 실행기 실험은 반복하지 않았다. 이번 리뷰의 실제 VM·CLI binary·trace·정책 변경·인증/model 호출은0회다.

## 잘한 점

1. 오류 문자열에 맞는 소스를 찾는 데서 멈추지 않고, 당시 바이너리→공개 패키지 bytes→선언된 commit을 연결했다. 최신 소스로 과거 동작을 설명하는 위험을 줄였다.
2. 최초 CLI·helper·payload 환경과 외부/내부 파일 경계를 구분했다. 단순히 `/tmp`를 writable로 바꾸는 처방보다 원인 판단에 직접 기여하는 결과다.
3. 사실·정적 추론·미확정 사항을 분리하고, 선두 후보와 반대 근거를 함께 제시했다. 정적으로 알 수 없는 부분을 숨기거나 과업 실패로만 처리하지 않았다.
4. 새로운 실행기 없이 필요한12개 소스와 작은 근거 묶음으로 다음 질문을 좁혔다. 기록된 조사 시간은555.477초(약9분15초)이며 최초 지시/Git 읽기가 빠져 있음을 명시했다. 이전 회차의 전체 소요 시간과 직접 비교하지 않는다.

## 관리자로서 개선할 점

- **실패를 판별할 관측을 실행 전에 정해야 했다.** 앞선 smoke는 오류 존재를 확인했지만 실패 path/syscall을 남기지 못해 별도 진단 회차가 필요했다. 앞으로는 해당 가설을 구분하는 최소 관측을 실행 설계에 포함한다. 모든 데이터를 미리 수집하거나 전체 trace 기반을 선행시키라는 뜻은 아니다.
- **소스와 필수 초기화 요구를 더 이르게 확인할 기회가 있었다.** 엄격한 서비스 경계를 설계하면서 CLI 초기화가 허용 경로 밖에 쓰는지 짧게 확인하는 질문을 제가 먼저 제시할 수 있었다. 이번 결과가 과거 모든 환경 실패를 예방했을 것이라고 단정하지는 않지만, 제한된 호환성 조사에 앞서 경계를 계속 다듬는 순서는 개선한다.
- **작업을 지나치게 잘게 나누면 의사결정 왕복이 늘어난다.** 다음에는 경로 확인과, 가설 확인 시 적용할 수 있는 국소 조치·대조 범위를 한 과업으로 합의하는 방안을 제안한다. 이미 합의한 조건 안의 대응은 개발 세션에 맡기되, 이 리뷰 자체로 재실행·설정 변경을 승인하지 않는다.
- **근거 수집의 깊이는 다음 결정에 필요한 수준에서 멈춘다.** 이번 패키지/소스 연결은 유용했지만 새 공급망 검증 체계·재현 빌드까지 확대할 필요는 없다. 보고서는 판단과 불확실성을 먼저, 상세 근거는 참조로 유지한다. 시간은 동일한 측정 범위로 비교하고 한 사례만으로 새 지시 방식의 효과를 단정하지 않는다.

앞으로 리뷰에서 잘한 점과 지시하는 세션의 개선점을 함께 평가하도록 AGENTS에 사용자 요청을 반영했다. 위 개선은 개발 결과의 결함이나 재작업 요구와 구분한다.

## 다음 판단

보고서의 **동일 조건에서 실제 실패 path·연산·errno를 확인하는 제한 관측**을 권고한다. 관측 도구 선택은 개발 세션에 맡기며, tracer가 실패 조건에 영향을 주는지와 같은 서비스의 mount/대상 사전 상태를 함께 설명할 수 있어야 한다. 가설 확인 뒤 관리자 사전 생성 등 최소 조치까지 같은 과업에 포함할지는 사용자와 범위·예산을 합의할 사안이다. `/tmp` 전체 쓰기 허용이나 ProtectSystem 해제부터 진행할 근거는 없다.
