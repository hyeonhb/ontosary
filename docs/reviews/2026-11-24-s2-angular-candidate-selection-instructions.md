# S2 개발 지시 · 동결된 Angular 자료에서 출발해 실제 변경 과업 선정하기

**Vendure의 기존 Angular Admin UI에서 본 비교에 쓸 실제 변경 한 건을 찾아 채택 여부를 제안해 주세요.** 이번 질문은 같은 구현에 연결된 도메인 모델이 있을 때 에이전트가 업무 요청의 영향 범위를 찾고 보존해야 할 동작까지 수정하는 데 도움이 되는가입니다. #4728에서는 부분 수정의 차이가 화면에 나타났지만 실제 수정 대상은 React Dashboard였고 동결된 B/C의 코드 근거는 Angular 파일에 있었습니다. 이번에는 자료의 적용 범위를 먼저 확인해 후보를 좁힙니다. 참가 모델 호출은 예비 실행을 포함해 0회입니다. ## 어디서 어떤 변경을 찾을지

11월 10일 동결한 B의 68개 조회 결과와 C의 대응 문서 4개를 사용합니다. 이미 확인한 코드 근거 30개가 가리키는 8개 파일에서 주문 상세, 직접 취소, 환불에 동반되는 취소, 대화상자와 데이터 서비스 사이의 실제 경로를 확인해 주세요. 이와 같은 구현에 영향을 준 Vendure 이슈·병합 PR과 변경 이력이 후보군입니다. 8개 파일은 탐색의 시작점이며, 연결된 다른 파일이나 업무 경로도 과업에 포함할 수 있습니다. [동결 B/C](../../experiments/domain-model/s2/results/2026-11-10-trial-preparation/) · [기존 근거 파일과 심볼](../../experiments/domain-model/s2/results/2026-11-24-modified-order-selection/results.json)

후보는 다음 기준으로 판단합니다.

- **변경 전에도 같은 구현을 설명하는가.** 후보의 해결 커밋과 직전 리비전을 고정하고, 관련 B/C의 인용·심볼·관계를 직전 소스에서 확인합니다. 경로나 파일 해시가 달라졌다면 어느 근거가 여전히 유효하고 어느 근거가 깨졌는지 대조합니다. 자료에 직접 연결된 경로 하나와 참가자가 추가로 발견해야 할 경로가 공존해도 좋습니다.
- **사용자 행동으로 변경과 보존을 함께 판정할 수 있는가.** 실제 업무 요청과 기존 동작에서 신규 기대와 보존 요구를 도출합니다. 한 경로만 고치면 요청 일부를 충족해도 다른 경로의 동작을 놓치는 이유를 설명할 수 있어야 합니다. 수정 파일 수나 패치 크기는 복합성의 대용 지표로 쓰지 않습니다.
- **자료가 정답을 미리 알려주는가.** 자료의 기준 소스가 해결 이후라면 특히 주의해 주세요. 수정 후 코드, 해결 지시, 정답 테스트가 어느 조건에 들어가는지 확인하고, 기존에 알 수 있던 도메인 지식과 해결 결과에서만 알 수 있는 정보를 구분합니다. 후보를 살리기 위해 B/C를 수정하거나 빠진 관계를 보충하지 않습니다.

탐색한 범위와 유력 후보의 채택·제외 근거를 간단히 남겨 주세요. 여러 후보가 적합하면 실제 업무 근거와 변경 전후 동작을 독립적으로 확인하기 쉬운 것을 우선합니다. B에 설명이 많은지, A가 실패할 듯한지는 선택 기준에서 제외합니다.

## 한 후보에 대해서만 동작 대조

위 기준을 통과한 후보가 있으면 평가자용 사례를 먼저 적고, **변경 전 원본·그럴듯한 부분 수정·알려진 정상 수정**을 같은 입력과 관측 경로에서 비교해 주세요. 어떤 사용자 행동에서 세 결과가 갈리는지 보여 주면 됩니다. 기존 검사나 작은 재현으로 충분하면 이를 사용하고, 참조 패치와 구현 모양이 달라도 동작이 같으면 인정합니다.

참가자용 요청 초안에는 사용자가 겪는 문제, 기대하는 결과, 보존해야 할 약속을 명시합니다. 파일·심볼, 정답 구현, 해결 PR, 사후 테스트는 평가자 자료로 둡니다. 후속 비교에서는 A/B/C 모두 같은 변경 전 소스와 일반 문서에서 출발하며, B에는 구조화 모델 조회, C에는 대응 서술 자료 조회를 더합니다. 최종 변경·보존 성공, 수정 전 발견한 관계와 근거, 실패를 포함한 비용이라는 기존 비교 기준을 유지합니다.

## 인계와 종료

채택을 권하면 **참가자용 요청 초안, 이슈·PR과 기준 리비전, 유효한 근거와 자료 공백, 대조별 기대값·실제값, 재현 방법**을 결과 PR에 담아 주세요. 구현 방법과 확인 순서는 개발 세션이 결정합니다.

정해진 자료 범위에서 적합한 후보를 찾지 못하거나 동작 검증에 별도 환경 투자가 필요하면, 어디까지 확인했고 어느 조건에서 멈췄는지를 근거와 함께 인계하면 완료입니다. 쉬운 과업으로 기준을 낮추거나 React 자료 재작성·범용 실행기 구축으로 확대하지 않습니다. 실제 과업의 채택, 참가 실행과 예산은 독립 리뷰 뒤 결정합니다.
