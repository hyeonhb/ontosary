## 목표 정렬과 다음 판단

사용자가 최종 목표를 **기존 프로젝트를 agent가 도메인을 이해하고 수정하기 좋은 프로젝트로 전환하도록 돕는 것**으로 명확히 했다. 온톨로지는 도메인 지식의 명시적 표현 수단이고 FCA는 그 구축을 돕는 방법이다. 업무 개념에서 코드 근거를 찾는 탐색은 첫 사용 경로이며 최종 제품 목표 전체가 아니다. 예시 그림의 계층/형식은 확정 아키텍처로 취급하지 않는다.

따라서 상한을 올려 전체 앱의 개념을 먼저 많이 만드는 것보다, 한 도메인의 사실→후보→검토 가능한 모델→agent 변경 과업을 연결한다. 현재 기본 상한은 PoC의 계산/결과 관리 예산이지 FCA의 수학적 최대 크기나 제품의 영구 한계가 아니다. 이번에는 상한을 유지한 별도 역할 context의 명시적 계약을 실험하며 원래 전체 context 실패를 덮어쓰지 않는다.

고정 원문에서 `OrderDetailComponent.refundOrder`(601행 이후)도 조건부 취소 service 호출(615~616행)을 포함하고, 뒤에서 환불 요청을 만든다(647~650행). `cancelOrder` 이름만 보는 탐색보다 확인할 경로가 넓다. 반면 취소 대화상자의 `cancel()`은 입력 없이 닫는 동작이다. 이 연결은 원문/참조 탐색으로도 확인할 수 있으며 FCA만의 발견이라고 주장하지 않는다. 어떤 공유 속성 묶음이 모델 작성·검토에 도움을 더하는지는 후속 실험 대상이다.

두 연구 질문을 분리한다. **H-O:** 모델을 제공하면 agent의 변경 누락/오류와 전체 비용이 개선되는가? **H-F:** 동일 사실에서 FCA를 추가하면 모델 구축·검토의 품질/비용이 개선되는가? 지금은 둘 다 미검증이다. 모델을 사람이 만들었다면 이를 FCA 자동 생성 결과로 세지 않으며, FCA가 별도 도움을 못 줘도 H-O가 자동으로 반증되는 것은 아니다.

## Gate와 인계

- Gate 1: 기존 제품 코어의 제한된 검증 범위 통과 유지. 모든 TS/런타임 건전성 증명은 아니다.
- Gate 2/3: 업무 개념 품질, 기존 검색·AI 도구 대비 효용, agent 변경 성능은 미검증이다.
- Gate 4: 환경 준비 비용 관찰은 추가됐다. 사람 작성/검토와 모델 유지 비용은 미측정이다.
- Gate 5: 확장/제품화 근거는 아직 부족하다. 새 core 기능·온톨로지 표준·자동 리팩터링을 승인한 결과가 아니다.

리뷰 세션은 제품 기능을 구현하지 않고 독립 검증과 방향/개발 지시를 정리한다. 다음 한 작업은 S1이며 S2의 실제 agent 비교는 그 결과를 검토한 뒤 진행한다. 사용자의 주요 기술적·철학적 판단 요청은 유지한다. 기존 정확성 지적 R1~R5의 해결 범위도 유지한다.
