# S2 개발 지시 · 주문 변경 후 환불 수량 과업의 채택 여부 검증

Vendure 이슈 #4728을 첫 실제 복합 변경 후보로 검토해 주세요. 우리가 알고 싶은 것은 같은 에이전트가 업무 요청에서 출발해 도메인 모델로 영향 범위를 더 정확히 찾거나, 같은 품질의 수정을 더 적은 비용으로 완성하는지입니다. 이번 결과물은 **이 과업을 A/B/C 비교에 쓸 수 있는지에 대한 근거 있는 판정**입니다. 실제 참가 호출은 0회이며 A만 먼저 실행하는 난이도 교정도 하지 않습니다. [이전 준비 종료 리뷰](2026-11-24-s2-refund-preparation-close.md)

## 참가자용 업무 요청 초안

> 고객이 주문을 변경해 기존 상품의 수량을 늘리거나 새 상품을 추가하고 차액을 결제했습니다. 그런데 관리자가 환불하려고 하면 변경 전 수량까지만 선택할 수 있거나, 추가한 상품이 나타나지 않습니다. 환불 화면에서 변경 후 실제로 구매한 상품과 수량을 확인하고 환불할 수 있게 해 주세요. 이미 일부를 취소·환불한 주문에서도 남은 수량은 계속 처리할 수 있어야 하며, 같은 수량을 중복 환불해서는 안 됩니다.

후속 비교의 세 조건은 이 업무 요청과 같은 변경 전 소스·일반 문서에서 시작합니다. A는 일반 검색, B는 A에 구조화 모델 조회 추가, C는 A에 대응 서술 자료 조회 추가입니다. 아래 이슈·해결 PR 링크, 구현 단서, 정답 테스트와 부분 수정은 평가자용입니다. 참가자용 입력과 검색 범위에서 해결 커밋이나 이후 기록을 읽을 수 없게 구분해 주세요.

## 채택을 판단할 두 가지 근거

**1. B와 C가 같은 변경 전 구현을 설명하는가.** 실제 수정 대상은 React Dashboard입니다. 기준 소스는 해결 커밋 `e7f8fe0029ceba9b450f60554226cec2cf628309`의 직전 부모 `e30fd9e94214135de85c95631edc6f2fcedd0da1`에서 확인해 주세요. 기존 Ontosary 자료는 주로 Angular Admin UI를 가리킵니다. B의 관련 개념·관계가 가리키는 파일이나 심볼을 이 리비전에서 열고, C의 설명에도 같은 사실·예외·근거·검토 상태가 담겨 있는지 예를 들어 보여 주세요. 같은 업무 용어가 등장한다는 사실만으로 두 구현의 관계가 같다고 판정하지 않습니다. [기존 B/C 자료](../../experiments/domain-model/s2/results/2026-11-10-trial-preparation/)

자료가 어떤 소스와 절차로 작성됐고 언제 고정됐는지 기록해 주세요. 자료에 빠진 업무 관계도 결과입니다. 이 지시문이나 해결 패치를 읽은 세션이 정답에 맞춰 B/C를 보충하면 자료 효과를 평가할 수 없습니다. 기존 자료나 과업과 독립적으로 정해진 절차로 같은 구현의 자료를 확보할 수 있는지 판단해 주세요. 별도 모델링·사람 검토·새 환경에 상당한 비용이 든다면 필요한 범위와 대안을 인계하면 충분합니다.

**2. 업무상 다른 수정을 독립적으로 가려낼 수 있는가.** 평가자는 아래 결과를 먼저 기준으로 삼고, 같은 입력·관측 경로에서 변경 전 원본, 화면 표시만 고친 수정, 현재 수량만 기준으로 삼은 수정, 알려진 정상 수정을 대조해 주세요. 각 사본에서 어떤 사례가 왜 갈렸는지 기록합니다. 평가 대상은 실제 화면에서 사용하는 표시·선택 가능 여부·수량 상한입니다. 평가기에 다시 구현한 계산만으로 제출에 점수를 주지 않습니다. 원래 PR의 구현 방식이나 파일 개수는 채점 기준이 아닙니다. | 평가 상황 | 사용자가 확인할 결과 |
| --- | --- |
| 1개 주문 후 2개로 늘리고 차액 결제 | 2개로 표시되고 2개까지 선택할 수 있다. |
| 새 상품 1개를 추가하고 차액 결제 | 새 상품이 환불 대상으로 나타나고 1개를 선택할 수 있다. |
| 3개 중 2개를 이미 취소·환불 | 남은 1개는 처리할 수 있고 2개를 다시 선택할 수 없다. |
| 해당 상품의 구매 수량을 전부 환불 | 더 이상 환불할 수량으로 선택할 수 없다. |

## 결과 인계와 종료

- **채택 권고**는 두 근거가 모두 성립할 때 제안합니다. 자료 버전·출처, 참가자용 입력 범위, 대조별 기대값과 실제값, 재현 방법을 결과 PR에 담아 주세요. 비교를 진행한다면 최종 변경·보존 성공을 일차 결과로, 첫 수정 직전 찾은 관계와 근거를 별도로 기록합니다. 품질이 같을 때는 실패를 포함한 총 토큰·탐색 시간으로 비용을 비교합니다.
- **보류 또는 다른 후보 권고**도 완료입니다. 어느 조건이 성립하지 않았는지, 확인한 사실과 미검증 부분, 다음 선택의 비용을 구분해 주세요. 자료 부적합이 일찍 확인되면 그 판정을 위해 새 Dashboard 실행기까지 만들 필요는 없습니다. 대안으로 기존 모델이 직접 다루는 실제 변경을 제시할 수 있습니다.
- 확인 순서와 국소적인 검증 방법은 개발 세션이 정합니다. 실제 Vendure 수정의 외부 제출, 참가 모델 실행, 본 비교 예산 확정은 이번 범위 밖입니다. 독립 리뷰에서 후보 채택 여부를 먼저 결정합니다.
