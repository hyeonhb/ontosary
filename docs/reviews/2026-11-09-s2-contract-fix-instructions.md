# 개발 세션 지시 — S2 평가 계약 R8/R9/R10 보완

작성: 2026-11-09. 기준 main `b71f5f6ef2a018de4f43c0501c3f93bf6c0dfab9`(독립 리뷰 PR #24). 실제 작업은 **이 지시가 반영된 최신 main**에서 시작한다. 이 문서는 개발·평가자 전용이며 A/B/C agent 제공 자료에 포함하지 않는다.

## 1. 목표와 승인 범위

사용자는 독립 리뷰에서 발견한 R8/R9/R10을 보완하도록 승인했다. 이번 목표는 **빌드할 수 없는 제출, 잘못된 취소·환불 요청, 요구 범위를 벗어난 환불 변경을 성공으로 인정하지 않는 평가기와 유효한 참조 수정**을 만들고 독립 재검토에 넘기는 것이다.

S2의 목적은 변경 전 도메인 모델이 agent의 수정 정확성에 도움이 되는지 검증하는 것이다. 모델 사용 효과 H-O와 FCA 구축 기여 H-F는 별개다. 평가기를 고치는 것은 효용 입증이 아니며, 본 비교를 실행하거나 다음 단계로 넘어갈 권한으로 해석하지 않는다.

단일 baseline 준비 세션, 동결 모델, 순수 조회, 사전 생성 B/C view, 실험 내부 모듈이라는 합의 구조는 유지한다. **완료 지점은 R8/R9/R10 구현·검증·재현·인계**다. `readyForTrial:false`와 미정 정책/격리/실행 조건을 유지한다.

## 3. 수정할 곳과 이번에 하지 않을 일

허용 범위는 S2 `evaluation/`의 제출 타입 검사·실행/판정·참조 수정·교정 runner, 이에 필요한 작은 내부 타입/모듈, 테스트/자체 fixture, 실험 README/현재 문서와 새 날짜의 결과다. 관련 코드는 전체 `pnpm check`의 타입 검사 안에 둔다. 제출 검증 모듈의 파일 분할과 CLI 보조 명령은 이 범위에서 개발자가 정한다.

공통 과업 문장·실행 계획의 적용 범위/평가 상태 설명을 수정할 수 있다. 이 경우 A/B/C에 동일하게 반영하고 새 버전 자료를 생성한다. 정답 함수명·수정 위치·참조 패치·평가 기대값은 agent 제공 자료에 넣지 않는다.

제품 core/CLI, FCA·논리 알고리즘/상한, S1/V1/V2, 모델12항목의 의미와 승인 상태, 준비/조회 계층의 큰 구조는 변경하지 않는다. 새 의존성·LLM/SMT·동적 agent 도구·S3 갱신·대규모 성능 리팩터링·C 문서 전면 재설계는 범위 밖이다. 리뷰의 비차단 성능 부채는 이번 수정과 분리한다. 과거 `results/2026-11-08`, `verification/2026-11-08`, 날짜별 리뷰·probe는 덮어쓰지 않는다.

## 4. 구현 순서와 세부 계약

### 단계 0 — 수정 전 반례를 고정

새 출력 경로에서 원래 oracle와 독립 반례를 실행해 다음 관찰을 재확인한다. 이후 API/구조가 바뀌어 역사적 probe가 실행되지 않게 되더라도 과거 코드를 수정하지 말고 동등한 사례를 새 회귀/교정 runner로 옮긴다.

| 발견 | 수정 전 관찰 |
|---|---|
| R8 | baseline TS 진단0, 참조 수정 진단5인데 oracle는 보존6/6·새 요구18/18 |
| R9 | 잘못된 주문 ID 또는 환불 결제 ID/금액을 보내는 변형도6/6·18/18 |
| R10 | 환불만+공백 reason 보존 사례를 더하면 baseline7/7, 참조 수정6/7 |

과거의 24개라는 총수를 새 합격 조건으로 고정하지 않는다. 사례가 늘어나면 실제 분모와 추가 이유를 보고한다.

### 단계 1 — R8: 제출 코드의 타입·구문 검증을 동작 검사와 분리

`transpileModule`은 실행용 변환으로 남겨도 되지만 제출 타입 검증을 대체할 수 없다. **추출·재구성한 메서드가 아닌, 실제 제출의 원래 클래스/모듈과 호출자 문맥**을 준비된 TypeScript 설정/의존성으로 검사한다. 설정·strict·진단 필터를 완화하거나 stub/`any`/오류 억제로 참조 수정의 오류를 숨기지 않는다.

원래 준비 Program의 진단0을 확인하고, 제출마다 해당 소스 버전의 구문/타입/설정·해석 진단을 수집한다. TypeScript 진단 코드·상대 파일·위치·메시지, 설정/도구/입력 지문, 실제 검사 파일과 변경 파일의 포함 여부를 결과에 남긴다. 파일 수1,638은 baseline 분모이며 helper 추가 후에도 같은 수여야 한다는 조건은 아니다.

제출 소스와 환경을 결합하는 경계를 명확히 한다.

- 파일시스템의 별도 복제 또는 CompilerHost의 가상 소스 뷰를 사용할 수 있다. 어느 방식이든 제출의 수정·추가 helper·삭제를 정확히 반영하고 의존성/설정은 고정 환경에서 가져온다. 타입 검사와 동작 실행이 같은 제출 내용을 읽었음을 hash/manifest로 확인한다.
- 제출에서 사라진 파일을 baseline 원문으로 조용히 보충하지 않는다. 기존 oracle의 네 파일만 있는 임시 복제는 완전한 제출이 아니므로 교정용 baseline+명시적 변경 집합으로 구성하거나 완전한 제출 복제로 바꾼다. 일반 제출 root와 명시적인 delta 입력을 혼동하지 않는다.
- 새 상대 helper의 import 해석과 내용이 실제 Program에 들어가야 한다. 검사 범위 밖의 변경, 미지원 의존성/구문/삭제는 구체적인 미지원/실패로 보고한다. 변경된 앱 소스를 검사하지 않고 전체 성공으로 표시하지 않는다. 기존 HTML 수동 검토 경계도 따로 유지한다.
- baseline의 변경 없는 환경 감사는 평가 배치에서 재사용할 수 있지만 서로 다른 제출의 SourceFile·진단을 잘못 재사용하지 않는다. 준비 단계는 계속 Program1회다. 제출 평가의 Program 수·시간은 별도로 기록한다.

보고서는 최소한 `typecheck`, `behavior`, `overall`에 해당하는 상태를 분리한다. 구체 필드명은 조정할 수 있다. 타입 검사가 실패/미지원/미수행이면 전체 합격은 불가능하다. 동작 검사를 건너뛰면 성공0건처럼 오해하지 않도록 `not-run`과 이유를 남긴다. 지원되지 않는 실행은 동작상의 실패와 구분하며 미지원도 합격은 아니다. UI/정책 검토 pending은 이 기술 판정과 별도다.

기존 CLI의 exit0이 관찰 수집 완료를 뜻하는 계약을 유지할 수 있으나, 결과의 전체 합격과 실행 오류/미지원 의미를 README와 교정 runner가 같은 방식으로 해석해야 한다. 부분 실패 시 성공 파일만 남기거나 전체 통과로 요약하지 않는다.

### 단계 2 — R10: 유효한 참조 수정과 취소 정책의 적용 범위를 맞춘다

현재 검토용 실패 처리 대안(a), 즉 invalid 취소 reason이면 요청/연쇄 환불을 억제하는 초안을 유지하면서 타입에 맞는 참조 수정을 만든다. 정확한 helper 이름·diff·특정 RxJS 표현을 정답으로 강제하지 않는다. 반환 타입과 호출자의 처리 계약을 함께 확인한다. 동기 예외/stream error 대안, UI 오류 표시·닫힘 방식은 이번에 승인된 최종 제품 정책으로 확정하지 않는다.

적용 범위는 다음과 같다.

| 경로 | 검토용 요구/보존 동작 |
|---|---|
| 직접 취소, service 직접 취소 요청 | 취소 payload reason을 trim한 nonblank 문자열로 전송. invalid이면 취소 요청 없음 |
| 환불+실제 일부 취소 | 취소 payload에 같은 요구 적용. invalid 취소 reason이면 초안(a)에 따라 취소·후속 환불 모두 억제 |
| 취소 없는 환불 | 새 취소 reason 정책을 적용하지 않음. 원래 환불 호출/인자/사유 보존 |
| 두 dialog dismiss | 취소·환불 요청 없음 |
| 정상 취소 후 환불 / 취소 오류 결과 후 환불 | 정상은 원래 호출 순서/내용 유지, 취소 오류 결과 뒤에는 환불하지 않음 |

`RefundOrderDialogComponent.select()` 진입 전체에 무조건 guard를 넣지 않는다. 실제 취소 lines가 있는지 원래 업무 분기를 기준으로 적용하고, 취소 입력만 필요한 변환을 한다. 공유 `this.reason`을 변경해 환불 payload까지 암묵적으로 trim하는 회귀도 방지한다. 혼합 경로에서도 환불 payload의 사유는 기존 의미를 보존한다. 환불 reason까지 강화하려면 범위 변경이므로 사용자 판단을 요청하며 이번 작업에 끼워 넣지 않는다.

환불만 경로에는 정상·앞뒤 공백·공백만 reason 보존 사례를 둔다. 원래 UI 조건과 메서드 직접 실행을 구분하고, 빈 문자열/null/undefined는 원래 UI에서 가능한지와 하네스 강제 주입인지 표시한다. 하네스가 UI 전체를 검증했다고 주장하지 않는다. generated GraphQL 타입·서버 schema를 고치지 않는다.

### 단계 3 — R9: 요청 payload와 부수 효과를 실제로 판정한다

호출 기록만 남기는 것을 검사 완료로 세지 않는다. 기대값은 fixture 입력과 명시적 계약에서 독립적으로 작성하며 제출의 실제 출력이나 참조 함수 실행 결과를 그대로 기대값으로 복사하지 않는다.

- 취소: 요청 종류, `orderId`, reason, active 주문의 lines 생략, 부분 취소 lines의 ID/양수 수량, `cancelShipping`을 확인한다.
- 환불: 요청 종류, `paymentId`, amount, lines의 ID/수량, reason, shipping, adjustment를 확인한다. 환불만 경로와 취소 후 환불 모두 포함한다.
- 호출 횟수·순서·불필요한 추가 요청·취소 오류 결과 이후 환불 중단을 함께 확인한다. dismiss와 invalid 취소에서 네트워크 호출0을 검사한다.
- 비교는 필드 의미에 맞춘다. 객체 key 순서 등 비의미 차이를 결함으로 세지 않고, lines의 중복/누락·수량은 놓치지 않는다. `undefined`와 필드 부재처럼 실제 전송에서 같은 의미를 갖는 경우의 비교 규칙을 문서화한다. 관찰값은 호출 시점에 복사해 이후 입력 객체 변조가 과거 기록을 바꾸지 않게 한다.

특정 fixture 값에만 맞춘 변형을 놓치지 않도록 최소한 복수 주문/결제 식별자, 서로 다른 양수 수량/환불 금액, 포함/제외 line과 배송 취소 flag를 다루는 작은 시나리오를 추가한다. 전체 Vendure 테스트 체계를 재구현하지 말고 이번 과업의 요청 보존 계약에 집중한다. 외부 서비스/UI 대역은 유지할 수 있으나 그 안에 취소/환불 분기·reason 정규화를 재구현하지 않는다.

| 직접 취소만 수정 / trim 누락 | 타입에 맞게 구성 | 해당 새 요구에서 실패 |
| 모든 환불에 취소 / dismiss 요청 / 취소 실패 뒤 환불 / 정상 취소 뒤 환불 누락 | 타입에 맞게 구성 | 각각 보존/연쇄 호출 검사에서 실패 |
| 잘못된 주문 ID / 환불 결제 ID / 환불 금액 | 각각 진단0인 변형 | 각각 요청 인자 검사에서 실패 |
| 환불중취소 lines의 ID·수량 변형 | 진단0 | 부분 취소 인자 검사에서 실패 |
| 환불만에도 취소 reason guard 적용 / 환불 사유 불필요한 trim | 진단0 | 공백만 또는 앞뒤 공백 reason의 환불 보존 검사에서 실패 |

**R9/R10 및 기존 동작 결함 변형은 유효한 새 참조 수정에 각각 독립적으로 적용한다.** 공통 타입 오류 때문에 모두 거부된 것을 동작 검출 성공으로 세지 않는다. 결함별 실제 바뀐 코드 hash/변경 내용과 실패한 assertion의 기대값·관찰값을 남긴다. 한 변형에 결함을 여러 개 섞기보다 원인을 분리한다. 잘못된 결제 ID와 금액도 각각 검출되는지 확인한다.

항상 실행되는 자체 소유 fixture에 타입 검사/추가 helper/삭제/미지원/판정 상태·payload 비교의 부정 사례를 넣는다. 외부 cache가 없다는 이유로 이 테스트를 skip하지 않는다. 실제 Vendure 교정은 별도 명시적 통합 명령이며 cache 부재를 성공으로 처리하지 않는다. 기존 Promise/async·제외 seam의 미지원 회귀도 유지한다.

## 5. 검증·재현·산출물

최소 검증 순서는 수정 전 반례 → 자체 fixture 회귀 → 새 참조 수정의 실제 타입/동작 검사 → 교정 행렬 → 전체 검사 → 준비/배포 보존 확인이다.

- `pnpm check`: 새 TS 모듈·항상 실행 fixture를 포함하고 기존 검사 범위를 줄이지 않는다. 실행/통과/실패/skip을 실제로 기록한다.
- `pnpm experiment`: 기존 비교4/4를 확인한다.
- 실제 제출 평가/교정 명령: baseline·새 참조·각 변형의 타입/동작/전체 판정을 새 날짜/버전 디렉터리에 저장한다. 원래 입력·참조 수정·제출·환경의 hash와 원문→실행 대응을 남긴다. 임시 복제/overlay만 쓰고 cache 변경이 없음을 확인한다.
- 새 교정 runner를 다른 출력 경로에서도 실행해 시간·실행 경로 등 명시적 변동 필드를 제외한 판정·진단·요청 내용·hash가 재현되는지 확인한다. 결과를 맞추기 위해 진단·실패 사례를 제외하지 않는다.
- `s2:prepare`를 새 두 출력 경로에 실행하고 비시간 파일/세 ID를 비교한다. 평가기만 변경했다면 기존 agent 제공 파일·모델/기준 ID가 그대로인지 확인한다. 공통 과업 설명을 수정했다면 변경된 TASK/배포 hash와 bundleId, 바뀌지 않아야 할 모델 의미/근거를 구분해 설명한다. evaluator metadata 변화와 agent 자료 변화도 별도로 대조한다.
- A/B/C allowlist와 source inventory를 확인하고 새 평가 코드/참조 패치/검증 자료가 제공 영역에 추가되지 않았는지 검사한다. OS 격리는 여전히 별도 미검증 상태다.

새 출력 위치는 `experiments/domain-model/s2/verification/<실제 완료일 또는 새 버전>/`를 사용한다. 같은 날짜의 기존 디렉터리가 있으면 새 suffix로 구분한다. 배포 자료가 바뀌면 `results/`에도 새 버전을 둔다. 재현 명령과 CLI 계약을 README에 실제 동작대로 갱신한다. 평가기/과업 명세 버전과 지문을 결과·run-plan에 남겨 같은 모델 bundle을 다른 평가기로 채점했는지 알 수 있게 한다.

제출 평가 비용은 baseline 환경 검사, 제출 타입 검사, 동작 평가로 나눠 wall time·Program 수·검사 범위를 기록한다. 준비 단계의 Program1회 계측과 섞지 않는다. 이번에는 숫자형 성능 목표나 FCA 최적화 목표를 새로 만들지 않는다.

## 6. 완료 조건과 인계

다음 모두 충족해야 **R8/R9/R10 보완 구현 완료·독립 재검토 대기**로 인계한다.

1. 실제 제출과 추가 helper가 원래 타입 문맥에서 검사되고, 구문/타입 오류 또는 검사 불완전 상태가 전체 합격이 되지 않는다. baseline 진단0, 새 참조 수정 진단0을 실제 Vendure에서 확인했다.
2. 새 참조 수정은 보존·가상 요구 전체를 통과하고, 환불만/혼합 경로의 환불 payload가 새 취소 정책 때문에 변하지 않는다. exact diff를 채점하지 않으며 유효한 helper 대안도 확인했다.
3. R9의 각 핵심 인자 변형과 R10의 범위 회귀를 **타입 검사 통과 후 동작 검사로** 거부했다. 원래6결함도 각각 의도한 검사에서 구별한다.
4. 상태·분모·diagnostic·기대/관찰값·소스/환경/평가기 지문이 있는 원시 결과와 재현 명령이 있다. 실패/미지원/미수행을 구분한다.
5. 새 fixture·전체 check·기존 비교·실제 교정 반복·준비 두 번 재현이 통과했고 원래 모델/배포 경계와 과거 증거가 보존됐다. cache 부재 등 미완료 항목을 숨기지 않는다.
6. 과업 실패 처리의 최종 승인, B/C 사람 의미 동등성, 실제 격리, agent 버전/도구/예산/배정/공개 테스트는 여전히 미정이며 `readyForTrial:false`다. H-O/H-F·사람 의미 승인·S3·본 비교 완료를 주장하지 않는다.
7. 완료 보고와 현재 문서, 검증된 커밋/PR 반영까지 마쳤다. 독립 reviewer의 해결 판정을 대신 기록하지 않는다.

`docs/reviews/<완료일>-s2-contract-fix.md`에 R8/R9/R10별 전후 결과, 변경 파일/명령, 제출 타입 검사 범위와 source binding, payload 기대 계약, 과업 적용 범위, 교정 행렬, 검사 수/skip, 재현/비용·미지원, 미정 사항을 작성한다. PROGRESS/ARCHITECTURE/ROADMAP/REVIEW_CONTEXT와 S2 README를 실제 상태로 갱신한다. 기존 합의 안의 중요한 구현 계약은 DECISIONS에 기록하되 미정 정책을 승인된 것처럼 올리지 않는다.

현재 범위에서 해결할 수 없는 원문 충실성/의존성 문제, 환불까지 정책을 넓혀야 한다는 판단, 새 기술 투자/설치 예산이 필요한 경우에는 근거·선택지·권고를 제시해 사용자 판단을 요청한다. 그 선택과 무관한 승인된 작업은 계속한다. 사소한 파일명/모듈 분리·테스트 배치는 자체 판단한다.

AGENTS/CONTRIBUTING의 지속 승인에 따라 검증 → staged diff 자체 검토 → Conventional Commit → 작업 브랜치 push → PR 생성·자체 검토 → 필수 검사/정확한 head 확인 후 merge → 로컬 main 동기화까지 진행한다. 보호 규칙을 우회하거나 별도 사람의 승인으로 표현하지 않는다. 최종 응답에 완료 보고서와 PR을 연결해 이 리뷰 세션에서 재검토할 수 있게 한다.
