# 개발 세션 지시 — corpus 평가 계약 보완

2026-11-07 [독립 리뷰](2026-11-07-corpus-independent-review.md) 후속. 현재 사용자 방향은 **업무 개념·관련 코드 탐색 우선**이다. 아래는 그 실험의 기반을 정리할 작은 정확성 작업 하나이며, 탐색 제품 기능을 한꺼번에 구현하라는 지시가 아니다.

## 작업 목표

corpus 자동 평가기의 `correct`가 원문 라벨의 주장과 일치하도록 하고, 선언 이름을 실제 사용으로 인정하는 오류를 막는다. 제품 코어의 분석 범위는 고정한다.

## 현재 상태와 근거

AGENTS, CONTRIBUTING, PROGRESS 및 위 독립 리뷰를 읽고 원격·브랜치·사용자 변경을 확인한다. 대상 구현은 PR #5/main `a58a88b2cd61e0cd2396656d4e12e2cac841a21d`이며 이후 리뷰 문서가 추가되어 있을 수 있다.

독립 재실행에서 89개 테스트, 인공 예제 비교 4개, 실제 corpus 비시간 산출물 14개의 byte 일치를 확인했다. raw 관찰은 correct 22/unsupported 2, predicate 지원 0, 사전 비교 0/2, p-queue 전체 FCA 상한 초과다. 하지만 다음 두 평가기 결함이 있다.

- **R4 / Medium:** `evaluate-labels.mjs:16–19`는 type/function의 이름·좌표, parameter의 이름만 검사한다. date-fns-10은 DateArg의 union을, p-queue-02는 배열 타입을 주장하지만 메모리상 fact의 타입을 각각 `never`/`number`로 바꿔도 correct다. 실제 원본 타입이 틀린 것은 아니며 “검사한 정보보다 강한 주장”의 문제다.
- **R5 / Medium:** 같은 파일/같은 시작 offset만으로 선언 reference를 제외한다(`:35`). `export function unused() { return true; }`의 이름 reference는 offset 16이고 target 선언은 offset 0이라 통과한다. 실제 본문 사용이 없어도 self-use 라벨이 correct다. 진짜 재귀 호출은 별도로 허용해야 한다.

재현 코드/JSON은 `docs/reviews/evidence/2026-11-07-corpus-evaluator-{check.mjs,results.json}`이다. 스크립트는 관찰 출력용이며 exit 0을 수정 완료로 해석하지 않는다. 현재 24개 라벨의 수치가 반드시 달라진다는 주장은 아니다.

## 구현 범위

1. 위 두 문제를 먼저 실패하는 회귀 검사로 만든다. actual scan에서 선언 이름의 evidence와 target 선언 evidence가 다른 fixture를 포함한다. 기존처럼 mock 좌표를 같게 만든 검사만으로 끝내지 않는다.
2. 모든 라벨의 claim과 기계적 기대 조건을 대조한다. 타입·종류·매개변수 타입 등을 판정하려면 원문에서 독립적으로 작성한 expected 값을 사용한다. 자동 검증이 어려운 내용은 claim을 실제 검사 가능한 범위로 좁히거나 별도 `unverified` 항목으로 분리한다. 정답을 scan/FCA 출력에서 복사하지 않는다.
3. reference 라벨에 사용 위치와 선언 대상의 별도 근거를 넣거나 원본 AST에서 declaration-name을 구분한다. 평가기 층에서 해결하는 것이 우선이다. `target.id === function.id`를 모두 제거하는 식으로 재귀 호출을 놓치지 않는다. 호출이라는 주장과 일반 참조라는 주장도 구분한다.
4. 역사적 `labels.json`의 주장/원시 판정·summary·gzip·개발 보고는 과거 실험으로 보존한다. 새 라벨/평가기 버전과 변경 사유를 새 결과에 연결하고, 이전 실험을 재현할 경로도 유지한다. 현재 라벨이 수정되어 비교 불가해졌는데 단순히 22/24를 전후 성능 차이로 보고하지 않는다.
5. 새 버전에서 같은 corpus를 실행하고 라벨별 전후 판정 및 검사 범위 변경을 설명한다. source/타입/조건 원문은 변경하지 않는다. 사람의 승인·검토 시간을 자동으로 채우지 않는다.

## 제외 범위

코어 지원 문법 확장, 클래스 모델링, FCA 알고리즘/상한/랭킹 변경, LLM/SMT/프레임워크 플러그인, UI, 자동 의미 승인, npm 배포는 제외한다. 이번 수정 결과만으로 Gate 2~4를 올리지 않는다.

## 완료 조건

- DateArg 타입과 array 매개변수 타입을 틀리게 바꾼 결과가 강한 원래 claim에 대해 correct로 유지되지 않는다. claim을 좁힌다면 타입 보존은 미검증임이 기계 결과와 검토표에 보인다.
- 사용하지 않는 함수의 선언 이름 및 매개변수 선언 자체를 use로 세지 않는다. 실제 재귀 호출·import 사용은 인정하며 동명 다른 선언은 혼동하지 않는다.
- 가능한 한 사용 위치와 target 위치를 함께 출력해 검토자가 두 근거를 재확인할 수 있다.
- source/target/use anchor, diagnostics 0, 실패·미지원·판정 보류 분리를 검증한다.
- 역사적 결과가 유지되고 새 결과에는 입력·평가기 버전/해시, 라벨 변경 사유, 재현 명령이 있다. 현재 단계의 자동 라벨 판정을 사람 승인으로 표시하지 않는다.
- `pnpm check`, `pnpm experiment`, 기존 실험 재현 및 새 버전 corpus 재현이 통과한다. 연구상 Unsupported/상한 초과를 검사 실패와 혼동하지 않는다.

## 검증 방법

최소 실패 재현 → 평가 계약 보완 → actual scan/변형 fact의 부정 검사 → 고정 corpus 전후 대조 순서로 수행한다. 정답 라벨이 틀린 경우와 도구 결과가 틀린 경우를 분리하고, 숫자보다 어떤 claim의 어느 부분을 검사했는지 보고한다.

## 문서화 및 인계

PROGRESS/실험 README에는 최신 평가 계약과 실행 방법, RESEARCH에는 기존 숫자와 새로운 해석의 차이를 기록한다. 중요 설계 선택은 DECISIONS에 이유를 남긴다. 과거 리뷰·raw evidence는 덮어쓰지 않는다. staged diff 확인 및 지속 승인된 PR/merge/main 동기화 절차를 따른다.

그 뒤 별도 제품 실험을 **실제 업무 애플리케이션의 한 개념에서 관련 코드·조건 근거를 찾는 과업**으로 준비한다. 현재 library 24개 라벨 확인은 측정 품질 검토이지 사용자 가치 입증이 아니다. 검색/LSP 및 동일 facts의 단순 그룹을 기준선으로 두고 FCA의 추가 가치·검토 부담을 비교한다. 대상·질문·정답 근거·참가자·학습 효과·시간 측정 절차를 실행 전에 정한다. 아직 그 실험의 구현이나 사람 결과를 완료했다고 쓰지 않는다.

사용자는 주요 기술적·철학적/방향성 판단이 필요하면 요청해 달라고 했다. 타깃 과업 변경이나 근거/사람 검토 원칙의 완화, 주요 기술 추가/제거가 필요해지면 구체적인 관찰·선택지·권고를 제시한다. 이미 승인된 방향의 작은 오류 수정과 검증·원격 반영은 반복 승인을 요구하지 않는다.
