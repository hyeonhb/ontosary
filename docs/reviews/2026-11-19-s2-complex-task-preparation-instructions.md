# S2 개발 지시 · Vendure 복합 수정 과업과 비교 기준 준비

**같은 실행 예산에서 변경 전 도메인 지식을 받은 agent가 소스만으로는 놓치기 쉬운 업무 조건까지 지켜 패치를 완성하는지, 그때 성공 한 건을 더 얻는 데 얼마가 드는지 비교할 수 있게 준비해 주세요.** 지난 파일럿에서는 A/B/C의 첫 패치가 모두 52개 검사를 통과했고 B와 C는 A보다 입력 토큰을 각각 71%, 83% 더 썼습니다. 이번 인계물은 난이도를 가늠한 예비 결과와, 리뷰 후 그대로 실행할 수 있는 평가 과업·입력·채점·비용 계약입니다. ### 업무 관계가 결과를 가르는 과업을 고릅니다

고정 Vendure revision에서 변경이 두 업무 경로 이상에 걸치거나, 한 경로의 수정이 다른 경로의 기존 동작을 깨뜨릴 수 있는 후보를 비교해 주세요. 예를 들어 부분 취소와 이전 환불 이력이 겹치는 주문, 취소 완료와 대화상자 닫기가 서로 다른 후속 화면 동작을 요구하는 상황을 조사할 수 있습니다. 두 예시의 정책은 아직 확정되지 않았습니다. 실제 소스와 변경 전 모델이 더 잘 뒷받침하는 다른 후보를 골라도 좋습니다.

후보마다 요청할 **새 동작**, 소스에서 확인할 수 있는 **기존 보존 조건**, B/C에서 그 판단에 도움이 될 **변경 전 개념·관계와 근거**를 연결해 주세요. A도 공통 소스만으로 합리적인 답을 낼 수 있어야 합니다. 참가자에게는 바뀔 업무 정책과 결과를 명시하고 구현 위치와 분기별 풀이를 스스로 판단할 여지를 둡니다. 모호한 업무 정책은 가정으로 표시하고, 정책 선택이 정오 판정을 바꾸면 리뷰에서 결정할 수 있게 남겨 주세요.

### 예비 과업에서 난이도를 교정합니다

권장 규모는 예비 1개와 독립된 평가 과업 2개입니다. 예비 입력을 보내기 전에 과업을 나누고 분리 이유를 기록해 주세요. 예비 과업의 이름이나 입력값만 바꿔 평가에 재사용하면 학습한 풀이가 그대로 통할 수 있습니다.

예비 과업에 한해 기존에 검증한 고정 입력·도구 없는 Codex 경로에서 **A 조건의 새 세션 한 번, 첫 응답 한 개**로 난이도를 관측합니다. 원본·참조·부분 수정 패치에 대한 외부 채점은 참가 호출 없이 반복할 수 있습니다. 예비 A가 성공하면 어떤 관계를 스스로 판단해야 했는지, 실패하면 업무 관계 누락·불충분한 소스·모호한 요구·패치 형식·평가기 한계 중 무엇을 근거로 설명할 수 있는지 기록합니다. 한 번의 성공이나 실패를 확률로 해석하거나 A가 실패할 때까지 재시도하지 않습니다. 관측 후에는 선정 기준을 다듬고 평가 과업을 동결합니다. 예비 B/C와 평가 과업 A/B/C의 참가 호출은 준비 결과 리뷰 뒤 별도 결정합니다.

### 동일하게 줄 입력과 독립 채점을 준비합니다

- A는 공개 요구·제약·공통 소스·제출 형식을 받습니다. B는 여기에 변경 전 구조화 도메인 뷰를, C는 같은 지식을 담은 서술 문서와 근거 부록을 받습니다. 공개 범위로 소스를 선정하고 숨긴 검사나 참조 패치로 파일을 골라 주지 않습니다. 평가자 자료·예비 응답·다른 세션 기록은 참가 입력과 분리합니다. [기존 고정 입력 환경](../../experiments/domain-model/s2/trial/fixed-input)
- 필요한 만큼 자료를 줄일 수 있습니다. 핵심 조건, 예외, 방향이 있는 관계, 코드 근거와 검토 상태가 B와 C에서 같은 의미인지 실제 문구와 소스를 대조해 주세요. 두 표현 중 한쪽에만 답을 암시하는 내용이 있는지도 확인합니다. 과업을 본 뒤 보조 자료에 새 정책이나 해설을 보태지 않습니다. 사람 판단이 남은 항목은 근거와 함께 리뷰에 올립니다.
- 기존 방식으로 새 전체 소스 복사본에 패치를 적용하고 외부에서 타입·요구 동작·보존 동작을 채점합니다. 새 업무의 채점 사례는 별도 버전으로 둡니다. 평가 과업별로 **원본이 변경 요구에서 실패하고, 참조 패치가 모두 통과하며, 그럴듯한 부분 수정 패치가 특정 보존 조건에서 실패하는지** 실제 관측으로 확인해 주세요. 평가기가 정답 패치의 코드 모양에 의존하거나 동등한 구현을 판별하기 어려운 범위는 명시합니다. [기존 평가 진입점](../../experiments/domain-model/s2/evaluation/run.ts)

### 평가 전에 성공과 비용의 단위를 확정합니다

| 비교 항목 | 준비 결과에서 동결할 기준 |
| --- | --- |
| 일차 결과 | 각 조건의 예정된 과업·반복 중 첫 패치가 적용되고 타입·변경 요구·보존 조건을 모두 통과한 건수와 분모. 각 과업에서 A/B/C의 성공 여부를 짝지어 제시합니다. A가 성공한 과업도 포함합니다. 검사 사례 수는 표본 수와 구분합니다. |
| 같은 기회 | 모델·추론 설정, 공통 원문, 독립 세션, 첫 제출, 과업별 반복 수와 실행 순서 배정 방식, 시간·토큰 예산의 수치와 초과 처리 규칙. 가장 긴 패킷에 출력 여유가 있는지 확인하고 보조 자료도 예산에 산입합니다. CLI에서 강제 가능한 상한과 사후 usage로만 판정할 수 있는 한도를 구분합니다. |
| 비용 | 실패를 포함한 모든 예정 시도의 실제 입력·출력 토큰과 경과 시간. 캐시와 추론 토큰은 usage 정의에 맞게 중복 없이 기록합니다. 사람의 모델 작성·의미 검토·유지 시간은 회당 사용량과 따로 표시하고 과거에 측정하지 않은 비용은 미상으로 둡니다. |
| 효과 해석 | A 대비 B, A 대비 C 각각의 전체 사용량 차이와 완전 성공 건수 차이를 냅니다. 추가 성공이 양수일 때만 두 차이의 비로 추가 성공 한 건당 비용을 제시합니다. 신뢰할 금액 환산 기준이 없으면 입력·출력 토큰 단위로 각각 보고합니다. B/C 간 표현 효과는 의미 대응이 확인된 범위에서 해석합니다. |

무응답·적용 실패와 실행 환경 또는 평가기 오류를 구분하고, 누락 usage를 0으로 처리하지 않습니다. 인프라 오류의 재채점·무효 처리와 비교 가능 여부를 결과를 보기 전에 정해 주세요. 반복 수와 예산 수치는 개발 세션이 과업 수, 실제 패킷 크기와 지난 사용량을 근거로 제안하고 동결본에 적습니다. 동결본에는 계획된 총 참가 호출 수와 조건별 예상 토큰 범위도 적어 리뷰에서 실행 비용을 판단할 수 있게 해 주세요. 이후 비교에서는 세 조건의 원응답을 봉인한 뒤 동일한 평가기로 채점하도록 계획합니다.

### 리뷰 인계와 완료 조건

후보 선택 이유, 예비 A 원응답과 판정 근거, 평가용 공개 입력과 비공개 채점 자료의 구분, 세 대조 패치의 관측, 비용·성공 판정 계약을 한 보고서에서 따라갈 수 있게 해 주세요. 기존 방식으로 소스 revision·패킷·평가기·실행 설정의 버전이나 지문을 남기고, 리뷰어가 참가 호출 없이 입력과 채점 결과를 재현할 명령을 제공합니다. 저장소 검사를 실행하고 PROGRESS에 예비와 평가 호출 수를 따로 기록합니다.

구현 방법과 작업 순서는 개발 세션이 정합니다. 적합한 과업이나 검증 가능한 보존 조건이 부족하면 어떤 후보가 왜 탈락했고 무엇을 결정해야 하는지 인계해 주세요. 새 실행 기반이나 인증 경로가 필요할 때도 같은 방식으로 논의합니다. **이번 작업은 준비 결과 PR을 독립 리뷰에 인계하면 종료합니다. 실제 비교의 시작은 그 리뷰 뒤에 결정합니다.**
