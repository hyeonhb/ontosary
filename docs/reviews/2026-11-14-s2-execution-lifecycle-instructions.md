# S2 준비물 재사용과 공통 실행 수명주기 개발 지시

2026-11-14 사용자 승인. 별도 개발 세션에서 이 문서의 구현·검증·정리·인계를 **새 3시간 회차 하나**로 수행한다. 이번 지시 작성은 실행 결과가 아니다.

## 작업 목표

검증된 공개 준비물을 재사용하고, 실패 경로도 같은 종료·삭제 절차를 거치게 하며, 정책과 실행 식별자의 비교 기준을 명시한다. 반복 준비 비용을 줄이고 다음 차단이 운영 코드의 결함인지 실제 실행 경계의 제약인지 구분할 수 있게 한다. 현재 Lima/VZ·containerd/nerdctl 경계와 기존 CLI·셸을 유지한다.

Ontosary의 최종 목표는 기존 프로젝트를 agent가 도메인을 이해하고 수정하기 좋은 프로젝트로 점진적으로 전환하도록 돕는 것이다. 이 작업은 S2에서 변경 전 도메인 모델의 수정 효용을 비교하기 위한 실험 운영 보완이다. 제품 아키텍처 확장이나 H-O/H-F 가설 검증 완료로 해석하지 않는다.

승인 범위는 공개 준비물 보관, 실험 내부 공통 실행 코드, 정책/식별자 비교, 작은 fixture와 조건부 원래/후보 대조다. **실제 자격 증명 전달·로그인/갱신·provider/모델 호출·본 비교는 결과를 리뷰한 뒤 결정한다.** 추가 권한·다른 실행 backend·상시 VM·API/proxy는 이번에 도입하지 않는다.

## 현재 상태와 기준

최초 작업 명령에서 UTC와 host monotonic을 기록한다. 읽기·계획·구현·대기·실패·검증·정리·보고를 모두 회차 비용에 포함한다. AGENTS, PROGRESS, ARCHITECTURE, ROADMAP, CONTRIBUTING을 읽고 원격·브랜치·사용자 변경을 확인한다. 구현 기준은 main `f621521`(PR #52)이며 실제 시작 head와 그 사이 변경을 기록한다. 지시/맥락 문서만 추가된 차이와 구현 변경을 구분한다.

[직전 보고](2026-11-12-s2-policy-retry.md), [정책 후보](2026-11-11-s2-namespace-policy-proposal.md), [lifecycle 계약](../../experiments/domain-model/s2/trial/container/lifecycle/README.md), [정책 시험 도구](../../experiments/domain-model/s2/trial/container/single-policy-test/README.md)를 읽는다. 과거 보고·원시 증거·scope/index는 수정하지 않는다.

- snapshot의 명시적 closing 등록/원자 포장과 공통 환경 deadline 전달 보완은 독립 검증됐다. pnpm check 304, Python 44(새 31+기존 13), 새 증거 60파일/16archive·분석 8/closing 4 재현과 기존 입력 불변을 확인했다. 이번 구현은 이 보완을 재사용한다.
- 원래 정책에서는 namespace clone EPERM을 재현했다. 후보의 생성된 seccomp는 승인한 한 행만 달랐지만, hook 환경의 `MEMORY_PRESSURE_WATCH` 감독자 경로 차이로 시작 전에 거부됐다. 후보 시작/커널 적용은 0회이며 정책 효과는 미확인이다.
- 독립 종료 처리는 실패 후보를 0.275초에 stopped-confirmed로 확인했다. 그러나 `retry-guest.py`의 사전 검사 실패가 정상 수집 경로의 container 삭제를 건너뛰어 삭제가 181.412초에 이뤄졌다. 이는 단위 120초 계약 위반이다. 당시 모든 소유 자원은 최종 정리됐다.
- 공개 Ubuntu/nerdctl 다운로드 약 1.21GB를 이전 계약에 따라 다시 삭제했다. 이번에는 검증된 불변 준비물 보관을 승인한다. 이전 실제 실행 상태의 재사용 승인은 아니다.

지시 작성 시 별도 실행한 `pnpm check`는 타입 검사 통과·300테스트 통과/4실패였다. 기존 `tests/domain-model-v2.test.ts`가 참조하는 `/tmp/ontosary-vendure-preparation-20261108/vendure` 디렉터리는 남아 있지만 `package-lock.json`과 대상 소스가 누락됐다. 제품/테스트/실험 코드는 기준과 동일하며, 예제 build는 별도 통과했다. 개발 시작 시 이 환경 상태를 확인하고 새 변경의 실패와 구분한다. 통과로 보고하거나 테스트를 생략하도록 바꾸지 않는다. 기존 cache를 임의 복구/변경하거나 이 문제 해결을 이유로 3시간을 늘리지 말고, 필요한 복구 범위가 이번 예산을 넘으면 검증 미완료로 인계한다.

이번 회차 내내 R11 unresolved, R12 기존 검증 범위, production/live 거부, `fixtureOnly=true`, `validSubmission=false`, `trialAuthorized=false`, `readyForTrial=false`, `results=null`을 유지한다.

## 구현 순서와 책임

### 1. 실행 계획과 재사용 경계를 먼저 고정한다

최초 계획에 변경 파일 범위, 준비물 목록과 예상 크기, 고정 버전/입력, 허용 동적 식별자, fixture 순서와 수, 명령별 제한, snapshot 분석/closing 범위, 정리 소유권을 기록한다. 실험 도구의 작은 함수/모듈 세 책임으로 구성한다. 파일명은 기존 구조에 맞게 선택하되 범용 플러그인/여러 backend 추상화는 만들지 않는다.

| 책임 | 입력과 산출물 | 소유 범위 |
| --- | --- | --- |
| 준비물 관리 | 고정 manifest → 검증된 공개 파일/이미지 아카이브 | 회차 간 보관 가능한 불변 데이터 |
| 실행 수명주기 | 실행 계획 → 종료·삭제 확인 및 제한된 수집 기록 | 실행별 container/cgroup/경로/마감 |
| 정책 비교 | 실제 Spec+입력+소유권 기록 → 검증된 전체 diff | 고정 정책과 검증된 식별자 대응 |

기존 deadline/snapshot/scope/package, 소유 cgroup 종료 확인과 collector를 재사용한다. `retry-job.py`·`retry-guest.py`·`retry-install.py`·`retry-remove.py`·`retry-export.py`의 중복 책임을 정리하고 단일 정책 시험을 공통 경로에 연결한다. 공유 lifecycle 변경은 허용하되 영향을 받는 기존 caller의 호환성 또는 명시적 adapter와 회귀를 마련한다. 과거 실행 도구 전체를 일괄 이식하지 않는다.

### 2. 검증된 준비물을 보관한다

준비물 저장소, 회차 VM, 개별 실행 상태의 수명을 분리한다. 고정 공개 VM 이미지/도구 압축 파일과 검증된 컨테이너 이미지 아카이브만 회차 간 보관한다. VM은 회차마다 새로 만들고, 각 실행의 source/output/HOME/CLI 상태/scratch는 새로 만든다. 준비물에서 작업 결과·세션·인증 정보·실행했던 writable layer를 복원하지 않는다.

manifest에는 출처 URL, SHA-256, 바이트 크기, 버전, 플랫폼/아키텍처, 이미지 식별자와 빌드 입력 hash를 둔다. digest로 파일을 찾되 캐시 적중 판정은 요청한 입력 manifest의 일치도 요구한다. 동일 tag/파일명이 같은 내용이라는 가정은 금지한다. 빌드 결과는 도구/기반 이미지/레시피/설정 입력이 달라지면 재사용하지 않는다.

호스트 관리자만 쓰는 전용 저장소에서 잠금 → 임시 파일 → 실제 바이트 검증 → 원자 등록 순서를 사용한다. 부분 다운로드·동일 이름의 다른 내용·손상 파일·예상 밖 symlink는 거부한다. 재사용 전 실제 파일 SHA-256을 확인하고 재사용 중 worker 쓰기를 허용하지 않는다. hash와 manifest가 실패한 파일을 조용히 정상 cache로 재등록하지 않는다.

[Lima v2.3.0 downloader](https://github.com/lima-vm/lima/blob/v2.3.0/pkg/downloader/downloader.go)는 기존 target이나 cache digest metadata 경로에서 실제 data hash를 재계산하지 않을 수 있다. `cache hit` 출력만 신뢰하지 말고 이번 관리 계층이 바이트를 검증한다. 이미지 아카이브 import 뒤에도 실제 manifest/config/rootfs chain과 실행 이미지·바이너리 identity를 확인한다.

고정 버전 한 세트, **전용 보관량 10GiB**를 상한으로 한다. 등록 파일과 진행 중 임시 파일을 합산하고 초과 예상 시 새 확보를 중단한다. 자동 LRU/일반 artifact 서버는 구현하지 않는다. 기존 사용자 cache는 변경/삭제하지 않는다. 정상 회차 정리는 보관 대상으로 검증·등록한 준비물을 삭제하지 않으며, 임시·거부된 신규 파일은 소유권을 확인해 정리한다. manifest/검증 기록만 Git에 넣고 대형 바이너리는 넣지 않는다.

최초 재확보 후 같은 준비물을 두 번째 사용할 때 다운로드/빌드가 다시 발생하지 않는지 기록한다. 작은 로컬 fixture로 누락·버전 변경·손상·부분 파일·등록 실패를 먼저 검증한다. 실제 대형 파일을 일부러 손상하거나 동일 VM을 재생성해 cache 검증 비용을 늘리지 않는다.

### 3. 모든 종료 원인을 공통 수명주기에 연결한다

하나의 관리자 소유 실행 기록에 run ID, 시작 시각/절대 마감, 소유 디렉터리, service/slice/cgroup 경로와 inode, container 이름/ID, 이미지, 진행 중 create/start/exec 요청, outcome과 정리/수집 상태를 담는다. 원자적 기록과 기존 lock을 재사용한다. 소유권과 요청 예정 상태를 자원 생성 전에 기록해 응답 유실·부분 생성도 식별한다. PID 종료나 container ID 미수신만으로 생성 부재를 추정하지 않는다.

정상 종료·사전 검사 거부·시작 실패·timeout·wrapper 사망·감독자 사망은 모두 다음 공통 경로로 보낸다.

1. 다음 실행과 추가 start/exec 요청을 차단한다.
2. 소유 cgroup의 전체 종료와 runtime 요청 정착 여부를 확인한다. pending이 불명확하면 빈 cgroup만으로 완료 판정하지 않는다.
3. task/container를 제거하고 실제 부재를 재확인한다. 외부 runtime 오류를 무조건 “이미 없음”으로 취급하지 않는다.
4. 종료·부재·소유권이 확인된 경우에만 기존 제한된 collector로 작업 결과를 수집한다. 조회/삭제 실패 시 관리자 진단만 보존하며 유효 결과 공개와 다음 실행을 차단한다.
5. 종료 기록을 확정하고 소유 service/slice/임시 자원을 정리한다. 정상 수집 후 다음 실행을 열기 전 선행 실행의 정리 상태를 확인한다.

정지와 삭제의 최종 책임은 독립 감독자/종료 후 처리에 둔다. 호스트 wrapper의 `try/finally`는 보조 요청 경로이며 유일한 정리 주체가 아니다. 호스트가 사라져도 게스트가 마감과 소유 기록을 가지고 종료·삭제를 마칠 수 있어야 한다. 감독자는 worker cgroup 밖에 유지한다. 중복 cleanup·늦은 응답·관찰자 재접속에도 다른 실행 자원을 제거하거나 결과를 두 번 공개하지 않는다.

`outcome`, `terminationConfirmed`, `removalConfirmed`, `collectionStatus`를 구분한다. 과업 실패/정리 완료와 종료 여부 불명은 다른 상태다. 감독자 사망·collector 실패 등 기존에 결과를 거부하던 경로를 성공으로 완화하지 않는다. 차단 후에는 확인된 안전 복구 절차만 다음 실행을 열 수 있다. 소유권/요청 정착을 확인하지 못하면 회차를 차단하고 VM을 폐기한다. VM 폐기를 해당 단위의 정상 종료 증거로 대체하지 않는다.

이번 작은 fixture의 **실행 등록부터 정리·제한된 수집까지 외부 120초**를 유지한다. 준비/생성/검사/실행은 처음 80초 이내, 종료·삭제는 110초까지, 수집·기록/단위 정리는 120초까지 끝내도록 설계한다. 작업 자체 payload는 기존 최대 15초다. 조기 실패는 즉시 종료 단계로 들어가고, 실패 시 전체 120초를 다시 시작하지 않는다. 기존 RuntimeMaxSec=95 같은 값과 개별 timeout을 그대로 합산하지 말고 이 마감 안에 종료 후 처리 여유가 실제 남도록 맞춘다. 미래 agent 과업의 실행 제한은 변경하지 않는다.

호스트와 게스트 monotonic은 직접 비교하지 않는다. 호스트 외부 마감과 게스트 독립 감독자의 제한을 각각 연결하고 전송/등록 지연을 포함한다. lifecycle의 lock 대기·runtime query·삭제·수집도 유한 제한을 가져야 한다. 장시간 실시간 대기 대신 fake clock/짧은 subprocess로 중첩 마감과 reserve를 검증한다.

### 4. 정책 불변성과 검증된 식별자 대응을 분리한다

`runtime_policy.py`의 전체 Spec 비교를 유지한다. 보안 필드 일부만 추출해 나머지 차이를 무시하는 방식으로 바꾸지 않는다. 원본 Spec → 소유 관계 검증 → 사전 지정 위치의 값 치환 → 전체 비교 순서를 사용한다.

| 종류 | 비교 계약 |
| --- | --- |
| 보안 정책 | seccomp default/architecture/전체 규칙, AppArmor, UID/GID, capability, NNP, namespace, mount 권한, network, 자원 제한 보존 |
| 실험 입력 | 같은 이미지/바이너리·trace·설정·합성 자료·명령을 hash/실제 identity로 확인 |
| 실행 식별자 | container ID/hostname, 소유 mount source, cgroup/service/상태 경로 등이 자신의 실행 기록과 정확히 일치할 때만 역할 이름으로 치환 |
| 미분류 차이 | 전체 diff에 남기고 시작 거부. 실행 후 예외를 추가하거나 재시도하지 않음 |

runtime 명령에 전달할 환경을 최소한의 명시적 목록으로 구성한다. systemd 감독자의 환경을 worker/runtime hook으로 무조건 상속하지 않는다. 이 변경은 원래/후보 양쪽에 동일하게 적용하며 기존 보안 정책과의 대조 근거도 남긴다. 필요 환경을 제거해 기능을 바꿨다면 그 결과를 숨기지 않는다.

남아 있는 동적 값은 이름/정규식만으로 지우지 않는다. `MEMORY_PRESSURE_WATCH`는 자기 감독자 cgroup의 실제 경로인지 확인한 뒤에만 치환할 수 있다. [systemd 문서](https://github.com/systemd/systemd/blob/v260/man/systemd.exec.xml)의 해당 항목은 서비스의 압력 감시 경로다. 현재 이름만으로 치환하는 `INVOCATION_ID`, `JOURNAL_STREAM`, `SYSTEMD_EXEC_PID`도 전달 필요성과 관리자 기록을 통한 검증 방법을 정한다. 검증할 수 없는 값은 제거가 실제 허용되는 환경 구성인지 확인하거나 차단 상태로 남긴다.

현재 회차의 실제 원래/후보 Spec을 저장 fixture로 사용한다. 과거 원문을 고치지 말고 새 기대 대응과 근거를 별도 저장한다. 다른 run의 경로, 소유 밖 경로, 중복 환경 키/충돌, 추가 hook/명령/권한/mount와 seccomp 차이를 거부한다. 치환은 사전에 지정한 JSON 위치에만 적용하고 mount/hook 순서 등 의미 있는 차이를 정렬로 숨기지 않는다. 배열을 정규화한다면 중복·순서 의미 보존 근거와 부정 테스트를 둔다.

원본 두 Spec, 실행별 identity 기록, 치환 위치/원값/검증 근거, 치환 후 전체 diff를 남긴다. 후보에 허용되는 정책 차이는 아래 한 행뿐이다.

```json
{"names":["clone"],"action":"SCMP_ACT_ALLOW","args":[{"index":0,"op":"SCMP_CMP_EQ","value":2013397009}]}
```

## 검증 순서와 실제 실행 범위

### 로컬 계약 검증

준비물의 hit/miss·손상/부분 파일·버전 불일치·원자 등록과 읽기 경계, 실제 두 Spec의 정상 대응/위조 부정 사례, 모든 종료 분기의 상태 전이·중복 호출·진행 중 요청·조회/삭제 실패·마감 차감을 검증한다. CLI의 실제 진입점과 결과 공개/다음 실행 차단도 확인한다. 내부 함수의 반환값만 검사해 통합 성공으로 표시하지 않는다.

snapshot 생성 시 정확한 command/args/phase 등록, 미등록/위조 거부, 분석 동결 후 runtime 차단과 원자 포장 회귀를 유지한다. 로컬 필수 회귀가 통과하기 전 VM을 시작하지 않는다. 신규 동작에 필요한 표준 라이브러리 수준의 작은 코드와 테스트를 우선한다.

### 실제 작은 fixture

하나의 새 VM에서 기본 정책으로 다음 **필수 7단위**를 사전 계획한다. 동일 불변 준비물을 재사용하되 실행별 writable 상태는 공유하지 않는다.

| 단위 | 확인할 사실 |
| --- | --- |
| 정상 종료 1 | 허용 읽기/쓰기 양성, 종료→삭제→수집 순서와 120초 이내 완료 |
| 생성 후 사전 검사 실패 | 작업 시작 0회여도 자동 삭제까지 진행, 실패/정리 상태 분리 |
| 시작 실패 | 생성 자원 잔여와 pending을 확인하고 자동 정리, 불확실하면 차단 |
| timeout | 분리된 자손 포함 전체 종료, 늦은 쓰기 없음, 제한된 진단 처리 |
| 호스트 wrapper 사망 | 호스트 수동 정리에 기대지 않고 게스트 감독자가 종료·삭제 완료 |
| 작업 감독자 사망 | 독립 종료 후 처리로 정리, 결과 공개/다음 실행 차단 및 명시적 복구 |
| 정상 종료 2 | 안전 복구 뒤 새 실행, 이전 파일/HOME/CLI 상태/scratch 접근 불가, 같은 준비물 재사용 |

timeout/사망은 준비 완료 신호에 맞춰 주입하고 단순 sleep 추측으로 대신하지 않는다. 종료 요청/확인, 마지막 쓰기, task/container 부재, pending, 수집 시작/완료 시각을 각각 기록한다. worker에서 준비물/제어 경로/이전 실행 canary를 읽거나 쓸 수 없는지와 자기 입력 양성 대조를 함께 확인한다. 순서는 실제 복구 계약에 맞게 계획하되 실패 결과를 성공으로 바꾸어 다음 단위로 넘어가지 않는다.

조회/삭제 실패 시 차단은 로컬 필수 검증이다. **실제 주입은 선택적인 8번째 fixture**로, 최초 계획에 포함하고 모든 다른 runtime 관찰 뒤 마지막에만 수행한다. VM 폐기가 필요하면 그 후 정책 대조나 새 fixture를 시작하지 않는다. 이 선택 검증을 수행하지 않았으면 미실행으로 기록하고 실제 종료/삭제 실패 복구까지 입증했다고 주장하지 않는다.

### 조건부 원래 정책과 후보 정책 대조

필수 로컬 검증과 실제 7단위의 기대 결과/정리 확인을 통과하고 예산이 남을 때만 **원래 1회·후보 1회**를 진행한다. 이 조건부 대조까지 이번 승인 범위이며 자격 증명이나 모델은 사용하지 않는다. optional 8번째 파괴적 fixture보다 앞에 배치한다.

같은 고정 CLI `0.167.0-alpha.3.2`, Node `22.19.0`, trace/합성 입력·명령과 이미지 identity를 사용한다. 원래 정책에서 parent 양성 동작 및 첫 clone `0x78020011` EPERM을 확인한다. 기준/보안 정책/이미지가 예상과 다르면 후보를 시작하지 않는다. 후보 전용 관리자 profile에 한 행만 추가하고 실제 생성된 Spec 전체를 새 비교기로 확인한 뒤 시작한다.

clone 직접 반환값·자식 관계·다음 실패를 기록하고 내부 사전 점검과 실제 명령 준비를 구분한다. 후보 시작은 최대 1회다. 다음 syscall/mount/LSM 차단에서 추가 trace 실행·정책 수정·후보 재시작 없이 종료한다. created Spec 할당, 실제 시작, 커널에서의 clone 관찰을 별개로 센다. payload 성공도 전체 CLI/인증/네트워크 경계 검증으로 확대하지 않는다.

worker network none, UID/GID1000, capability0, NNP1, RO root/cgroup, CPU2, 메모리4GiB, PID256, tmp64MiB, 기존 AppArmor와 mount 접근 제한을 유지한다. 준비용 공개 다운로드와 worker 네트워크를 구분한다. host home·키체인·runtime socket·실제 인증·전체 사용자 config/env를 제공하거나 조사하지 않는다.

## 비용 상한과 중단 기준

최초 시계부터 **180분**, 신규 유료 비용0, 새 VM 최대1개, 실제 fixture 최대8단위+정책 대조 최대2단위다. 생성/시작 요청이 실패한 시도도 실행 수에 포함한다. 숨은 smoke container를 별도로 추가하지 않는다. 준비 이미지의 build 단계는 작업 단위와 구분해 계획/기록하고 마감에 포함한다. 허용 수는 목표 반복 횟수가 아니다.

| 최초 시작부터 | 통과 조건 또는 중단 동작 |
| --- | --- |
| 60분 | 세 책임의 구현·필수 로컬 회귀·실행 계획 준비. 미충족이면 VM 착수 포기, 부분 결과 인계 |
| 100분 | 준비물 검증과 VM/런타임·같은 이미지/입력 준비. 미충족이면 새 준비·실행 중단 |
| 150분 | 실제 fixture·조건부 대조 관찰 종료. 이후 새 runtime 실행·수정·탐색 금지 |
| 180분 | 검증·소유 자원 정리·증거 포장·보고 완료 |

환경 준비 진입 시 최초 1회만 하위 마감을 `min(진입 시각+20분, 회차 시작+100분)`으로 고정한다. 이는 직전 회차의 “최초20분”을 이번 긴 구현 회차에 맞춰 명시적으로 바꾼 계약이다. 다운로드·해제·부팅·이미지 준비는 모두 같은 잔여를 사용하며 재시작하지 않는다. 호스트 UTC/monotonic 중 더 이른 잔여를 사용하고 snapshot·명령 준비 시간도 차감한다. 150분 이전이라도 새 단위 120초를 확보하지 못하면 시작하지 않는다. 마지막 30분은 검증·정리·보고용으로 남긴다.

로컬 테스트 수정/재실행은 마감 내 허용한다. 실제 단위 실패 뒤 구현을 바꾸어 같은 단위를 자동 재시도하지 않는다. 생성 전 명령 조립 오류의 국소 수정은 증거와 동일 계획 유지가 확인될 때 총1회까지 허용하되, 추가 VM/실행 수·마감은 늘리지 않는다. 보안/identity/정리 계약의 변경은 기계적인 오타 수정으로 취급하지 않는다.

다음 경우 새 실행을 중단하고 근거 있는 부분 결과를 남긴다: 필수 회귀 실패, 구현이 전면 재작성으로 확대, hash/버전/입력 불일치, 준비물10GiB 초과, 미분류 Spec 차이, 추가 권한 필요, 예상 밖 접근, 소유권/종료/삭제/요청 정착 확인 불가, 시간/횟수 상한 도달. 손상된 준비물을 거부하는 테스트의 예상 실패와 실제 운영 입력의 무결성 실패를 구분한다.

마감은 정리를 포기할 이유가 아니다. 새 실험은 멈추고 소유 자원에 한해 안전 정리를 계속하며, 불가피한 초과 시간과 남은 복구 항목을 별도 보고한다. 기준 누적 측정 `14280.296826292초`와 기존 직렬화 보수 상한 합계10초를 유지하고 새 실측/직렬화 상한/누적을 구분한다. Git 게시·PR·merge 시간은 실험 회차 뒤 별도로 기록하며, 그 시간을 실험 재개에 사용하지 않는다.

## 완료 조건과 판정

**구현 완료**는 준비물 재사용·실패 공통 종료·정책/identity 비교가 연결되고 필수 로컬/실제 검증이 통과한 경우다. 코드만 작성했거나 실제 실패 경로를 확인하지 못하면 부분 완료다. **회차 종료**는 정책 성공 여부와 별개로 상한 내 관찰 또는 근거 있는 중단, 정리 상태, 검증·비용·인계를 남긴 경우다. 두 판정을 혼동하지 않는다.

- 준비물의 실제 hash·입력 일치와 두 번째 사용의 다운로드/빌드 생략을 확인한다. 실행 상태는 새로 만들고 격리 증거를 남긴다.
- 필수 7단위가 기대한 결과와 정리 계약을 만족한다. 사전 검사 실패도 120초 내 삭제로 이어지고 wrapper/감독자 사망에도 호스트 수동 작업 없이 처리된다. 실행 실패를 과업 성공으로 표현하지 않는다.
- 검증된 자기 실행 식별자만 치환하고 실제 두 Spec 및 부정 변형을 검증한다. 정책 한 행 외 차이가 있으면 start를 거부한다.
- 정책 관찰은 `synthetic-payload-completed`, `first-clone-passed-next-blocked`, `clone-still-denied`, `inconclusive`로 구분하고, 미실행은 그 이유를 기록한다. 다음 차단이 있어도 운영 보완이 검증됐다면 이를 별도 성과로 보고한다.
- `pnpm check`, 영향받은 lifecycle/collector/cleanup·production/live 거부, snapshot/deadline/package와 정책/준비물 회귀, 저장 증거 재검증, 문서 링크/변경 범위 확인을 마친다. 테스트 수는 중복 import로 부풀리지 않는다. TS/평가 의미를 바꾸지 않았으면 Vendure7·pnpm experiment 전체 반복은 하지 않고 이유를 적는다. 영향이 생겼다면 필요한 회귀를 예산 내 수행하거나 미검증으로 인계한다.
- 과거 증거와 제품/모델/B/C/평가기/배포 ID 입력은 최초 inventory와 대조해 불변성을 확인한다. 의도한 도구 변경과 불변 대상을 분리해 hash 차이를 설명한다.

## 문서화와 인계

새 보고서는 `docs/reviews/2026-11-14-s2-execution-lifecycle.md`, 증거는 `experiments/domain-model/s2/verification/2026-11-14-execution-lifecycle/`에 저장한다. 실제 실행 날짜가 다르면 맞추고 기존 경로에는 덮어쓰지 않는다. 준비물 실제 경로·용량·관리 소유자·보관/폐기 방법과 실행 명령을 실험 README에 남긴다.

보고서에는 세 책임의 변경/재사용 경계, cache 최초 확보/재사용 비용과 파일 목록, 계획 대비 실제 분모, 각 실패 원인/정리 결과/시각, 원본 Spec과 검증된 치환 diff, 최초 입력·현재 실행 코드 hash, 정확한 snapshot 범위와 최종 index, 테스트/미실행 항목, 자원 잔여와 비용을 포함한다. 로그/수집은 기존 용량·파일 종류 제한을 유지하고 민감 데이터는 포함하지 않는다.

분석 동결 후 새 runtime 실행은 금지한다. 생성 시 명시적으로 등록한 closing만 최종 포장에 포함하고 전체 파일/archive 내부를 검증한다. 보관 준비물은 최종 정리 보고에서 의도적 보관으로 분리하며 소유 VM·container/task·cgroup·service·profile·임시 파일 잔여와 혼동하지 않는다.

PROGRESS·ARCHITECTURE·ROADMAP·reviews/REVIEW_CONTEXT와 필요한 DECISIONS를 실제 결과로 갱신한다. CONTRIBUTING에 따라 검증·staged diff 검토·커밋·push·PR 검토·필수 검사 충족·검증한 head 병합·로컬 main 동기화까지 수행한다. 독립 리뷰를 받지 않은 결과는 개발 인계로 표시한다.
