# 다음 개발 지시 — Vendure 도메인 모델의 첫 연결 실험

작성: 2026-11-08. **다음 구현 범위 S1의 지시이며, 구현 완료나 업무 의미 승인 기록이 아니다.** 별도 개발 세션에서 이 문서만 전달받아도 시작할 수 있도록 작성했다. 현재 제품 상태는 [PROGRESS](../PROGRESS.md), 이번 근거는 [Vendure 준비 독립 리뷰](2026-11-08-vendure-preparation-independent-review.md), 방향 결정은 ADR-020이다.

## 작업 목표

Ontosary의 최종 목표는 기존 프론트엔드 프로젝트를 **AI agent가 도메인을 이해하고 수정하기 좋은 프로젝트로 점진적으로 전환하도록 돕는 것**이다. 코드에 드러난 사실과 개발자가 확인한 개념·관계·규칙을 연결한 도메인 모델이 그 수단이고, FCA는 모델 구축 비용을 낮추기 위한 후보 발견 수단이다. 코드 탐색은 이 목표의 첫 사용 경로다. 사람 친화적인 코드가 agent에게 불리하다는 전제, OWL/RDF 채택이나 전면 재작성은 필요하지 않다.

이번 한 작업(S1)은 **Vendure 주문 취소·환불의 작은 도메인 모델 초안, 근거 검증기, FCA의 기여를 추적할 대조 자료**를 만든다. 다음 변경 과업 실험에서 agent에게 제공할 수 있어야 한다. 모델의 업무 의미를 자동 승인하거나 agent 성능 향상을 이번 결과로 주장하지 않는다.

단기 진행 순서는 다음과 같다. 이번에는 S1만 구현한다.

## 구현 범위

### 1. 새 실험 입력과 작은 도메인 모델

`experiments/domain-model/v1/`에 독립적인 실험을 만들고, 날짜별 결과·원문 고지·재실행 명령을 둔다. 고정 revision, 대상 파일/심볼, 입력 hash, 분석/수동 작성 방법, 도구 버전, 범위 밖 항목을 manifest에 기록한다. 기존 설치 cache는 읽기 전용으로 재사용하되 원문·설정 hash를 검증한다. 사라졌다면 기존 고정 archive와 저장 facts로 진행 가능한 부분을 분리하고 생략된 live 검증을 명시한다. 종료된 30분 준비 예산을 다시 열거나 의존성 설치 투자를 확대하지 않는다.

표현은 작은 JSON과 읽기 쉬운 Markdown으로 충분하다. 범용 온톨로지 엔진보다 이번 사례에서 필요한 계약을 먼저 만든다. 최소한 다음 정보를 표현한다.

- **코드 사실:** 소스 심볼/위치/anchor/hash, 관찰 내용, 추출 방법(기존 scanner/추가 AST 관찰/수동 원문 확인), 진단·지원 상태·적용 범위. 수동 작성도 agent 작성인지 사람 작성인지 구분한다.
- **모델 초안:** 주문·주문 항목·결제·취소 요청·환불 요청 같은 개념 이름, 관계와 규칙의 후보, 각 항목의 fact 참조·FCA 후보 참조·해석 근거·미확인 사항. 모두 검토 대기에서 시작한다. 관계 이름과 ID는 실험용이며 최종 아키텍처가 아니다.
- **승인된 지식:** 실제 사람의 결정 기록이 있는 경우만 별도로 표현한다. 검증기 통과·agent의 재검토·사용자의 연구 방향 동의를 업무 의미 승인으로 세지 않는다. 없으면 빈 목록이다.

코드에서 현재 관찰한 동작과 사람이 의도한 업무 정책을 별도 필드/종류로 구분한다. `observed-in-source`는 정적 원문 관찰이며 런타임 보장이 아니다. 도메인 후보가 어떤 사실에 기대고 있는지와 어떤 추가 질문이 남는지 보여준다. 예를 들어 “이 경로는 취소 service 호출을 포함한다”는 관찰과 “이 둘은 같은 취소 업무의 변형이다”라는 해석을 하나로 합치지 않는다.

ID는 revision에 묶인 것으로 시작해도 된다. 편집 후 안정적인 ID, 모든 영향 범위 탐색, 테스트 coverage를 이미 해결한 것처럼 표시하지 않는다. 코드와 모델이 충돌하거나 근거가 만료되면 agent가 원문을 다시 확인해야 한다는 사용 계약을 포함한다.

### 2. FCA용 범위를 의미 있는 질문으로 고정

질문은 **“취소·환불의 요청 준비와 호출에 참여하는 메서드들이 어떤 관찰 속성을 공유하는가?”**다. import closure는 타입/심볼 해석에 유지하고, FCA 객체 범위는 별도의 파생 실험으로 명시한다. core의 `buildContext`나 CLI 범위 계약을 바꾸지 않는다.

초기 객체 선택은 `OrderDetailComponent`, `CancelOrderDialogComponent`, `RefundOrderDialogComponent`, `OrderDataService` 네 클래스의 **이름 있는 메서드 전체**다. 취소와 무관한 메서드·대화상자 닫기도 포함해 과도한 그룹을 관찰한다. 생성자·접근자·필드 초기화·익명 callback·HTML·GraphQL을 객체로 포함하는지/제외하는지를 실행 전에 명시한다. 이 정의를 바꿔야 하면 이유와 새 버전을 남긴다. 원하는 그룹이나 상한 통과를 위해 사후에 메서드를 골라내지 않는다.

속성도 결과를 보기 전에 적은 수의 **원문에서 판별 가능한 역할**로 고정한다. 예: 정확한 취소/환불 service 메서드에 해소되는 호출식의 존재, modal 열기, 취소 입력 객체 구성/전달. `is-cancellable` 같은 업무 정답을 속성으로 미리 넣지 않는다. 속성마다 긍정·부정 판정 기준과 근거 위치를 남긴다. symbol identity와 AST 역할을 구분해 같은 이름의 다른 메서드를 합치지 않는다.

중첩 callback의 호출식을 소속 메서드의 속성으로 집계한다면 “이 메서드의 원문 영역에 해당 호출식이 있다”는 별도 관찰 계약으로 정의한다. 실제 호출·도달 가능성·전체 호출 그래프를 계산했다고 하지 않는다. 기존 core의 중첩 함수 facts와 같은 객체라고 표시하지 않는다. 추가 관찰기는 이 실험 안에 두고 TypeScript Compiler API를 재사용한다. 의미 해석이 필요한 속성은 수동 주석으로 둘 수 있지만 작성 비용·검증 범위와 자동화 비율을 드러낸다.

미확인 속성을 false로 입력하지 않는다. 각 셀은 yes/no/unknown과 근거/판정 방법을 먼저 갖고, 모든 셀의 이진 해석이 정해진 context에만 FCA를 적용한다. unknown이 남거나 상한을 넘으면 그 상태를 보고하고 실행을 중단한다. 결과를 맞추기 위한 자동 축소·상한 증가를 하지 않는다. 모델 초안·실패 관찰은 유효한 완료물로 남길 수 있다.

### 3. 같은 사실에서 단순 그룹과 FCA를 대조

먼저 FCA 없이 소스/facts에서 작성한 모델 초안을 보존한다. 그 뒤 **완전히 같은 객체·속성·incidence**에서 속성별 단순 그룹과 기존 FCA를 실행해 raw context, formal concepts, 후보, 관계, 상한/잘림을 저장한다. 단순 그룹에도 공유 속성·근거를 제공해 표시 정보의 차이를 계산 효과로 오인하지 않게 한다.

각 FCA 후보에 대해 단순 그룹과 extent가 같은지, 추가 교집합인지, 지나치게 넓은지, 업무 해석을 보류하는지 기록한다. 모델 전후 차이에는 해당 후보가 항목을 추가/수정/기각하는 데 어떤 근거를 주었는지 연결한다. 이미 사람이 알고 넣은 연결은 FCA 발견으로 세지 않는다. 직접 참조 검색으로도 찾을 수 있는 취소 호출 연결은 그대로 인정한다. 추가 가치가 없다는 결과도 정상이다.

형식 개념의 포함 관계는 속성 집합의 관계다. 업무의 상속·동일성·인과관계로 자동 변환하지 않는다. 별도 속성 함의를 설명한다면 고정 context에서만 성립하는 관찰로 한정하고 실제 지원 객체를 보여준다. 이번에 일반 implication basis나 업무 규칙 추론기를 추가하지 않는다.

### 4. 근거 검증기와 다음 agent 실험의 준비

작은 validator를 만들어 깨진 fact/candidate 참조, 중복 ID, 원문 hash/anchor 불일치, 필요한 출처/범위 정보 누락을 검출한다. 업무 의미의 참·거짓을 판정하는 도구가 아니다. source가 바뀌면 관련 모델 항목을 stale 또는 재검토 필요로 식별하고 성공/승인으로 통과시키지 않는다. 승인 상태에는 결정자·근거·시점이 필요하지만 형식 검사만으로 실제 사람 검토가 인증되는 것은 아니다.

agent가 모델에서 개념 → 관련 동작/조건 → 원문 근거 → 미확인 질문을 따라갈 수 있는 짧은 사용 예를 준비한다. 취소 경로 외에 환불 경로의 취소 호출과 대화상자 닫기의 차이가 드러나야 한다. “이것만 수정하면 충분하다”는 완전성 보장은 하지 않는다.

S2를 위한 과업/평가 절차 초안도 남긴다. 첫 후보는 **취소 요청 입력 계약이 바뀔 때 관련 클라이언트 경로를 빠짐없이 수정하는 작은 가상 변경**이다. 서비스/서버 계약 변경이 필요한지와 고정 fixture에서 무엇을 검증할지 구체화하되 이번에는 Vendure를 수정하거나 agent 비교를 실행하지 않는다. 모델을 먼저 동결하고 평가용 기대 변경·실패 조건은 agent 제공 자료에서 분리한다. 이미 내용을 아는 이 사례는 개발용 pilot이며 독립 일반화 평가는 아니다.

S2 조건은 같은 agent 모델·버전, 동일 소스 접근·도구·예산·기존 문서를 사용하고 도메인 모델 제공 유무만 달리한다. 별도 세션과 반복 실행, 실행 순서·오염 방지, 일반 문서와 동등한 정보량의 비교 조건도 설계한다. 변경 누락, 잘못된 수정/회귀, 전제 위반, 검증 성공, 사람 재작업, token/time와 모델 작성·검토·갱신 비용을 함께 측정한다. 아직 실행하지 않은 수치와 사람 비용은 `null`/미측정으로 둔다.

## 제외 범위

제품 core/CLI·논리 지원·strictNullChecks·FCA 상한 변경, 전체 앱 온톨로지 생성, 새 의존성/LLM/SMT/MCP/프레임워크 플러그인, OWL/RDF 채택, 범용 승인 UI, 자동 리팩터링은 이번에 포함하지 않는다. 모델은 JSON 실험 계약이며 제품 API가 아니다. 새로운 서버 정책·권한·상태 전이 지식을 임의로 채우지 않는다.

## 완료 조건

1. 새 manifest·모델 JSON/읽기 문서·근거 목록·validator·재현 명령이 있고 원본 revision으로 추적 가능하다. 자동/수동/미지원·검토 대기/승인 상태가 분리돼 있다.
2. 취소·환불·대화상자 닫기 경계가 모델에 반영되고, 추론하지 못한 서버/업무 정책과 사람이 결정해야 할 질문이 구체적이다.
3. 선택/속성 계약을 고정한 context의 단순 그룹/FCA 대조와 모델 전후 변경 근거가 있다. 불완전 입력/상한 초과면 원인·규모를 남기며 성공 산출물을 꾸미지 않는다.
4. 근거 변경·잘못된 연결을 validator가 실패/재검토로 잡는다. 분석 성공과 업무 의미 승인·agent 효용을 혼동하지 않는다.
5. 다음 agent 변경 과업과 기준선·평가 절차가 구체적이다. S1의 자동화 wall time·수동 작성 범위·미측정 비용을 따로 보고한다.

## 검증 방법

- 정상 입력 검증과 별도로 source hash/anchor 변경, 끊어진 참조, 승인 근거 누락을 변조한 부정 사례를 확인한다. 변경은 실험 fixture/임시 복제에만 적용한다.
- AST 역할 관찰기를 추가했다면 동명 타깃·선언 이름·실제 호출·중첩 callback 소속·unknown 구분에 의미 있는 회귀 테스트를 둔다. 단순한 문서/정적 표를 그대로 되풀이하는 테스트는 만들지 않는다.
- 같은 고정 입력으로 서로 다른 출력 디렉터리에 두 번 실행해 비시간 결과를 대조한다. 결과 파일에 시간/경로가 포함되면 비교 제외 규칙과 이유를 기록한다.
- `pnpm check`, `pnpm experiment`를 실행하고 이전 제품/예제 결과가 유지되는지 확인한다. 기존 corpus·공개 앱 결과를 덮어쓰지 않는다.

## 문서화 및 인계

실험 README와 `docs/reviews/YYYY-MM-DD-domain-model-prototype.md`에 구현 범위·재현 명령·판정·비용·실패·미확인 질문·다음 한 가지 권고를 적는다. PROGRESS를 실제 결과로 갱신하고 설계 결정은 DECISIONS, 관찰/가설은 RESEARCH에 추가한다. ROADMAP에서 S1의 상태와 S2로 진행할 근거를 구분한다.

AGENTS/CONTRIBUTING대로 최신 main·원격·사용자 변경을 확인하고 짧은 작업 브랜치에서 수행한다. 검증·staged diff 검토·커밋 → push → PR/자체 검토 → 필수 검사 충족 후 검증한 head로 merge → main 동기화까지 지속 승인돼 있다. 연구 결과가 부정적이어도 사실대로 전달한다.

주요 방향 판단은 사용자에게 요청한다. 예: 실제 업무 의미 승인, FCA에 지속 투자할지 여부, 코어 전제/상한 변경, 장기 온톨로지 형식, 코드 구조 변경의 범위. 이미 정한 실험의 작은 구현 선택이나 저장소 반영을 다시 승인받지는 않는다.
