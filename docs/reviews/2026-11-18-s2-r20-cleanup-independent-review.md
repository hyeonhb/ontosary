# R20 정리 보완 독립 리뷰

2026-11-18. [개발 보고서](2026-11-18-s2-r20-cleanup.md)와 PR #70 head `3f3cc134b80212c2ada9173eda797e6fadc4cab6`을 검토했다. **R20은 합의한 로컬 검증 범위에서 해결됐으며, 추가 병합 차단 결함을 발견하지 못했다.** 검증한 head로 PR #70을 squash 병합했다(`ca576e4`). 새 VM·실제 limactl/CLI·trace·정책·자격 증명·모델 호출은 하지 않았다.

## 구현 평가

정리 실행에 필요한 유한 capture와 디스크 진단 저장을 분리했다. 출력 초과 시 정리 명령은 계속 진행하며 일반 실험 명령의 초과 종료는 유지한다. 정리의 시간 제한, 소유권 확인, 불완전한 조회에 대한 unconfirmed 판정도 유지됐다. `bounded.py`의 pipe EOF 뒤 timeout 처리와 한 번의 종료 신호, `dispose()`의 기존 소유권 파일 잠금 및 기록 오류 분리는 이번 국소 결함과 직접 관련된 변경이다.

구현은 기존 smoke 도구 안에 머물며 별도 실행 프레임워크를 추가하지 않았다. 메모리에는 제한된 출력만 보유하고 초과분을 버리므로 처리 시간은 읽는 출력량에 비례하되 명령 마감으로 제한된다. 디스크 저장 용량 계산은 기존 진단 파일 수에 비례하며, 현재 유한 smoke 범위에서 추가 색인이나 범용 저장 계층을 도입할 근거는 없다. 구현 순서나 helper 선택이 이전 제안과 다른지는 결함 기준으로 삼지 않았다.

## 독립 검증

- Python32개와 `pnpm check`의304개 테스트·타입 검사·예제 build가 통과했다. 진단 조회/저장 실패, 정리 명령 실패/timeout, 잘린/잘못된 조회, 소유권 거부 및 일반 명령의 출력 초과 중단을 포함한다.
- `verify_historical.py --reproduce-r20`를 재실행했다. 당시2008351 코드에서 예산 여유 시 stop/delete 완료·가짜 VM 제거, 예산 소진 시 둘 다 미완료·가짜 VM 잔존을 다시 확인했다. 수정 코드의 회귀에서는 같은 반례가 통과했다.
- 독립 추가 조합3개(예산 소진+stop/delete 대량 출력, 예산 소진+진단 용량 조회 실패, 예산 소진+모든 JSON 보고 쓰기 실패)에서도 실제 대체 stop/delete 완료와 가짜 VM/소유 root 제거를 확인했다. 모두 complete였으며 마지막 경우 receiptWritten=false를 함께 반환했다. 최종 파일 총량은 각각4,133,133·4,131,228·4,129,200bytes로4MiB 이하였다.
- 독립 무한 출력 subprocess는 discard 정책에서도0.3초 마감에 종료됐다(관측0.3014초, exit−9, timedOut/truncated=true). 보존 stdout은 지정한1KiB 이하였다.
- 과거 verifier의 blocked-before-payload·VM1/sandbox1·payload 미시작·cleanup complete, index98파일/121,674bytes를 재현했다. index를 포함한 과거 tracked99파일은2008351과 bytes가 모두 같았다.
- after.json의4개 소스 hash가 현재 파일 및 구현 커밋e7759f9와 일치하고, before/after가 같은 fixture를 사용함을 확인했다. 이후 커밋은 문서/증거 변경만 포함한다.

가짜 외부 명령 검증은 실제 VM의 성공이나 전체 OS/파일시스템 무응답에 대한 보장이 아니다. 기록 매체 전체가 쓰기 불가할 때 영구 receipt를 보장하지 않는 한계는 보고서와 일치하며, 자원 정리 결과와 기록 성공 여부를 분리해 반환한다. 당시 실제 VM 폐기 증거와 이번 실패 경로의 로컬 회귀를 구분한다.

## 방향과 다음 판단

지시 개정 후 개발 세션은 필요한 구현과 검증을 선택했고, 완료 기록상984.934초(약16분25초)로45분 안에 인계했다. 이번에는 환경을 확대하지 않고 원래 결함을 해결했다. 한 사례만으로 자율성 확대가 속도 향상의 원인이라고 단정하지 않지만, 목적·결과 기준 중심의 지시를 유지할 근거와 충돌하지 않는다.

추가 보완 지시는 필요하지 않다. 다음 불확실성은 고정 CLI가 EROFS를 발생시킨 정확한 쓰기 대상이다. 다음 작업은 **해당 바이너리와 대응이 확인되는 소스·설정·저장 근거로 원인 후보를 좁히는 진단**을 권한다. 새 구현 기반을 먼저 늘리지 않는다. 실제 trace/재실행이 필요하면 목적·범위·예산을 사용자와 합의하며, 권한 확대나 C안 채택·Vendure/인증/model 통합으로 자동 전환하지 않는다.

R20 해결은 R11 전체 해결이나 H-O/H-F 입증이 아니다. PR #67·후속 실제 시험·본 비교는 계속 보류한다.
