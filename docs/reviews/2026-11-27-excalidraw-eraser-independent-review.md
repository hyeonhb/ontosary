# Excalidraw 지우개 사례 독립 리뷰

교정 사례로 채택한다. PR head `c8facaa`에서 재현 스크립트를 실행해 새 upstream 사본 두 개의 결과를 대조했다. 같은 좌표에서 마우스를 뗀 뒤 병합 부모에서는 두 점이 모두 남았고, 병합본에서는 드래그 경로 근처의 점만 삭제됐다. 양쪽 판정기는 원래 요소 ID의 삭제 플래그와 살아 있는 장면의 멤버십을 함께 확인한다. 이 결과는 줌 1의 편집기 통합 테스트 한 장면에 해당한다. 독립 검산에서 병합을 막을 결함을 발견하지 않아 [PR #129](https://github.com/hyeonhb/ontosary/pull/129)를 병합했다. [준비 결과](2026-11-27-excalidraw-eraser-preparation.md)

기록을 고정한 커밋부터 제출까지 note 내용이 같고, 기록에 든 소스·설정 파일 6개의 해시도 일치했다. 당시 코드와 복원 테스트는 로컬 점열 생성, 제자리 해제 시 끝점 보정과 짧은 획 보존, 지우개 드래그 중 후보 수집, 입력 해제 시 삭제 확정을 뒷받침한다. 특히 클릭은 해제 위치 아래의 요소를 추가하는 경로가 있어 드래그 예제로 두 동작을 구별할 이유가 있다. 적절한 접촉 거리, 다른 장치에서의 체감, 이 기록으로 절약한 수정 비용은 미측정이다. 작성자는 작은 점이라는 단서를 알고 있었다. 일반 탐색이 최초 발견 경로였고 공개 CLI는 두 심볼의 위치를 재확인했다. [수정 전 기록](../../experiments/first-use/excalidraw-eraser/note.md)

## 컴파일 진단과 FCA의 입력 크기

고정 자료 시점 `3bdaafe`에 의존성을 설치한 동일 사본에서 같은 패키지 tsconfig를 두 컴파일러로 검사했다. 두 실행 모두 `tsc -p <packages/excalidraw/tsconfig.json> --emitDeclarationOnly false --noEmit --pretty false`를 사용했다. 원 설정은 선언만 출력하도록 되어 있어, 출력 없는 대조를 위해 양쪽에서 이 옵션을 해제했다.

| 실행 | 결과 |
| --- | --- |
| Excalidraw가 고정한 TypeScript 4.9.4 | 종료 0, 진단 0 |
| Ontosary가 사용하는 TypeScript 5.9.3 | 종료 2, 진단 7. 버퍼·DOM API 타입 6건, 이벤트 대상 타입 1건 |
| Ontosary 공개 CLI의 설치 후 재실행 | scan 종료 1, 진단 7개의 코드·위치·메시지가 제출 JSON과 일치. concepts 종료 1, stdout 0바이트, 컴파일 오류 반환 |

이 사본에서는 컴파일러와 그에 딸린 타입 선언을 바꾸는 것으로 진단 차이가 재현된다. CLI는 프로젝트 전체의 컴파일 오류를 확인한 뒤 후보 탐색에 진입한다. 따라서 이번 차단은 FCA 열거 전이며, 일곱 진단의 직접 위치는 모두 지우개 모듈 밖이다. 위치만으로 분석할 타입과의 독립성을 보증할 수는 없다. [설치 후 진단](../../experiments/first-use/excalidraw-eraser/installed-cli.json) · [CLI의 오류 처리](../../src/cli/index.ts)

독립적으로 다시 얻은 설치 후 scan JSON에 현행 `buildContext`만 적용해 크기를 확인했다. 분석 파일 370개, 객체 4,475개, 속성 4,464개였다. 기본 입력 한도는 객체 128개·속성 64개다. 이 입력 크기라면 컴파일 오류만 해소해도 같은 패키지 범위로 후보를 열거할 수 없다. 이 계수에는 FCA 열거나 진단 무시 후의 후보 채택이 포함되지 않는다. [문맥 구성과 기본 한도](../../src/core/fca.ts)

저장소 검사는 `pnpm check` 299개 통과·기존 캐시 의존 5개 건너뜀, `pnpm experiment` 기존 비교 4/4였다. A/B/C 참가 호출은 0회다.

## 다음 판단

이 사례는 사용자 동작을 검산하고 기록의 출처를 점검하는 데 재사용한다. 기록이 agent의 변경에 도움이 되는지 보려면 기록을 먼저 동결한 채 별도의 후속 변경을 평가해야 한다. FCA의 작성 기여를 우선 확인하려면 과업에서 설명할 수 있는 작은 분석 범위를 먼저 정하고, 전체 프로젝트의 타입 정보를 보존하면서 그 범위 안에서 후보를 만들 수 있을지 따로 논의할 만하다. 컴파일러 호환 정책, 부분 분석 계약, 상한 변경과 A/B/C 실행은 이번 리뷰에서 결정하지 않았다.
