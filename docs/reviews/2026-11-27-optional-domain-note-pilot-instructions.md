# 개발 세션 지시문 · 변경 중인 agent가 도메인 기록을 요청하는가

**실제 변경 과업 두 건에서, 혼자 조사하던 agent가 코드 근거를 모은 기록을 선택하는 순간과 그 선택의 결과를 관찰해 주세요.** 기존 Vendure 실험에서는 주어진 기록이 회귀 사례에 재사용됐습니다. 이번에는 기록 없이 시작해도 끝낼 수 있는 과업에서 요청 여부, 새로 확인한 판단, 작성 비용까지 확인합니다. 결과는 이 조건에서의 agent 행동으로 보고하고 사람의 사용 의향은 미측정으로 유지합니다. ## 모델을 호출하기 전에

공개 TypeScript 업무 앱의 실제 변경 이력에서 과업 두 건을 고르세요. 기존 준비물을 쓸 수 있는 저장소도 좋습니다. 부분 출고와 이미 실험한 과업은 제외합니다. 먼저 대상 저장소·기간·조회 순서와 적격 기준을 기록하고, 그 순서에서 **처음 적격인 두 건**을 씁니다. 적격 기준은 변경 전 소스가 있고, 두 곳 이상에 걸친 업무 판단이나 보존할 예외를 후속 변경·테스트로 검토할 수 있는 것입니다. 기준선의 예상 실패, FCA 실행 성공, 견본과의 유사성은 선정 기준에서 제외합니다. 두 건을 확보하지 못하면 범위를 임의로 넓히지 말고 확보한 수와 제외 이유를 보고합니다.

참가 호출 전 저장소에 사전 계획을 커밋하고 그 SHA를 결과에 남기세요. 과업별 변경 전 리비전, 참가자용 변경 요청 원문, A/B 공통 안내와 B 전용 선택 문구, 실행 순서·모델·예산, 채점할 필수 업무 조건·보존 동작·회귀 사례를 고정합니다. 작성자와 작업 agent에게는 변경 전 소스·당시 일반 문서만 주고, 해결 패치·후속 테스트·이슈 토론의 정답·채점 기준은 검토자가 보관하세요. 참가자에게는 제품 성능에 관한 기대를 알려줄 필요가 없습니다.

## 한 과업에서의 실행

| 역할 | 받는 입력과 할 일 |
|---|---|
| A · 기본 작업 agent | 깨끗한 변경 전 사본에서 기존 검색·읽기 도구로 조사합니다. 첫 변경 계획으로 수정할 위치와 이유, 보존할 동작, 검증할 회귀 사례와 소스 근거를 제출합니다. |
| B · 기록을 선택할 수 있는 작업 agent | A와 같은 과업·도구·출발점·제출물을 사용합니다. 기록 없이 먼저 조사합니다. 처음 찾은 근거와 남은 의문을 짧게 남긴 뒤, 선택권을 한 번 안내받습니다. 그대로 완료하거나, 필요할 때 기록을 한 번 요청할 수 있습니다. |
| 작성 agent · 명시적 요청이 있을 때만 | 새 세션에서 같은 변경 전 사본, 원래 과업, B가 실제로 보낸 질문만 받습니다. 공개 CLI·일반 검색을 자유롭게 써서 관련 조건·예외·파일/심볼·미확인 사항이 담긴 한 장을 작성합니다. 결과 패치나 완성된 변경 계획을 대신 만들지 않습니다. |

A도 같은 초기 조사 시점에 찾은 근거와 남은 의문을 남깁니다. 추가 조사 없이 바로 답할 수 있으면 그렇게 기록하고 끝낼 수 있게 하세요. B의 안내 예시는 다음과 같습니다.

> 이 변경과 관련된 코드 조건과 근거를 한 장으로 요청할 수 있습니다. 요청하면 별도 agent가 작성하고 그 시간과 사용량도 과업 비용에 포함됩니다. 필요할 때 확인하고 싶은 점을 한 문장으로 요청하거나, 그대로 작업을 마치세요.

요청이 없으면 작성자를 실행하지 않습니다. 요청이 있으면 그 시점과 질문·직전 판단을 보존하고, 작성자의 첫 기록을 손보지 않은 채 **같은 B 세션**에 전달합니다. B는 최종 제안에서 기록으로 추가·수정·확인한 판단과 자신이 별도로 찾은 근거를 구분합니다. A와 B에는 같은 형식의 첫 변경 계획을 받습니다. 요청 이유와 기록 사용 내역은 별첨으로 받아 품질 채점 때 가릴 수 있게 하세요. B에 전달하는 요청 기록 한 장 외에는 세션 간 대화·산출물을 공유하지 않습니다. 수동으로 한 장을 받아 전달해도 충분합니다. 진행자가 준비된 디렉터리와 기존 CLI로 할 수 있는 범위를 먼저 사용하세요.

## 품질·선택·비용을 판정하는 방법

- **품질을 먼저 판정합니다.** A/B 표시와 요청 이력을 가린 첫 제출을 같은 사전 기준으로 읽고, 업무 조건과 회귀 사례마다 충족·누락·오류·판정 불가를 근거와 함께 표시합니다. 다른 위치나 구현으로 같은 동작을 보존하는 제안도 인정합니다. 평가 대상은 변경 계획이며 실제 패치의 성공은 미측정입니다.
- **요청과 효용을 따로 봅니다.** B가 어느 시점에 무엇을 몰라 요청했는지, 기록의 어느 주장과 소스가 최종 판단에 이어졌는지 대조합니다. 이미 찾은 사실을 재확인했다면 재확인으로 기록합니다. 새 조건을 찾아 누락을 막은 경우와 잘못된 기록으로 오류가 생긴 경우도 같은 기준으로 남깁니다. 작성자가 처음 찾은 근거가 일반 검색인지 Ontosary 출력인지 기록해 두세요. 작성자 호출은 추가 agent 한 명의 도움도 포함하므로 B의 결과를 Ontosary나 FCA 단독 효과로 돌리지 않습니다.
- **비용은 A 대 B 전체로 계산합니다.** 모델·추론 설정과 작업 agent의 가용 시간·도구는 같게 둡니다. 과업별 최초 제출까지의 실제 경과, 역할별 활동·대기 시간, 요청 수와 입출력 토큰을 남깁니다. B 토큰에는 작성자와 기록을 받아 읽은 후속 비용을 포함합니다. 벽시계 경과에 이미 들어간 작성 대기는 이중 합산하지 않습니다. 환경 준비·진행자 개입은 별도, 캐시 토큰은 입력의 부분집합, 미제공 사용량은 결측으로 표시합니다.

## 예산과 마감

이번 지시문의 실행 단위는 **2과업 × A/B 각 1회**, 작성자는 B의 요청 시 과업당 최대 1회입니다. 총 4개 작업 세션과 최대 2개 작성 세션입니다. 기존 로그인 경로와 직전 대리 검증의 요청 설정(`gpt-6.2-sol`, `medium`)을 기본으로 하고, 첫 호출 전에 현재 가용한 시간·사용량 범위 안에서 구체적인 운영 한도를 기록하세요. B가 작성자를 기다리는 동안에는 작업 agent의 조사 시간과 별도로 대기를 계측합니다. 새 유료 경로, 추가 참가 세션, 평가기·실행 환경의 확장이 필요하면 집행 전에 이유와 대안을 공유하세요. 자료 노출, 모델 변경 필요, 사용량 결측, 예산 도달이나 실행 실패 시 이미 얻은 결과와 비교 가능한 범위를 보존합니다. 성공 사례를 얻으려는 교체·재시도는 하지 않습니다.

결과 PR에 **예정 과업 전체**를 올리세요. 과업별로 A/B 첫 제안의 품질, 요청 여부와 이유, 요청 전후 달라진 판단과 근거, 작성 비용을 포함한 총비용을 한 행에서 비교할 수 있으면 됩니다. 고정 계획, 실제 안내·질문·기록·최초 제출·계측 근거를 연결해 모델 재호출 없이 판정을 검토할 수 있게 하세요.

두 과업 모두 요청이 없으면 해당 안내·조건에서 자발적인 요청을 관찰하지 못한 것으로 마감합니다. 요청했지만 같은 품질에 비용만 늘면 추가 비용을 그대로 보고합니다. 누락 감소나 같은 품질에서의 비용 감소가 있다면 그 차이를 낸 구체적인 판단을 한 건 짚어 주세요. 혼합 결과와 미완료도 원래 과업에 남기고, 다음 과업·반복 실행은 이 회차의 리뷰 뒤 결정합니다. 두 건은 탐색적 관찰이며 사람 수요나 일반적인 우위의 추정에 쓰지 않습니다.
