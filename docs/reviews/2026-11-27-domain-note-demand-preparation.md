# 자기 프로젝트에도 이런 변경 기록을 원하는가?

**자료 준비 완료 · 실제 회차 미실행.** 이 과업에서 개발자에게 전달한 견본 0건, 응답 0건, 자기 과업 제출 0건이다. 참가자는 미배정이며 시험 적용 동의와 실제 사용도 관찰되지 않았다. 이 수치는 준비 시점의 집계다. 개발자 수요는 미측정이다.

[개발자가 읽을 한 장](../guide/examples/partial-fulfillment.md) · [복사해서 보낼 질문과 견본 링크](../../experiments/first-use/domain-note-demand/question.md)

## 첫 전달 전에

운영자는 사용자가 정한 접점에서 TypeScript 프로젝트의 변경을 agent와 함께 수행해 본 개발자에게만 전달한다. 견본을 처음 보는 사람을 대상으로 하며, 이 사례의 준비·성공 결과를 아는 개발 세션은 제외한다. 첫 회차 운영안은 **대상 3명을 미리 고정하고 첫 전달 7일 뒤 마감**하는 것이다. 운영자가 대상·접점과 마감 일시를 정한 뒤 시작한다. 현재 접점·대상자·달력상의 마감일은 미정이다.

세 사람에게 같은 커밋의 질문과 견본을 건넨다. 배경 설명이나 답 예시를 덧붙여 과업을 만들어 주지 않는다. 거절하거나 답하지 않은 사람도 해당 회차의 대상에 남긴다. 진행자는 마감 때 한 번 집계한다. 참가 전에는 위 준비 기록만 둔다.

## 응답을 어떻게 읽을까

익명 번호별로 **전달 여부·응답 상태 / 변경 요청과 확인할 조건 / 현재 확인 방법 / 견본에 대한 반응 / 과업 제출 / 시험 적용 동의 / 실제 사용**을 기록한다. 참가자가 말하지 않은 항목은 ‘미확인’으로 둔다. 공개 요약에는 개인 이름, 식별 가능한 링크, 비공개 소스 없이 변경 요청과 행동의 요지만 적는다.

| 관찰 | 기록 기준 |
| --- | --- |
| 전달·응답 | 전달하지 못하면 ‘미전달’. 전달 후 마감까지 답이 없으면 ‘무응답’. 참여를 거절한 답은 ‘거절’, 읽고 쓸 일이 없다고 답하면 ‘적용할 일 없음’으로 구별한다. 거절도 회신 수에 포함한다. |
| 칭찬·사용 의향 | “보기 좋다”, “언젠가 써보고 싶다” 등은 반응으로 보존한다. 이 말만으로 자기 과업이나 시험 적용 동의를 집계하지 않는다. |
| 구체적인 자기 과업 | 본인이 실제로 받은 변경과 확인할 조건이 모두 식별되면 1건이다. 링크는 선택이다. 현재 방식은 별도 기록한다. 동료·agent가 대신 만든 문제는 제외한다. |
| 시험 적용·실제 사용 | 제출한 과업에 한 번 적용하겠다고 명시하면 ‘동의’. 자기 작업의 어느 단계에서 무엇을 검토했는지 보고하면 ‘사용’과 그 근거를 별도로 적는다. 비공개 산출물을 요청할 필요는 없다. |

같은 사람이 과업을 제출하고 적용에도 동의하면 두 관찰에 모두 표시한다. 마감 보고에는 대상·전달·회신 인원, 실제 자기 과업 건수, 적용 동의·사용 인원을 각각 쓴다. 회차 규모가 작아 비율로 일반화하지 않는다.

## 다음 판단

- **자기 과업과 적용 동의가 함께 있다면** 그 변경 요청, 확인할 조건, 현재 방식을 묶어 다음 기록 작성 비용 비교의 후보로 제시한다. 실제 사용이 있었다면 어떤 판단에 썼는지도 함께 남긴다.
- **호평만 있거나 과업을 냈지만 적용은 원치 않는다면** 당사자가 밝힌 이유와 아직 모르는 점을 남긴다. 현재 방식으로 충분하거나 기록이 번거롭다는 응답도 근거다. 대상 개발자와 첫 공개의 약속을 먼저 재검토한다.
- **아직 전달하지 못했거나 회신이 없다면** 각각 미실행과 무응답으로 마감한다. 사람의 반응을 agent로 대체하지 않는다. 후속 적용이나 프로젝트 분석은 결과 리뷰에서 결정한다.

## 편집·검산 근거

작성자의 최초 기록과 후속 agent의 제안에서 일반 주문의 창 진입 조건, 행별 수량 상한, 제안 문구를 추렸다. 공개 견본만으로 세 장면의 현재 버튼과 제안할 안내를 각각 읽을 수 있도록 표에 나란히 놓았다. 제작 경위에 일반 검색·원문, `scan`의 재확인, FCA 상한 종료와 편집·정책 승인 상태를 명시했다.
