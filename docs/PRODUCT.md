# 제품 방향

## 문제와 사용자

최종 목표는 기존 프론트엔드 프로젝트를 **AI agent가 도메인을 이해하고 수정하기 좋은 프로젝트로 점진적으로 전환하도록 돕는 것**이다. 사람에게 읽기 좋은 코드는 agent에게도 도움이 된다. 다만 타입·함수·조건문·API·UI·테스트·문서만으로 업무 개념과 관계, 규칙의 의도·예외가 충분히 드러나지 않는 부분을 문제로 삼는다.

Ontosary는 코드의 사실과 개발자가 검토한 개념·관계·규칙을 연결해 agent와 개발자가 참조하고 유지할 도메인 모델을 지향한다. 온톨로지는 이 지식을 명시하는 수단이고, FCA는 기존 코드의 공유 속성에서 모델 후보를 발견해 구축 부담을 줄이기 위한 방법이다. 자동 추출만으로 업무 의도를 복원한다고 전제하지 않는다.

첫 사용 경로는 업무 개념에서 관련 코드·조건의 근거를 찾는 탐색이다. 이후 작은 변경 과업과 변경 후 지식 갱신으로 가치를 검증한다. 초기 전환은 기존 코드 옆에 검토 가능한 모델과 근거 연결을 두는 형태이며, 코드 구조 변경이 필요한지는 후속 관찰로 판단한다. 사용자의 예시 그림은 역할 설명이며 확정된 목표 아키텍처가 아니다(ADR-020).

## 이름

Ontosary = Ontos + -ary. Ontos는 존재·존재자와 관련된 고대 그리스어 어근이며 ontology의 어원적 기반이다. -ary는 관련된 장소·체계를 나타내는 접미사다. 코드의 개념·관계·규칙을 발견하고 축적하는 체계라는 제품 철학을 표현한 조어이며 특정 온톨로지 기술이나 형식을 뜻하지 않는다.

## 유지할 원칙

1. **Developer Value First** — 모델의 정교함보다 agent와 개발자의 이해·변경 정확성 및 총비용에 주는 가치.
2. **Codebase First** — 실제 코드 근거에서 출발하고 읽기만으로 도입 가능. 구조 변경은 필요가 확인된 범위부터.
3. **Ontology as a Means** — 개념과 관계의 정리는 수단이며 개발 방법론의 강제가 아님.
4. **Incremental Adoption** — 작은 tsconfig 범위와 필요한 도메인부터 시작.
5. **Evidence Based** — 파일·심볼·소스 위치·분석 전제를 연결.
6. **Human Verified** — 자동 후보와 사람이 승인한 지식을 분리.
7. **Framework Agnostic Core** — 공통 TS 코어 위에 필요할 때 프레임워크 정보를 추가.
8. **Empirical Validation** — 실제 가치와 분석 방법의 효과는 비교 실험으로 확인.

전면적인 새 아키텍처 이전, 도메인 모델 전체의 선작성, OWL/RDF 사용, 코드 생성, 자동 리팩터링, 공식 업무 정책으로의 자동 승격을 요구하지 않는다. 점진적인 전환을 돕는다는 목표와 도입 강제는 구분한다.

## 성공 기준

같은 소스·도구·예산과 충분한 기존 문서를 제공한 기준선에 비해 agent의 변경 누락·잘못된 수정·회귀·근거 없는 해석이 줄고, 검증 성공과 사람의 재작업 비용이 개선되는지 평가한다. token/time뿐 아니라 모델의 작성·검토·갱신 비용을 포함한다. 검색 시간·근거 정확성은 이를 돕는 중간 지표다.

모델 자체의 효과(H-O)와 FCA가 모델 구축·검토에 추가하는 효과(H-F)는 별도 가설이다. 동일 facts의 직접 탐색·단순 그룹과 비교해 FCA의 추가 기여를 측정한다. 개념 수나 격자 크기는 성공 지표가 아니다. 현재는 두 가설 모두 미검증이며, 작은 재현 가능한 개선과 최소 사용성이 확인되면 Public Beta를 검토한다.

현재 PoC의 범위와 장기 계획은 [ROADMAP](ROADMAP.md), 구현 여부는 [PROGRESS](PROGRESS.md)가 기준이다.
