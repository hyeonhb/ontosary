# 제품 방향

## 문제와 사용자

프론트엔드 개발자, 신규 합류자, 도메인 담당자와 코드 리뷰어는 타입·함수·조건문·API·UI·테스트·문서에 분산된 업무 지식을 이해하기 위해 많은 파일을 탐색한다. Ontosary는 코드의 근거를 모으고 관련 개념·규칙의 후보를 제시하여 탐색·변경 영향 확인·지식 유지 비용을 줄이는 도구를 지향한다.

## 이름

Ontosary = Ontos + -ary. Ontos는 존재·존재자와 관련된 고대 그리스어 어근이며 ontology의 어원적 기반이다. -ary는 관련된 장소·체계를 나타내는 접미사다. 코드의 개념·관계·규칙을 발견하고 축적하는 체계라는 제품 철학을 표현한 조어이며 특정 온톨로지 기술이나 형식을 뜻하지 않는다.

## 유지할 원칙

1. **Developer Value First** — 모델의 정교함보다 탐색 시간·이해·변경 안전성에 주는 가치.
2. **Codebase First** — 기존 코드·아키텍처를 유지하며 읽기만으로 시작.
3. **Ontology as a Means** — 개념과 관계의 정리는 수단이며 개발 방법론의 강제가 아님.
4. **Incremental Adoption** — 작은 tsconfig 범위와 필요한 도메인부터 시작.
5. **Evidence Based** — 파일·심볼·소스 위치·분석 전제를 연결.
6. **Human Verified** — 자동 후보와 사람이 승인한 지식을 분리.
7. **Framework Agnostic Core** — 공통 TS 코어 위에 필요할 때 프레임워크 정보를 추가.
8. **Empirical Validation** — 실제 가치와 분석 방법의 효과는 비교 실험으로 확인.

새 아키텍처로의 이전, 도메인 모델 전체 작성, OWL/RDF 사용, 코드 생성, 자동 리팩터링, 공식 업무 정책으로의 자동 승격을 요구하지 않는다.

## 성공 기준

검토자가 올바른 근거에 더 빨리 도달하고, 잘못된 의미 해석을 줄이며, 코드 변경 후 지식을 저렴하게 유지할 수 있어야 한다. 개념 수나 격자 크기는 제품의 성공 지표가 아니다. 승인 소요 시간·근거 정확성·추출 precision/recall·유지 비용을 평가한다. 재현 가능한 초기 개선과 최소 사용성이 확인되면 학술적 완결성 이전에도 Public Beta를 검토한다.

현재 PoC의 범위와 장기 계획은 [ROADMAP](ROADMAP.md), 구현 여부는 [PROGRESS](PROGRESS.md)가 기준이다.
